# Nanobot upstream migration plan

Status: implementation roadmap, not a deployment authorization. Prepared 2026-09-08; conversational busy-input target clarified in this update.
Accepted direction: update the upstream base while preserving ALL custom logic and features through retained implementations or verified equivalent replacements; deliver the agreed context enhancements alongside the migration. The target experience is one owner-bound personal assistant across channels, with conversational steering, queuing, stopping and status while it is busy. H1 below is required before claiming that harness experience, but is not silently enabled by the source migration. Sustained goals remain a separate optional follow-on outside migration completion. Numeric defaults and operational choices remain recommendations where identified.

## 1. Baseline and architecture decision

Start from `staging` commit `4aa562d9` (2026-09-01), already represented by `codex/upstream-migration`. Import official upstream at **`f47b8f23155ddec23cfb80ec001b544d495df89c`** (2026-09-08); do not track moving `main` during this project.
The common base is `63d646f7` (2026-03-31), with 118 fork-only and 2,800 upstream-only commits. The latest release, `v0.3.0` (2026-07-25), is 705 upstream commits behind the selected target.

Recommend pinned main because the studied context governor, conversation state, recovery and current channel/runtime architecture are there. Using the older tag would require another selective backport project before delivering the accepted context direction. The tag offers a smaller, released target, but its release label does not establish compatibility with this fork. Freeze the selected SHA and qualify it locally; do not infer production readiness from upstream tests or version `0.3.0`.

Use upstream implementations as the new internal foundation, with narrow adapters for proven fork contracts. Keep one canonical turn execution path, one context governor, one authoritative source transcript and one effective authorization decision at tool dispatch. Preserve upstream security improvements wherever compatible, then compose the fork's stricter role and repository restrictions on top.

Reject a reset/rebase onto upstream that drops staging ancestry, blanket “ours/theirs” conflict resolution, retaining two full provider/context engines, and cherry-picking thousands of commits independently. Also reject a wholesale product switch to upstream defaults: imported modules and dependencies do not authorize their UI, scheduling, plugin or tool behavior.

### GUI and startup compatibility contract

The GUI is an additional interface, not a replacement harness. Preserve the current production lifecycle: **systemd → foreground `nanobot gateway` → configured Telegram/cron workflows**. Keep existing config/workspace paths, environment precedence, service-user permissions, shutdown/restart ownership and logging. Do not switch the service to `nanobot webui`, a desktop launcher, or a second background gateway.

Verified differences at the pinned upstream SHA:

| Upstream evidence | Required migration behavior |
| --- | --- |
| `channels/websocket/manifest.py` has `default_enabled=True`; `runtime.py` also defaults its config to enabled | Missing GUI settings in old configs must not silently enable a WebUI/WebSocket listener. Apply an explicit compatibility default through config migration and effective channel activation. Audit discovery and validation rather than assuming omission disables it. |
| `cli/entry.py` changes bare-command dispatch; `cli/agent.py` defaults interactive `agent` to native TUI and offers `--classic` / `--no-tui` | Preserve staging's bare-command, interactive prompt, one-shot and result-streaming behavior. TUI adoption is separate opt-in work; do not force existing callers to discover new flags. |
| `cli/gateway.py` accepts config/foreground/background options but has no `--log-file` option | Retain our `gateway --log-file` compatibility and its rotation behavior. The exact command in the existing systemd unit must remain valid; do not silently discard logging or require service-command changes to hide the regression. |
| `cli/webui.py` can enable the channel, save config, synchronize workspace templates and start/attach to a gateway | Treat this as deliberate setup/startup, not a read-only viewer. Ordinary gateway/CLI startup must not invoke this setup path, rewrite config/templates or open a browser because GUI code was imported. Preserve legitimate existing state writes separately. |
| Upstream packaging includes WebUI assets and build hooks | Build required assets in the release environment. A headless service start must not prompt for or launch frontend builds, download TUI components, or install GUI dependencies on demand. |

Required evidence before acceptance:

- An old config without GUI fields starts its intended headless gateway without a new WebUI/WebSocket listener, browser, native-TUI process or second gateway. Existing intended API/health listeners are checked against the baseline rather than prohibited wholesale.
- The systemd `ExecStart` arguments parse and run with temporary equivalents of the same config/log paths; log output and rotation remain functional, and systemd retains process/restart ownership.

- If GUI enablement is pursued later, its requests must enter the same canonical turn path and preserve custom policies, session isolation and config fields. ## 3. History and integration strategy

1. Record staging/upstream/base SHAs and a contract-to-test inventory before changing code. Preserve untracked `sessions/` and existing design documents; never bulk-stage them. Use only sanitized fixtures in version control.
2. Prepare the merge in an isolated checkout descending from the current staging-based migration branch. Keep an immutable baseline reference for comparison. A normal merge of the pinned SHA should retain both histories; it is not permission to merge or push now.
3. One integration owner resolves the merge index. Classify conflicts as upstream mechanics, fork contract adapter, persistent schema, or product enablement. Keep a short resolution ledger with tests and rationale, especially modify/delete cases such as background subagents and channel file-to-package moves.
4. During conflict resolution, establish an importable upstream-shaped dependency graph first: packaging, entrypoints, config loading, tool registry and channel discovery. Temporary disabled compatibility stubs must fail clearly and be removed before package acceptance. Do not spend weeks porting leaf features onto a non-importable tree.
5. Review the merge resolution separately from subsequent compatibility commits. Preserve fork tests before accepting upstream file replacements. Resolve overlapping symbols through the single owner; workers can supply scoped patches only after boundaries are stable.
6. Freeze the resulting merge candidate. Subsequent upstream movement is a separate reviewed update; no automatic rebase onto latest main during qualification. Promote a tested fork release commit, never a branch name alone.

The early merge need not be deployable. Its exit gate is clean imports/config construction with external startup disabled, a documented remaining compatibility list, and preserved baseline tests. Only the later integrated candidate may reach runtime rehearsal.

## 6A. H1: conversational control of a busy assistant

The [busy-input inbox engineering proposal](migration/h1-busy-inbox-design.md) records the current 20-message fallback/republication gap, a candidate one-owner/two-lane ordering and crash protocol, and the material choices to accept before H1 implementation. It is a design supplement, not a change to the frozen upstream target or an authorization to activate the candidate.

**Accepted behavior.** Channels are authenticated input/output transports for one personal assistant, not separate agents or memories. A message received during work can steer that active run, wait for the next turn, stop it, or ask for grounded status. Telegram and other IM channels must understand and answer ordinary language while the task runner is busy, with no required buttons or command syntax. A separate bounded control-model inference may run concurrently with the task call to make an informed IM reply possible; it is not a second task-working agent. Preserve fast, explicit stop controls as a fallback. This is a post-migration harness-experience target, not a claim that pinned upstream or the current fork already implements it.

- **Admission and receipt.** Authenticate the sender and bind them to the canonical owner/session before any control or task admission. Persist a stable ingress ID, full original message, source channel/chat/reply route, trust/scope and acceptance revision before acknowledging it. Send a prompt, neutral receipt if interpretation is not yet ready; later send a conversational, truthful routing confirmation. The current Telegram reaction/typing indicator before the in-memory bus is not a durable receipt (`nanobot/channels/telegram.py`, `nanobot/bus/queue.py`). Channel receipts are not fake user turns or task completions. Keep cron/system/automation work on its existing explicit path rather than treating it as a personal message.
- **IM control inference while busy.** Run a bounded, stateless control-model request independently of the active model/tool call so an informed IM reply need not wait for the task runner's next safe step. Give it authenticated direct user content and a minimal factual snapshot of active work, not an independent memory. Dispatch it from a capacity-limited admission worker; do not hold a Telegram polling/update handler open while awaiting the model. It proposes `steer`, `next-turn`, `stop`, `stop-and-replace`, `status` or `clarify` and optionally a short reply draft. It has no tools or authority to grant permissions, cancel work, commit an inbox route, answer a separate substantive task, or promise completed work. The single harness writer validates and commits the route first; only then may the channel send a reply grounded in the committed state (for example, “I'll add this at the next step,” not “I already did it”). The task runner remains the sole consumer of task input. Determine the isolated provider configuration, latency ceiling and model budget before implementation rather than assuming concurrent inference is free or always available; a neutral receipt and safe queue remain the outage fallback.
- **Ambiguity and fallback.** A control-model timeout or error defaults to `next-turn` with an honest channel reply, never a guessed stop or steer. An ambiguous or low-confidence intent stays visibly `awaiting-clarification` and is not claimable as either task; ask naturally and attach the answer to its ingress ID, with a reviewed expiry policy so it cannot disappear silently. An immediate neutral receipt still works when the model/provider is unavailable. Do not silently infer stop from quoted, forwarded or otherwise untrusted text. An explicit authenticated `/stop` remains a fast fallback without a routing-model dependency.
- **What the main agent consumes.** For `steer`, present the **full user message** to the active agent exactly once at its next safe model step, with its origin and policy context; a routing label or summary is not a substitute. Do not alter an already-sent model request or an executing tool. For `next-turn`, keep the task payload out of the active run and give it to the same assistant in a new turn. A route-only model call is not an extra task-history user row. If the run ends before a steer is claimed, atomically move that message to the next turn. A status reply must use actual run events, and stop must preserve cancellation and uncertain external-effect state.
- **Durability and fairness.** Use one writer/revisioned transition for `accepted/pending-routing → next-step | next-turn | control | awaiting-clarification → claimed → committed/cancelled`; pending-routing and awaiting-clarification messages cannot be claimed by either task lane. Deduplicate provider/channel retries by ingress ID. Reclassifying a pending message must not create a second task. If the control model returns after the active run ends, revise against current state and queue it instead of falsely acknowledging a steer. Recover accepted-but-unclaimed messages after restart without replaying uncertain tool effects. Human next-turn input takes precedence over automatic continuation at a bounded work-slice boundary, so a long-running objective cannot starve the queue. This protocol must compose with the existing session/source-event store; a new storage engine requires its own review rather than being assumed by this plan.
- **Delivery and authority.** Preserve each message's originating route even when all authenticated channels share the assistant session. Recommended default: the active task's full outcome stays on its original route, a cross-channel steer gets a receipt and completion notice on its own route, and a queued task's result goes to the route that submitted it; avoid duplicate full deliveries. Do not let an injected message widen the active run's tool/workspace authorization. If requested work needs different authority or an independent approval, keep it for a separate turn.

**H1 implementation sequence:** first freeze conversational examples, IM reply-timing requirements and the inbox/authorization/delivery contract. Prototype the bounded control-model request separately from the active task's provider conversation, with explicit concurrency, timeout, rate-limit, cost and status-snapshot limits; verify the neutral-receipt fallback. Then add durable admission and idempotent transitions; integrate safe-step injection, stop, status and bounded fairness with the one canonical runner; finally adapt Telegram and each enabled IM channel's receipts and replies. Shadow routing on synthetic conversations before enabling model-driven decisions; qualify a single-consumer canary with rollback/export of new inbox state. Preserve all P1–P7 fork compatibility tests and do not enable unrelated upstream goals, Dream, GUI listeners or background agents.

IM timing to validate: authenticated message → durable pending-routing record → neutral receipt if classification is slow → concurrent bounded control inference → one validated route commit → informed channel reply → active agent consumes the full text at the next safe step **only if steered**. The control call must use a separate stateless provider conversation so it cannot corrupt the active task's provider state.

**H1 exit tests:** while the active provider request or side-effecting tool is blocked, admit a Telegram message, send a timely neutral or informed receipt, run control inference independently, and later inject a steer without duplicate task execution. Also test queue through a bounded continuation boundary; stop with an uncertain external result; status grounded in actual events; ambiguous/quoted control language; concurrent and out-of-order routing results; route-change versus turn-completion races; crash before/after persistence, receipt, claim and history commit; provider/routing failure; duplicate webhook delivery and failed channel acknowledgment; cross-channel owner authorization, per-message capability and exact reply destinations. Verify that a steered message reaches the active model with its full content once, a queued message does not, and every accepted message is eventually either completed or visibly pending. Measure routing accuracy on held-out conversational examples, receipt and informed-reply latency, auxiliary cost, task completion and duplicate side effects before calling H1 equivalent in experience.

Pattern references, not drop-in implementations: [official OpenAI Docs on Codex Queue/Steer](https://developers.openai.com/blog/mastering-codex-remote-for-engineering), [DeepSeek's pinned inbox lanes](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/inbox.ts), and [later upstream nanobot's session queue and mid-turn drain](https://github.com/HKUDS/nanobot/blob/9756468a8cb475dbf685f64837c0e0ecdac9ad10/nanobot/agent/loop.py). The accepted IM control-model response is our adaptation to conversational channels, not a feature established by those references. They do not change the frozen migration target in section 1.
