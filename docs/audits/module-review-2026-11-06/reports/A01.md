## Architecture judgement and preserved strengths

**Provisional Keep + Simplify.** Keep the conservative automation durability spine: process-completion state is journaled before/after owned effects; cron scheduling converges timer/manual/system work on one occurrence ledger; computation uses non-serializable execution fences; delivery uses immutable outbox state, task-bound send fences and explicit uncertain-outcome reconciliation; interruption recovery refuses to infer completed work; sustained-goal state is durable and bounded when its tools are actually registered. Simplify the ownership mismatches around that spine rather than adding parallel frameworks: move blocking persistence off shared asyncio owners, add explicit evidence epoch/retention policy, scope model-facing cron management, bound terminal delivery-runtime caches, align shipped commands with activated capabilities, and require durable/idempotent local-trigger settlement plus trusted-user provenance for approval.

## Responsibility and actual ownership

| Responsibility | Actual owner / activation | Important boundary |
| --- | --- | --- |
| Process continuation | `ProcessCompletionRuntime` installed by gateway when `gateway.process_continuations` is enabled | Durable state before launch/continuation; interrupted dispatch becomes unknown rather than replayed. |
| Sustained goals | Session goal metadata + bounded continuation policy | Goal mutation is permissioned and durable, but default tool composition omits the create/update goal tools. |
| Scheduled cron execution | `GatewayCron` + `CronRuntime` + scheduler/occurrence stores | Opt-in gateway owner, held scheduler lease, immutable occurrence snapshot, task/PID-bound execution fence. |
| Cron result and delivery | Canonical composition + completion projector + delivery outbox/runtime | Silent fresh execution, receipt-capable transport, durable uncertain outcomes and operator reconciliation. |
| Cron management | `CronTool` + `CronService` + action/definition stores | Typed CAS mutations and durable receipts, but model-facing list/remove are instance-global. |
| Local triggers | `LocalTriggerStore` + optional `run_local_trigger_queue` + automation coordinator | Queue substrate exists, but default foreground gateway intentionally does not own/start the consumer. |

### Finding qualifications

- **A01-F04** was initially provisional pending later management/migration review. A01-E read those surfaces fully and found no scheduler-history compaction, archive or epoch-rollover owner, so the finding is promoted without that earlier qualification.
- **A01-F06** is conditional on multiple mutually untrusted chats/users sharing one agent/service. A strictly single-owner personal agent can intentionally define one administration domain.
- **A01-F08** and **A01-F09** are activation blockers rather than default-gateway exploits because the shipped foreground gateway currently leaves the local-trigger runner inactive.
- **A01-F01/A01-F03** do not argue for weaker durability. They identify blocking persistence ownership on shared async paths.
- **A01-F05** is process-memory/lifetime growth, not duplicate-send authority; the durable outbox already consumes the underlying claim.

## Cross-cutting simplification direction

The review does not support replacing the cron/automation architecture. The smallest coherent direction is to keep the current durable state machines and consolidate ownership around them. One ordered persistence owner can serve process-completion and cron durability without weakening pre-effect fsync guarantees. Scheduler/action/definition evidence needs an explicit epoch/archive contract instead of independently accumulating bounded append-only histories. Cron management should use one clear creator/admin scope. Delivery-runtime terminal state should be bounded. Goal and local-trigger surfaces should only be advertised when the corresponding runtime capability is active. If local triggers are activated, they should reuse the same conservative pattern already present in canonical cron: durable occurrence/delivery identity, explicit unknown outcomes and approval authority that automation cannot mint.

## Retained observations, not promoted

1. Cron's POSIX descriptor/flock requirements fail closed on unsupported platforms when scheduled execution is enabled. This is a compatibility/product-scope constraint, not a correctness finding.
2. Several canonical delivery/composition modules still describe themselves as dormant even though the pinned gateway uses them, while older session-bound/message-fanout helpers remain alongside the canonical occurrence/outbox path. This is retirement/documentation debt.
3. Delivery destinations intentionally cap attempts/history and the offline reconciliation artifact plane caps evidence/plans/applications. Those explicit operator limits are distinct from A01-F04's live timer exhaustion.
4. The management plane separately caps durable action receipts and scheduling commits at 4,096 and has no matching cron export owner. This is a maintenance horizon that should be resolved with the same final retention/epoch policy, but it is mutation-driven rather than the live-timer failure in F04.
5. `CronDefinitionStore` retry caches retain historical full candidate wires until process restart. Their growth is indirectly bounded by the durable evidence ceilings, so this stays a simplification/lifetime observation rather than another memory finding.
6. `CronTool.every_seconds` accepts negative integers at the schema surface and lets typed-definition validation raise later instead of returning a normal tool diagnostic. This is validation polish.
7. Local-trigger storage is compatibility-grade pathname/FileLock JSON storage rather than the descriptor-pinned/private-mode discipline used by hardened cron stores. If triggers become a first-class gateway feature, storage authority and terminal failure observability should be raised to the same standard.

## Final discussion questions

1. **A01-Q1 / D5,D6:** Should process-completion, cron and future trigger durability share one ordered asynchronous persistence-owner pattern while retaining current pre-effect fsync semantics?
2. **A01-Q2 / D5,D6,P01:** What explicit epoch/archive policy should retire scheduler classifications, trigger requests, action receipts, scheduling commits and offline reconciliation evidence without weakening replay/authority proofs?
3. **A01-Q3 / D2,D4:** Is model-facing cron management intentionally instance-global, or should creator/session scope be the default with a separate administrator capability for global list/remove?
4. **A01-Q4 / D4,P01:** Should `/goal` and local-trigger commands be activated as supported first-party features, or hidden until their required tools/runtime owners are present?
5. **A01-Q5 / D5,D6:** Before local triggers are activated, should each delivery acquire a durable canonical run/settlement identity with explicit committed/unknown/retryable states rather than filesystem at-least-once recovery?
6. **A01-Q6 / D2,D4:** Should risky-action approval consumption be restricted to trusted foreground user ingress, making all cron/trigger/recovery/background automation incapable of affirmative/negative approval settlement?
7. **A01-Q7 / P01,D6:** Which legacy session-bound cron helpers, stale “dormant” comments and historical retry caches should be retired once the canonical occurrence/outbox path is the only supported owner?
