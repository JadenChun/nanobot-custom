## Architecture judgement and preserved strengths

**Provisional Keep + Simplify.** Keep the explicit core tool manifest, foreground-manager ownership graph, delegated role capability profiles, current workspace/resource-policy enforcement for filesystem mutations, session-scoped file state, artifact provenance/grant model, MCP owner-task transport lifecycle, OAuth generation/lease discipline, managed-WebUI host-capability restrictions and bounded session-history/session-message surfaces. Simplify the remaining authority and lifetime mismatches instead of adding parallel frameworks: make delegated MCP classification depend on trusted capability policy rather than remote hints, make MCP readiness/publication transactional, reuse one real descendant owner for generic subprocess adapters, bring optional desktop/browser/device authority under the same approval/path owners, and align advertised capabilities with the explicit manifest.

## Smaller alternatives and simplification

The review does not support a broad tool-system rewrite. The smallest coherent simplification is to tighten existing owners: keep one explicit core capability manifest and make instructions conditional on that manifest; replace the foreground MCP boolean “connecting” flag with a shared readiness future; publish one MCP server's wrappers transactionally after readiness; reuse the stronger existing process-range owner; route browser/device/desktop mutation through existing workspace and approval owners; and retain the canonical image-generation tool while retiring or hardening the dormant legacy writer.

## Retained observations, not promoted

1. The old `agent/tools/image.py` compatibility writer returns absolute output paths outside the workspace unchanged. Current explicit core composition registers `agent/tools/image_generation.ImageGenerationTool`, whose output path uses the canonical writer/artifact path. Treat this as retirement/hardening work unless the legacy class is reactivated.
2. Writable `MyTool` accepts any string for `provider_retry_mode` although config constrains it to `standard|persistent`. Current provider logic treats every non-`persistent` value as standard retry, so the observed effect is configuration/diagnostic drift rather than a crash or privilege expansion.
