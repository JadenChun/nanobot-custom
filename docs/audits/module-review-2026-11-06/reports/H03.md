## Architecture judgement and preserved strengths

**Provisional Keep + Simplify.** Keep provider-specific adapters where wire/auth semantics genuinely
differ, immutable per-turn runtime/route facts, typed request budgets, bound conversation-state
receipts and the existing retry/no-replay fences. Simplify around explicit terminal ownership,
credential-publication generations, route-attempt identity and one unambiguous accounting
boundary. The evidence does **not** justify a generic provider framework or collapsing provider
state/auth into the agent loop.

Important strengths to preserve include exact bound provider-state replay, request-budget validation
at the finalized transport body, live route verification, typed error/retry metadata, fallback
window repricing in the current staging delta, and observer propagation across ordinary outer retry
and fallback leaves.

### Important limits on those findings

F1 is not a claim that the retry layer replays output after deltas; `base.py` explicitly guards that.
F2 is rejected by a later login/logout generation, so the race is bounded to cancellation/expiry
without supersession. F3 claims redundant model request/cost/latency, not duplicate tool effects.
F4 has no demonstrated deployed cross-account incident. F5 does not claim every retry is hidden or
that token billing totals are universally wrong. F6 is narrowed because MyTool blocks direct
model/window writes during an active session and presets resolve fresh snapshots. F7 does not claim
same-process logout resurrection; WebUI clears registered flows before logout.

## Reference mechanisms and history

Pinned DSH `llm-pi-ai/src/stream.ts` ends only on `done/error` and throws `STREAM_CLOSED`
at EOF; pinned Codex `codex-api/src/sse/responses.rs` emits
`ApiError::Stream("stream closed before response.completed")` when the SSE closes without the
terminal event. These support H03-F1's outcome, not architectural parity. DSH login passes its
authorization-session cancellation signal into provider login, a useful bounded custody contrast
for F2/F7. Codex client setup is turn/session scoped but does not imply Nanobot should copy its
provider architecture.

History also matters. `b89abf1...` introduced prepared route facts specifically to describe the
leaf dispatch will use; `13d1469...` added `ProviderRouteChanged` and one reprepare. H03-F3 is
therefore an interaction between two intended safeguards, not an argument to remove route
verification. `cb71b864...` made model capabilities immutable and route-owned; direct setters
that preserve an old capability snapshot are inconsistent with that newer ownership model.
Current staging `9562e57...` correctly reprices fallback total/model-window limits to the fallback
context window; that repair is retained and is distinct from F3.

## Final discussion questions retained

1. **H03-Q1 / D6,D7:** Is an explicit provider terminal event mandatory before any streamed
   model/tool result becomes successful, and what is the retry rule after visible deltas?
2. **H03-Q2 / D2,D4,D6:** What common credential-intent/cancellation generation contract should
   Codex, xAI and future OAuth flows share?
3. **H03-Q3 / D5,D6,D7:** After a prepared primary is consumed and fails, what identity lets
   reprepare resume at the next fallback without replaying the primary?
4. **H03-Q4 / D7:** Is `LLMCallRecord` a logical model call or a physical transport attempt, and
   which request/error/latency metrics are public promises?
5. **H03-Q5 / D2,D4:** Are ambient process-global provider credentials allowed by a documented
   one-account-per-process contract, or must provider instances own explicit credentials?
6. **H03-Q6 / D4,D7:** Are direct default model/context-window setters supported compatibility, and
   which route-owned capability/policy snapshots must they recapture?
7. **H03-Q7 / D4,P01:** Which provider/fallback construction and dormant compatibility helpers can
   be cached, combined or retired without freezing live auth/revocation state?
