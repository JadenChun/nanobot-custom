## Provisional architecture judgement

**Keep + targeted simplification.** Preserve one canonical ingress/store, explicit upload binding, small channel compatibility, content-addressed records, document-on-demand, audio adapter registry, image-generation provenance, and the distinct lifetime of user attachments versus generated image artifacts. Do not consolidate all media under one generic lifecycle abstraction: signed WebUI assets, session references, externally acquired channel files, generated artifacts and temporary transcription files have distinct owners and retention contracts.

Prefer small, boundary-specific fixes over a new attachment manager framework: make pruning fail closed when reference evidence is incomplete; ensure migration planning is genuinely non-mutating; reclaim blob/sidecar metadata together; bound image-edit reference reads and PDF decoded streams before allocation; and decide whether audio duration is enforceable server policy or advisory client UX. Handle full-batch rollback/receipts only if product requirements demand atomicity across admission and transcript persistence; current manual, grace-based cleanup provides an eventual orphan-removal path, but cannot be treated as guaranteed safe under unreadable session files or concurrently pending upload-first records.

## Findings with triggers, consequences and smallest alternatives

**M01-F01 — P2 — Migration `--dry-run` writes canonical attachment blobs and sidecars (confirmed source behavior).** `nanobot/cli/commands.py:attachments_migrate` always calls `migrate_legacy_media(..., dry_run=True)` for preview, including before prompting for confirmation. In `nanobot/attachments/lifecycle.py:_migrate_event`, each qualifying legacy user event enters `AttachmentIngress.accept_path` and `commit_batch`; `AttachmentStore.stage_path/commit/_write_sidecar` create directories, blob files and metadata. The outer `if not dry_run` only guards the backup/transcript rewrite, not these writes. On a legacy media event with accessible files, even an aborted or no-confirmation CLI preview can change storage, and multiple passes can create additional logical records/sidecar rewrites. Existing dry-run test checks transcript immutability, not store immutability. Repair by a pure planning/preflight pass that checks accessibility/MIME/size without writing, or isolate staging in a throwaway scratch space and discard it before any dry-run return. Preserve backups and source event pin. No runtime execution used to reproduce.

**M01-F02 — P2 (retention/hygiene) — Unreferenced blob prune leaves its matching metadata sidecar (confirmed source behavior).** `AttachmentStore._write_sidecar` creates `<sha>.json` next to `<sha>.<ext>`. `lifecycle.py:prune_unreferenced` explicitly skips `.json`, unlinks eligible unreferenced blobs and then attempts `rmdir()` only for empty directories. Thus a pruned hash retains stale metadata, and the prefix directory remains. Its consequence is persistent stale metadata/storage accumulation rather than immediate data exposure. The existing prune test asserts only blob removal. Repair by collecting and removing matching sidecars after successful blob removal, with checks for unusual multiple extension variants per hash and shared bytes. If metadata retention is intentionally required, document its owner and add an explicit cleanup policy.

**M01-F03 — P2, conditional on max-duration being an enforced provider-cost policy — WebUI audio duration limit is caller-asserted only.** `transcription_ws.py:webui_transcription_event` passes `envelope.get("duration_ms")` to `audio/transcription.py:transcribe_audio_data_url`. The latter rejects only when `duration_ms` is numeric and exceeds `config.max_duration_sec * 1000 + 1000`; absent, zero or falsely low values pass. `save_base64_data_url` checks decoded bytes but no actual container duration, then forwards the file to the provider. A longer-duration compressed recording within the configured byte limit can bypass the declared duration check; the provider may reject, process or charge according to its own limits. This is **not** an unlimited byte upload, and no measured charge or runtime bypass is asserted. If duration is an authoritative server-side cap, inspect media duration before provider dispatch with bounded parsing or label the field advisory and rely on per-byte/provider limits; carry the policy choice to D6/D7.


**M01-F04 — P2 (conditional destructive maintenance/data loss) — Prune treats incomplete session evidence as zero references.** `nanobot/attachments/lifecycle.py:referenced_hashes:44–64` silently ignores `OSError` from opening a session JSONL file and skips invalid JSON lines; `prune_unreferenced:78–99` accepts an empty `sessions_dir.rglob("*.jsonl")` as valid evidence and offers all old, otherwise unreferenced blob paths for deletion. `nanobot/cli/commands.py:attachments_prune:207–254` uses this result for both preview and destructive run, with a count-only confirmation unless the operator chooses `--dry-run`. Trigger: wrong/missing session directory, unreadable session file, or damaged JSONL containing real attachment references, followed by explicit prune confirmation (or `--yes`). It may delete old blobs still needed by active/persisted conversations. This is **not** an automatic background deletion nor a proven deployed incident; it is a missing fail-closed invariant in an opt-in destructive command. Smallest repair: require an existing/verified sessions root and complete readable reference scan; abort, report uncertain files and require a separate explicit recovery mode if incomplete. Keep a dry-run list and clarify other owners (pending upload registry, alternate session roots) before commit. Related H02/E02 session durability obligations.

**M01-F05 — P2 (conditional memory/resource exhaustion) — Image generation reads arbitrary-size local reference images into memory before provider dispatch.** `nanobot/agent/tools/image_generation.py:67–89` declares `reference_images` as an array with no count constraint; `_resolve_reference_image:192–215` resolves paths through the scoped write-tool read authority (a positive security boundary), then calls `resolved.read_bytes()` with no size check to inspect the image signature. `execute:233–247` repeats this for every reference before model invocation. In the common image-provider implementations `nanobot/providers/image_generation.py:_read_image_b64:97–116`, `_post_image_edit:1169–1180`, the same files may be loaded again and base64-encoded, compounding peak memory. Trigger: enabled image generation, an authorized but very large image file or excessive reference list selected by the agent/tool caller. This is not a path-authority bypass, and the tool is disabled by default. Smallest repair: stat/open bounded header reads, enforce a clear per-reference and aggregate encoded-byte/count policy prior to provider dispatch, and avoid redundant full reads where possible. Relate to T01/H03 and D5/D7.

**M01-F06 — P2 (conditional parser resource-limit bypass) — PDF stream size limit is checked after full stream decoding.** Both `nanobot/utils/document.py:_open_pdf_line_source:191–207` and `extract_pdf_pages:468–477` compute `len(contents.get_data())` and *then* check whether it exceeds `_MAX_PDF_CONTENT_STREAM_SIZE` (32 MiB). For a highly compressed page stream, the full decompressed content may be materialized by `pypdf` before the application enforces its advertised page content budget. The 50 MiB input-file size and 100-page window do not bound a compressed stream's expansion. Trigger requires a hostile/pathological PDF presented to the document reader and a `pypdf` path which materializes the decompressed body; the installed parser's internal protections were not independently established, and no runtime memory failure is asserted. Smallest repair: enforce decoder-level expansion/output limits or a bounded parser path before materializing the content stream; add a focused compressed-stream regression, distinct from the current mocked post-decode size test. Coordinate with S01/T01 document read authority and D5/D7.

## Unpromoted observations and challenge results

- **O1:** `AttachmentIngress.commit_batch` returns previously committed records plus a failure after a later `OSError`; WebUI callers reject the request and eventual grace-based orphan collection owns leftovers. No requirement for an atomic multi-file transaction was established, so this is not a separate accepted bug.
- **O2:** `accept_batch` trusts declared MIME and checks bytes after base64 decode. Browser frame/request limits and the provider's later image decoding limit this in the main route; a malformed client-declared image can fail later, but a privileged escalation was not established. DSH verifies image media bytes and makes request budgets explicit; consider a local image-magic check if operator reliability requires it.
- **O3:** Records with absolute legacy `storage_key` can resolve outside the media root; these arise in deliberate SDK/test/workspace compatibility, while trusted file-tool grants apply at actual reads. Treat compatibility closure as a D2/D4 decision, not a blanket attachment traversal defect.
- **O4:** Now separated into **M01-F05** for the demonstrable unbounded `generate_image.reference_images` file-read path. The distinct `AttachmentContext` model-input projection also reads resolved images whole; ordinary WebUI ingress is bounded, while SDK/channel/external paths may differ. No measured OOM threshold; model-bound budgeting remains a H03/E02 coordination item.
- **O5:** DOCX/PPTX load parser documents after ZIP preflight even in the line-source API; XLSX uses read-only iteration. The PDF decoded-content check is after expansion, newly separated into **M01-F06**. No blanket parser insecurity or measured resource exhaustion is asserted.
- **O6:** The image-generation tool may create some persistent artifacts before a later provider/write failure; returning retained artifacts is intentional, and deleting successful artifacts automatically would violate the persistent-artifact contract.
- **O7:** Unbound upload IDs are process-local/TTL-based; a restart invalidates the binding while durable blobs remain available for later manual GC. This is a deliberate retry policy, not an asserted missing transaction.
- **O8:** `AttachmentStore.stage_bytes:94–112` has no exception cleanup around the temporary file write; unlike `stage_path:142–161`, an `OSError` after partial write can leave a stray `.staging` file. Conditional to storage failures; no direct evidence of repeated failures or a strong enough consequence to promote separately at this point.
- **O9:** `AttachmentStore.commit:177–179` reuses an existing content-addressed blob without refreshing blob mtime; `prune_unreferenced:88–99` uses that mtime, while a newly uploaded but unbound matching blob is absent from session JSONL. A rare explicit concurrent prune could therefore delete a reuploaded pending blob after the older mtime crosses grace. Keep for retention contract reconciliation, not a separately promoted defect without concurrency/activation evidence.
- **O10:** `UploadRegistry.bind:59–85` can pin session-neutral IDs before all the later WebUI scope/admission checks finish (`inbound_commands.py:973–1090`). A rejected cross-chat attempt may consume reusability despite no accepted turn. No cross-installation access is established; this is a conditional UX/lifecycle follow-up, not a security finding.
