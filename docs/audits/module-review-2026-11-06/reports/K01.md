## Architecture judgement and preserved strengths

**Provisional Keep + Simplify.** Keep the bounded repository catalog/discovery model, explicit context-repository manifests, canonical knowledge writer publication path, prompt budgeting before provider dispatch, progressive skill disclosure, managed-WebUI prompt validation, configured provider/runtime ownership, and bounded Dream/evaluator prompt overrides. Simplify the remaining seams by making every prompt/skill read use one resource-policy owner, making runtime skill validation match the shipped authoring contract, deriving prompt guidance from actually registered capabilities, routing auxiliary semantic work through the configured provider, and placing every Dream mutation inside the same audit/restore transaction.

## Responsibility and actual ownership

| Responsibility | Actual owner / activation | Important boundary |
| --- | --- | --- |
| Main prompt composition | `ContextBuilder` | Identity/bootstrap/context repos/catalog/tool contract/memory/skills/archive are concatenated into one system message; managed-mode validation is stronger than several auxiliary/non-managed reads. |
| Context repositories and catalog | `ContextRepoManager` + repository catalog | Catalog metadata does not itself grant filesystem access; manifests define context/skill entrypoints and repository policy. |
| Durable project knowledge | `SaveKnowledgeTool` | Canonical destination confinement/secret scanning/writer publication are strong, but project-to-knowledge association is not enforced. |

| Operational skills | Bundled `SKILL.md` bodies over core tools/external CLIs | Several instructions drift from current runtime/tool ownership, including cron, ClawHub, mobile/browser and nested Codex launch guidance. |
| Video semantic extraction | `video-understanding/scripts/extract_keyframes.py` | Local frame selection/OCR is bounded; default semantic mode may bypass Nanobot provider routing and contact OpenAI directly. |
| Session archive/compaction | `MemoryArchiver` + `ContextBuilder` | Normal summaries are compacted; degraded raw checkpoints can later be inserted into the system prompt. |
| Dream memory/skill mutation | `MemoryStore` Dream tool factory + GitStore | Dream may edit workspace skills, while Dream diff/log/restore owns only SOUL/USER/MEMORY plus cursor bookkeeping. |

## Smaller alternatives and simplification

The evidence does not support replacing the context/skill subsystem wholesale. The smallest coherent simplification is to reuse owners that already exist: one resource-policy path resolver for every instruction source, one skill metadata validator for authoring/package/runtime, one effective agent-workspace locator for bundled skills, one capability-derived prompt description, one configured provider route for auxiliary model calls, and one Dream mutation ledger. These changes reduce parallel contracts rather than adding new frameworks.

## Retained observations, not promoted

1. The default MEMORY/USER templates have some category overlap: memory invites user preferences while Dream routes user facts/preferences to USER, and USER mentions projects while Dream routes project context to MEMORY. This is usability/ownership cleanup, not a separate defect.
2. The old background `SubagentManager` templates have skill/prompt quirks, but T01 established that this path is retirement scaffolding because current `ToolLoader` rejects its `scope="subagent"` request.
3. `goal_runtime.md` is coherent guidance around `create_goal`/`update_goal`, but the current live prompt does not render it and A01-F02 owns the default production registration gap.
4. The generic untrusted-content snippet explicitly names web search/fetch. Broader browser/device/MCP/plugin result provenance remains a design question; K01-F12 is the concrete promoted authority-crossing path.
5. Workspace Dream/evaluator prompt overrides intentionally replace their built-in instruction bodies. K01-F01 concerns path confinement, not the authorized user's ability to customize prompt semantics.
6. `TOOLS.md` destructive-shell examples align with the reviewed ExecTool deny patterns; no documentation finding is promoted there.
7. The exact legacy default SOUL body is detected and substituted with the current bundled SOUL, avoiding its old wait-for-confirmation behavior. Modified legacy SOUL remains intentional user customization.
