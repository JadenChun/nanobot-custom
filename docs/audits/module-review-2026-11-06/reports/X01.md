## Promoted findings (source-based, conditional impact where noted)

### X01-F01 — P1 conditional — CLI app execution does not actually enforce restricted workspace/file capabilities

**Requirement:** when a turn is workspace-restricted, executable tools must not gain broader file/network authority solely by changing tool family.

**Source and call chain:** `nanobot/agent/tools/cli_apps.py:136–160` calls `current_tool_workspace` and passes `restrict_to_workspace` into `CliAppManager.run`. `nanobot/apps/cli/service.py:_resolve_cwd:1337–1348` checks only the **working directory**. `run:1431–1487` passes arbitrary model-selected CLI arguments to `subprocess.run([resolved,*clean_args], cwd=..., env=_subprocess_env(), ...)` without subprocess sandbox or per-path authorization. `_subprocess_env:993–1020` deliberately filters environment variables but cannot confine the child process's filesystem/network rights. `nanobot/config/schema.py:895` describes restrict mode as policy intent; `workspace_access.py:220–240` acknowledges application-level mode is **not** OS-enforced. By contrast `ExecTool` is wired to managed resource policy/native admission in `agent/tools/shell.py:249–266,539–575`.

**Trigger/impact/confidence:** enabled `run_cli_app` (enabled by default), previously installed CLI that accepts file-path or network arguments, an active restricted workspace scope, and no independent OS confinement of the agent host process. A selected app may read/write outside that workspace or use network endpoints with the host user's rights despite the cwd check. This is a **source-confirmed enforcement gap**, not evidence that a particular CLI was misused, that sandboxing is absent in every deployment, or that every app exposes a bypass. P1 is **conditional** on the intended restricted-scope protection being relied on. Minimal alternative: route every CLI app subprocess through the same managed process/sandbox authority and permission reservation as generic execution, or disable `run_cli_app` in restricted/managed turns until such enforcement exists. Checking argv strings alone is insufficient for arbitrary external CLIs. Defer the precise process owner to S01/S02/T01/Q01/D2/D4.

### X01-F02 — P1 conditional — crawler `expand` is classified read-only while clicking the page

**Requirement:** a delegated read-only research role, especially with an authenticated browser profile, must never perform unapproved page mutations.

**Source and call chain:** `nanobot/agent/tools/social_crawl.py:45–71,272–377` includes `expand` in `CRAWLER_READ_NAVIGATION_ACTIONS`, exposed to the crawler tool as a permitted action; `nanobot/extensions/crawler.py:74–104` says clicking and account actions are disabled. `nanobot/crawler/worker.py:623–631` rejects explicit `click` but `dispatch:788–796` creates JavaScript for `expand` that executes `element.click()` when the selected element matches **`details`, `summary`, or `[aria-expanded="false"]`**. The latter may be an arbitrary page-provided control whose click handlers mutate remote account state; the worker does not verify that its effect is only disclosure. `tests/tools/test_social_crawl.py:21–32,248–298,359–381` tests explicit click rejection but not the `expand` DOM event path.

**Trigger/impact/confidence:** crawler enabled (off by default), tool/model invokes `expand` against a site using an expandable or `aria-expanded` control with stateful click handlers; risk increases with an operator-prepared authenticated browser profile. A remote mutation can occur while action audit/classification says `read_navigation`. This is a **confirmed literal DOM click**, but the mutation consequence is page-dependent; no real account change or browser execution was demonstrated. P1 is conditional on the read-only authenticated-profile promise. Smallest fix: remove DOM click from `expand` and expose only non-event inspection, or restrict supported expansion to a verified non-click DOM mutation (e.g. `details.open`) that cannot invoke page event handlers; if app-specific toggles need clicking, classify and gate them as state-changing rather than smuggling them into the read-only role. Cross E02/T01/D2/D4/D7.

### X01-F03 — P2 — CLI command output is only truncated after unlimited capture

**Requirement:** running installed third-party CLI tools should not allow unbounded process-output buffering to overwhelm the host/agent while the displayed output is nominally capped.

**Source/call chain:** `CliAppManager.run:1453–1487` and `_run_argv:1022–1038` call `subprocess.run(capture_output=True, text=True)`. Only after child completion are stderr/stdout appended to output and truncated with `_truncate` to 12,000 characters for model display (or 4,000 chars in logging). The installed app can produce a high volume of stdout/stderr during a permitted run of up to 600 seconds.

**Impact/limit:** unbounded host memory use prior to truncation and possible blocking of the synchronous run caller. No measured memory threshold, OOM, or actual noisy CLI incident. Existing tests assert argv/text and final output shape, not peak buffering. Small alternative: bounded streaming stdout/stderr reader with a fixed per-stream/total byte ceiling, deadline and owned process-tree cancellation, preserving exit status and truncated tail/hints. Coordinate with T01-F09 and Q01 process policy, not a new general subprocess framework.

### X01-F04 — P2 conditional — optional extension catalog can overwrite higher-trust app install metadata while retaining a higher-trust label

**Requirement:** remote catalog provenance and executable install/update fields must not silently change trust source when entries from distinct registries share an app name.

**Source/call chain:** `CliAppManager.catalog:544–594` reads harness, public then optional `extensions` registries; entries are keyed only by lower-case name. On collision, `apps_by_name[key] = {**previous, **entry, "_source": merged_source}` gives the *later* registry authority over install strategy, command, package and entrypoint. `_manifest_source:603–608` exposes a combined value, but `_trust_registry:609–610` returns `cli-anything` for every combined source other than exactly `extensions`, even if the winning executable metadata came from `nanobot-extension`. The installer `get_app/install/update:612–618,1176–1251` then uses the merged latest record. Tests cover benign duplicate description merges and a distinct extension app (`tests/cli_apps/test_service.py:233–304`), not a cross-registry collision that changes installer fields.

**Trigger/impact/confidence:** an optional extension registry publishes the same normalized name as an official app (whether accidentally or maliciously), and user selects its install/update action. The UI can misleadingly show a `cli-anything` trust registry while package-manager arguments reflect the optional extension record. The source merging and labeling behavior are direct; **actual collision, compromise and malicious package execution were not established**. Minimal alternative: prohibit cross-origin overwrites of executable/provenance fields, require source-qualified IDs or explicit provenance conflict resolution, and display the source that supplied the chosen install command. Supply-chain trust scope belongs in Q01/D2/D7.

## Additional investigated leads (not promoted)

- **O1 / crawler DNS:** top navigation and selected links are checked with `_validate_public_dns`; browser's `context.route("**/*")` only validates host suffix and IP literal, without DNS-to-IP revalidation for resource requests or browser-time DNS pinning. An allowlisted hostname with a changed/private DNS result could bypass the intended public-only host boundary in some deployments, but actual browser DNS/socket timing, TLS behavior and a controlled allowlisted domain were not tested. Coordinate with S01 networking/Q01 deployment; do not assert a demonstrated SSRF.
- **O2 / worker local access:** Unix socket is private/group-owned when deployed via systemd. Optional loopback TCP has no separate request token; other processes on the same device may attempt reset/inspect if they can connect. Local trust model and profile-mode deployment assumptions remain unknown, particularly for Windows; no external unauthenticated exposure is implied.
- **O3 / optional feature config writes:** `write_config_data:283–295` directly truncates/writes channel JSON without atomic rename or a file lock. Concurrency with other config writers could lose changes or leave a partial document, but actual writer serialization, transaction ownership, and gateway reload responsibilities require E02/H02 reconciliation before promoting.
- **O4 / install state partial success:** `_record_installed:1165–1175` saves `installed.json` before `install_skill` and plugin enable. If filesystem writes or skill parsing fail, package/installed state may be ahead of the managed plugin. No recovery test/source failure rate established; the separation is worth preserving while making install receipts/retry states explicit if required.
- **O5 / mutable package supply chain:** pip/npm/brew/uv install/update are intentionally explicit operator actions with restricted argv and controlled environments; a fixed registry URL is not a package signature or version pin. Avoid declaring a generic injection vulnerability where registry trust and user consent already authorize package installation; Q01 should decide pinning/trust level.
- **O6 / runtime/local cache:** normal catalog failure falls back to stale cache when available, while `run/get_app` still relies on catalog discovery even for an installed app. State or catalog corruption could impede offline execution, but not a blanket offline failure. No removal recommendation without installed-only compatibility review.
- **O7 / browser lifetime and all-op isolation:** worker serializes actions via `_operation_lock`; per-host delegation serializes crawler via `_crawler_gate`; worker `reset` and single-session semantics are global, so separate gateway processes can interfere if configured to share worker. No known supported multi-gateway topology was established.
- **O8 / response and registry buffering:** registry HTTP fetch and screenshot payload decode are fully materialized before some size policies; requests have timeouts and screenshot output is bounded, but provider/HTTP response content cap isn't obvious in primary source. Record as bounded robustness question, not an exploit claim.

## Comparison to pinned DSH and Codex mechanisms

**DSH** `packages/sandbox/sandbox-policy/src/index.ts:1–95,189–217`: a single per-call sandbox policy resolves from session/deployment state, with enforcing filesystem, shell and terminal backends consuming it independently. Nanobot already has per-turn `current_tool_workspace` and a managed native admission path for shell; X01-F01 is a **missing integration of an existing authority**, not proof that DSH's abstraction should be copied.

**Codex** `codex-rs/core/src/tools/handlers/unified_exec/preparation.rs:1–120,128–200`: command preparation carries environment, cwd, sandbox permissions and approval requirement before spawn. `unified_exec/exec_command.rs:1–95` retains explicit tool lifetime/executor ownership. This contrasts with X01's raw synchronous subprocess runner under a cwd-only guard. The smallest viable change is to delegate to Nanobot's own process admission rather than reimplement a second policy.

Neither reference implementation supplies a directly comparable Crawl4AI browser DOM or three-origin CLI-Anything registry merger at these pins. The browser-state and provenance findings rest on Nanobot's own code and obligations, not parity with outside products. No Hermes study or new architectural baseline was introduced.

## Final cross-module discussion questions

1. **X01-Q1 / D2,D4:** Can model-facing `run_cli_app` remain available in restricted/managed turns without using the same sandbox/native-process authority as shell?
2. **X01-Q2 / D2,D4,D7:** Must crawler `expand` become pure inspection, or should state-changing expand actions require explicit operator approval and a different role/policy?
3. **X01-Q3 / D2,D7/Q01:** Should registry collisions be forbidden or represented by source-qualified identities and explicit trust provenance, including pinned package versions?
4. **X01-Q4 / D5,D6:** Which subprocess owner should bound output bytes and descendant/process-tree lifetime for CLI Apps and optional installers?
5. **X01-Q5 / D2,D4:** What network policy, DNS pinning, socket authentication, and browser-profile isolation are required for authenticated/local crawler deployments?
6. **X01-Q6 / D6,D7:** Should optional-feature/CLI app installation state use a transactional receipt and atomic configuration update, or do current retry semantics suffice?

The later **Q01** module owns packaging, dependency/install/build/CI deployment policy and can refine F04/O2–O5 without erasing X01 source facts. **S01/S02** own managed sandbox/process boundaries, **T01** core tool registration and process lifecycle, **E02** WebUI permission/transport requests; **E01** remains a deliberate limited-depth exception. **P01** cross-cutting simplification, K01 current-origin refresh, module integration and D1–D7 decisions remain pending.
