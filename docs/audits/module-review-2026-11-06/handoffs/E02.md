## E02-A behavior established

- The HTTP surface is intentionally a **minimal** OpenAI-compatible adapter, not full protocol
  parity. The pinned README explicitly documents exactly one user message per request, a fixed
  configured model and no streaming. The live server enforces those limits and rejects remote
  image URLs.
- API JSON and multipart media flow through the canonical attachment-ingress/store policy.
  The adapter uses one request-owned task, shares one timeout across readiness and execution,
  and joins that owned child on timeout/cancellation rather than returning while canonical
  admission/tool/provider cleanup is still running.
- API session isolation is explicit: no `session_id` uses `api:default`; a supplied value
  becomes an `api:<session_id>` logical key. The agent loop remains the sole session
  admission/lock owner; the HTTP adapter installs no second lock.
- API auth is optional for loopback use. The normal `nanobot serve` caller reads
  `api.api_key`, rejects non-loopback binding without authentication, and passes the key
  into `create_app`. `ApiConfig` separately rejects unauthenticated wildcard binds.
- `process_direct_result()` is a thin public wrapper over the same canonical
  `_execute_direct()` implementation used by the HTTP adapter. The API's private-name call
  therefore does not establish a second execution path in this source slice.
- The high-level SDK builds on the same direct-turn boundary. `Nanobot.run()` and streamed
  runs use `process_direct_result`, preserve per-run runtime/model selection, and expose
  detached sanitized traces only when requested.
- SDK stream delivery is single-consumer and bounded by a 256-entry queue. `wait()` drains
  events when no consumer is active; explicit close/cancel cancels and joins the underlying
  run. Tool/reasoning events remain explicitly public to the trusted SDK caller.
- Session display snapshots strip model-only runtime-context suffix metadata, while
  `export()`/ `restore()` intentionally form the trusted full-snapshot path. Untrusted
  `ingest()` strips the reserved runtime-context history marker from imported messages.
- Session deletion already triggers the `SessionManager` delete observer installed by
  `AgentLoop`, so SDK `delete()` does discard per-session file-read/write state even though
  it does not call `discard_session_file_state()` itself. No stale-file-state finding is
  warranted.

## E02-A provisional finding

### E02-F01 — P2 conditional — failed SDK transcript ingestion can leave a partial live-session mutation

**Evidence.** `SessionClient.ingest()` rejects managed persistent import first, but for the
normal unmanaged `save=True` path it immediately calls `SessionManager.get_or_create()`,
then applies caller metadata directly to `session.metadata`. It validates each input
message only as it reaches that message and calls `session.add_message()` after each valid
entry. A malformed later message therefore raises `ValueError` after metadata and any valid
prefix have already mutated the cached live session; there is no rollback. The final
`sessions.save(session)` is skipped by the exception, but `SessionManager.flush_all()`
later persists cached sessions, and an ordinary future turn/save can also make the partial
state durable. The source suite's ingest validation test exercises a malformed first message
without checking rollback, while `SessionClient.restore()` deliberately pre-validates every
message before mutating and its test asserts that a failed restore leaves the target clean.

**Consequence.** A caller can receive an import failure while the same session key already
contains imported metadata or a valid transcript prefix. Subsequent SDK reads/runs can observe
that state, so a supposedly rejected external transcript can influence later model history.
A later flush or normal save can persist it even though the original ingest call never
reported success.

**Qualification.** This requires the unmanaged persistent path (the default `save=True`)
and either metadata or at least one valid message before the invalid entry. Managed persistent
ingest is rejected before mutation, and `save=False` uses a detached transient `Session`,
so those paths do not share this partial-state consequence. The failed ingest call itself
does not write the partial state to disk before raising.

**Smallest later alternative.** Parse and validate the complete transcript and metadata into
a detached candidate before obtaining/mutating the live session. For the strongest import
contract, clone/build the candidate session and publish it to the live cache only after the
durable save succeeds.

### E02-B behavior established

- The built-in WebSocket plugin is always available/default-enabled for the gateway surface.
  Its setup validator is deliberately lightweight; runtime authentication and listener state are
  owned by the channel/gateway endpoint rather than the setup form.
- Default transport configuration is loopback-only, `websocket_requires_token=True`,
  `allow_from=["*"]`, bounded frame size, and bounded ping intervals. Static tokens,
  one-time issued tokens and explicitly configured trusted-proxy assertions are the handshake
  authentication mechanisms.
- The endpoint checks `allow_from` using the caller-supplied `client_id`; this is an
  authorization label, not an independent identity proof. Security therefore depends on the
  handshake authentication configuration when the listener is reachable by untrusted peers.
- One-time connection tokens are consumed on successful use. Bootstrap tokens carry a
  `webui` audience and are the only ordinary issued tokens that add the connection to the
  trusted WebUI mutation set. Plain client/static-token sockets cannot invoke privileged
  `webui_request` mutations unless a separately authorized mobile mutation allows the action.
- The local bootstrap path requires either a local-browser request, configured issue/static
  secret, or trusted-proxy authentication. API tokens are distinct from WebSocket tokens.
- Listener ownership is explicit. Initial bind failures such as `EADDRINUSE` fail rather
  than loop forever; a listener that was successfully serving and later loses its socket is
  recreated with bounded backoff. Shutdown closes the listener and connection-local writers.
- Each connection has a bounded 256-frame / 8 MiB outbound queue. Slow or failed connections
  are retired independently with send and close timeouts, so one client cannot indefinitely
  backpressure other subscribers through the channel's fan-out path.
- Connection cleanup is idempotent, cancels/drains its writer, detaches all chat subscriptions,
  removes gateway trust state and prevents buffered/stale envelopes from reviving a retired
  connection.
- Typed WebUI messages validate chat IDs, text/media ingress and workspace scope before bus
  publication. Trusted-only features such as user shell, quoted/session runtime context and
  WebUI mutations are gated by the bootstrap/trusted-proxy/mobile authority sets.
- Raw legacy frames remain supported. They are revalidated for an established typed mobile
  identity and otherwise flow through the base channel sender allowlist before publication.

### E02-F02 — P1 conditional — non-loopback WebSocket configurations can admit unauthenticated agent clients

**Evidence.** `WebSocketConfig.wildcard_host_requires_auth()` checks only the literal
wildcard hosts `0.0.0.0` and `::`; a listener bound directly to another non-loopback
address is not required to have any effective authentication. The handshake owner then accepts
all clients when there is no static `token` and `websocket_requires_token=False`.
On wildcard hosts, the validator can also be satisfied by `token_issue_secret` or
`trusted_proxy_auth` alone even though those do not make a direct untrusted handshake
mandatory when `websocket_requires_token=False`. Separately, with token-required mode,
a configured `token_issue_path` whose issue/static secret is empty explicitly issues a
connection token to any requester; the HTTP handler logs a warning but does not reject it.
The default sender allowlist is `["*"]`, and `client_id` is supplied by the peer.

**Consequence.** If an operator exposes the listener on a LAN/public interface using one of
those combinations, an unauthenticated remote peer can establish a WebSocket session and
submit agent turns as an allowed client. That can expose model output and exercise whatever
agent/tool capabilities the effective workspace and tool policies permit. This finding does
**not** establish arbitrary host control: privileged WebUI mutations remain separately gated
to WebUI/mobile authority, and normal tool/workspace/sandbox/approval policies still apply.

**Qualification.** The shipped default is materially safer: it binds to `127.0.0.1` and
requires a token. A non-empty static token is always enforced by the handshake even when
`websocket_requires_token=False`. Proper token-required issuance with a protected issue
secret and correctly configured trusted-proxy deployments are not the vulnerable case.
The trigger requires an explicitly network-reachable configuration whose effective client
authentication is disabled or publicly self-serviceable.

**Smallest later alternative.** Validate **effective** authentication for every non-loopback
bind rather than only wildcard literals. At minimum, reject non-loopback configurations where
a direct peer can connect without a static/issued token, and reject unauthenticated token
issuance on non-loopback listeners. If trusted-proxy assertion is the intended sole authority,
make direct non-proxy handshakes fail closed instead of letting `websocket_requires_token=False`
open a second path.

### E02-C behavior established

- Gateway composition centralizes one token store, HTTP handler, WebSocket endpoint, ingress
  policy, media service, transcript recorder, workspace controller and session projection.
  The transport and application routers share those objects instead of maintaining parallel
  authority state.
- WebSocket connection credentials and HTTP API credentials are distinct short-lived token
  namespaces. Issued WebSocket tokens are one-time; API tokens remain reusable until expiry.
  The HTTP token checker accepts either Bearer auth or the legacy/query-token form.
- Local-browser authority is based on the actual loopback peer, a loopback Host header and
  loopback-only forwarded identity values. Trusted-proxy authority instead requires an
  explicitly configured peer network plus a non-empty configured assertion header.
- WebUI text policy is measured in UTF-8 bytes and is deliberately separate from the raw
  WebSocket frame ceiling. Attachment compatibility wrappers delegate to the canonical
  attachment ingress/store and preserve whole-batch rejection semantics.
- Outbound event encoding is allowlisted rather than serializing arbitrary runtime metadata.
  Retry, recovery, compaction and turn-completion payloads explicitly choose their public
  fields and durability class.
- The outbound projector keeps runtime-model broadcasts, per-chat events, reconnect state,
  transcript persistence and turn-owner cleanup separate. Final turn completion is projected
  even without active subscribers so durable completion/transcript state is not dependent on
  a live browser.
- Session projection reads only persisted metadata required for attach/reconnect state:
  model preset, recovery state, last usage, actionable goal state and same-process active-turn
  status.
- Durable mutation replay records an `in_progress` entry before executing the effect,
  persists completed results before delivery, converts failed/timeout execution to an
  uncertain state, and fails closed on corrupt ledgers. Permission-sensitive mutations bind
  replay to canonical session source lifetime in the command router.
- Replay storage is bounded: completed results expire on the normal TTL, stale in-progress
  records become uncertain, and fresh in-progress records are not evicted merely to make
  capacity.
- WebSocket handshake logging suppresses only recognized peer disconnect/malformed-handshake
  noise under the exact "opening handshake failed" record while leaving other server-side
  handshake errors visible.

### Retained E02-C observations / questions

1. `DurableWebUIReplay` describes itself as process-safe but synchronizes only with an
   instance-local `threading.RLock` and caches the file contents in memory. Two live router
   processes sharing the same replay path could therefore race and overwrite one another's

   recommends separate config directories, so this is retained as a deployment-boundary

2. Completed replay entries intentionally expire much sooner than uncertain crash-window

   review so frontends do not treat request IDs as indefinitely reusable.

### E02-F03 — P2 conditional — Windows media GC can delete generated assets that are still referenced

**Evidence.** `collect_referenced_media_paths()` scans transcript/index JSON strings but
discards every value that does not start with `"/"`. Persisted generated-media paths are
absolute host paths. On Windows, ordinary drive-letter paths such as
`C:\Users\...\media\generated\image.png` and UNC paths do not start with `/`, so
they never enter the `referenced` set. `garbage_collect_generated_media()` then treats
those files as unreferenced: after `generated_media_orphan_grace_days` they qualify for
orphan deletion, and an enabled byte quota may delete unreferenced files regardless of orphan
age. The shipped config default is a seven-day orphan grace period. The
`nanobot media-gc` CLI invokes this exact path.

**Consequence.** A Windows user can run the supported media-maintenance command and delete
generated images/videos that are still referenced by conversation transcripts or generated-
asset indexes. After deletion, historical gallery/thread links can no longer resolve the
artifact. With `generated_media_max_bytes > 0`, the same misclassification can also make
referenced files eligible for quota eviction before the seven-day orphan threshold.

**Qualification.** This is conditional on Windows-style absolute paths and execution of the
media GC path; this source-only stage did not establish an automatic periodic invocation.
Configured age-based retention is intentionally allowed to delete referenced assets and is not
part of the defect. POSIX absolute paths beginning with `/` follow the intended reference
collection path.

**Smallest later alternative.** Parse stored paths with platform-aware absolute-path logic
instead of a leading-slash test. On Windows, accept canonical drive-letter and UNC absolute
paths, resolve them, and retain only candidates under the instance media root before applying
orphan/quota policy.

### E02-F04 — P2 conditional — the global generated-assets library silently omits sessions after the first 200

**Evidence.** `load_all_generated_asset_groups()` documents that it returns indexed groups
for "every persisted WebUI session", but it sorts discovered session keys and iterates only
`webui_session_keys(webui_dir)[:max_sessions]` with a default `max_sessions=200`.
`GatewayHTTPHandler._handle_all_generated_assets()` calls it without overriding that
limit. The API's later `cursor`/`limit` pagination operates only on groups already
collected from those selected sessions, so a client cannot page into the omitted sessions.
The response reports `total` only for selected groups and exposes no session-truncation flag.

**Consequence.** Once an instance has more than 200 persisted WebUI sessions, the global asset
library can permanently hide valid generated assets from later lexicographic session keys.
Creating a new session does not guarantee its assets appear, and ordinary group pagination
cannot recover the omitted data.

**Qualification.** The defect triggers only when more than 200 persisted WebUI sessions are
discoverable. Per-session generated-assets endpoints remain unaffected. A deliberate backend
scan cap is reasonable, but the current ordering and response contract make the cap silent
and non-pageable.

**Smallest later alternative.** Page session discovery itself (preferably by a stable/recent
ordering), or maintain a global asset index. If a hard scan cap is retained, return a
truncation/continuation cursor so every session remains reachable.

### E02-F05 — P2 conditional — lossy WebUI transcript filenames collapse distinct valid chat IDs

**Evidence.** The WebUI protocol accepts both `:` and `_` in chat IDs; the source test
explicitly accepts values such as `a1b2_c:d-e` and `unified:default`.
`webui_session_key(chat_id)` produces distinct logical keys, but every transcript path,
segment directory and legacy thread path calls `SessionManager.safe_key()`, which replaces
`:` with `_` before applying `safe_filename()`. Thus the distinct valid session keys
`websocket:a:b` and `websocket:a_b` both map to the same
`websocket_a_b.{jsonl,json}` / `websocket_a_b.segments` storage identity. The generated-
asset index reviewed in E02-D uses the same lossy stem. In contrast, canonical session storage
uses reversible base64url `storage_key()`.

**Consequence.** Two distinct valid chats can read and append to the same WebUI display
transcript. Reads for either logical key can return the other chat's rows while labelling the
payload with the requested session key; deletion or rewrite/fork operations against one key can
remove or replace the shared display history; generated-asset indexing and transcript-derived
file-preview provenance can likewise be attributed to the wrong logical chat. Canonical agent
sessions remain separate, so model history and WebUI display history can disagree.

**Qualification.** Normal `new_chat` creation generates UUID chat IDs and therefore does not
naturally create this collision. The trigger requires caller-supplied, imported or legacy chat
IDs that differ only through characters collapsed by `safe_key()`, especially colon versus
underscore. The typed WebSocket `attach` and message paths accept arbitrary chat IDs that pass
the public validator, so the colliding IDs are within the protocol contract rather than invalid
filesystem input.

**Smallest later alternative.** Move WebUI transcript, segment, legacy-snapshot and asset-index
filenames to the same reversible/collision-resistant session-key encoding used by canonical
session storage, with a compatibility migration/read fallback for existing lossy filenames.
Do not infer an original logical key from a lossy stem when multiple valid keys can map to it.

### E02-F06 — P2 conditional — session deletion can report success while readable WebUI transcript residue remains

**Evidence.** `delete_webui_transcript()` independently unlinks the active transcript and
legacy JSON, removes the segment directory, and deletes the generated-asset index. Each
filesystem deletion catches `OSError`, logs, and continues. Its boolean means that **at least
one** artifact was removed, not that all artifacts are gone. `delete_webui_thread()` preserves
that any-success semantics. The session-delete route separately deletes the canonical session
and returns `{"deleted": bool(draft_deleted or session_deleted or transcript_deleted)}`.
Therefore successful canonical deletion can produce `deleted: true` even when every
transcript deletion failed, and partial transcript deletion can also return true while segments
remain. Separately, source tests explicitly establish that transcript-only sessions with no
canonical session file are still listed and their thread is still served; workspace scope falls
back to the default scope when session metadata is absent.

**Consequence.** Under a filesystem deletion failure (permission change, locked directory/file,
I/O error, etc.), the user can receive a successful session-deletion result while old display
messages/tool traces/media references remain recoverable through the authenticated WebUI
session/thread surface. This violates the intuitive data-removal boundary and can also leave
transcript-derived generated-asset/file-preview state reachable after the canonical session is
gone.

**Qualification.** This is conditional on an actual filesystem deletion failure; the normal
source-tested delete path removes both canonical and transcript files. It does not claim that
canonical session history survives—the defect is the successful API result plus remaining
WebUI persistence that is intentionally capable of standing alone.

**Smallest later alternative.** Make transcript deletion return structured complete/partial
status and have `session.delete` fail or explicitly report partial deletion while any expected
WebUI artifact remains. A deletion tombstone that prevents transcript-only recovery for a
successfully deleted session can provide a second fail-closed layer until cleanup succeeds.

### E02-F07 — P2 conditional — transcript rotation can duplicate completed turns after a mid-rotation write failure

**Evidence.** `_rotate_active_transcript_if_needed()` moves old turns in two durable steps:
first `_append_segment_turns()` writes/replaces one or more segment files and then the segment
manifest; only afterwards does `_write_records_to_path()` replace the active JSONL with the
kept tail. There is no transaction, overlap marker or rollback across those steps. If an
`OSError` occurs after a segment has been committed but before the active JSONL replacement,
the moved turns remain both in the segment set and in the unchanged active file. On the next
read, missing/stale manifests are rebuilt from segment files and `read_transcript_lines()`
simply concatenates segments plus active rows. The replay fold aliases a repeated closed
`turn_id` rather than deduplicating its records.

**Consequence.** A disk failure during rotation can leave persistent duplicate user/assistant
turns in WebUI history. Pagination/message counts and transcript-derived file references can be
duplicated, and later fork/rewrite operations can copy the duplicated display history. Because
the active file still contains the moved rows, repeated failed rotation attempts can add further
overlap before a successful active-tail replacement.

**Qualification.** The trigger requires a multi-turn active transcript above the rotation
threshold plus a write/replace/manifest failure in the window after at least one segment file
has committed. The normal rotation path is loss-averse and source behavior shows no duplication
when all writes succeed. This stage did not execute fault injection; the duplicate state follows
directly from the write ordering and read concatenation.

**Smallest later alternative.** Give rotation an explicit atomic generation boundary: stage the
new segment set/manifest and new active tail together, then switch one committed generation
pointer, or persist a rotation watermark/digest that lets reads suppress active rows already
committed to segments. Recovery should prefer either the pre-rotation generation or the
post-rotation generation, never both.
