## E02-A behavior established

- The HTTP surface is intentionally a **minimal** OpenAI-compatible adapter, not full protocol
  parity. The pinned README explicitly documents exactly one user message per request, a fixed
  configured model and no streaming. The live server enforces those limits and rejects remote
  image URLs.
- API JSON and multipart media flow through the canonical attachment-ingress/store policy.
  The adapter uses one request-owned task, shares one timeout across readiness and execution,
  and joins that owned child on timeout/cancellation rather than returning while canonical
  admission/tool/provider cleanup is still running.
- API session isolation is explicit: no `session_id` uses `api:default`; a supplied value
  becomes an `api:<session_id>` logical key. The agent loop remains the sole session
  admission/lock owner; the HTTP adapter installs no second lock.
- API auth is optional for loopback use. The normal `nanobot serve` caller reads
  `api.api_key`, rejects non-loopback binding without authentication, and passes the key
  into `create_app`. `ApiConfig` separately rejects unauthenticated wildcard binds.
- `process_direct_result()` is a thin public wrapper over the same canonical
  `_execute_direct()` implementation used by the HTTP adapter. The API's private-name call
  therefore does not establish a second execution path in this source slice.
- The high-level SDK builds on the same direct-turn boundary. `Nanobot.run()` and streamed
  runs use `process_direct_result`, preserve per-run runtime/model selection, and expose
  detached sanitized traces only when requested.
- SDK stream delivery is single-consumer and bounded by a 256-entry queue. `wait()` drains
  events when no consumer is active; explicit close/cancel cancels and joins the underlying
  run. Tool/reasoning events remain explicitly public to the trusted SDK caller.
- Session display snapshots strip model-only runtime-context suffix metadata, while
  `export()`/ `restore()` intentionally form the trusted full-snapshot path. Untrusted
  `ingest()` strips the reserved runtime-context history marker from imported messages.
- Session deletion already triggers the `SessionManager` delete observer installed by
  `AgentLoop`, so SDK `delete()` does discard per-session file-read/write state even though
  it does not call `discard_session_file_state()` itself. No stale-file-state finding is
  warranted.

## E02-A provisional finding

### E02-F01 — P2 conditional — failed SDK transcript ingestion can leave a partial live-session mutation

**Evidence.** `SessionClient.ingest()` rejects managed persistent import first, but for the
normal unmanaged `save=True` path it immediately calls `SessionManager.get_or_create()`,
then applies caller metadata directly to `session.metadata`. It validates each input
message only as it reaches that message and calls `session.add_message()` after each valid
entry. A malformed later message therefore raises `ValueError` after metadata and any valid
prefix have already mutated the cached live session; there is no rollback. The final
`sessions.save(session)` is skipped by the exception, but `SessionManager.flush_all()`
later persists cached sessions, and an ordinary future turn/save can also make the partial
state durable. The source suite's ingest validation test exercises a malformed first message
without checking rollback, while `SessionClient.restore()` deliberately pre-validates every
message before mutating and its test asserts that a failed restore leaves the target clean.

**Consequence.** A caller can receive an import failure while the same session key already
contains imported metadata or a valid transcript prefix. Subsequent SDK reads/runs can observe
that state, so a supposedly rejected external transcript can influence later model history.
A later flush or normal save can persist it even though the original ingest call never
reported success.

**Qualification.** This requires the unmanaged persistent path (the default `save=True`)
and either metadata or at least one valid message before the invalid entry. Managed persistent
ingest is rejected before mutation, and `save=False` uses a detached transient `Session`,
so those paths do not share this partial-state consequence. The failed ingest call itself
does not write the partial state to disk before raising.

**Smallest later alternative.** Parse and validate the complete transcript and metadata into
a detached candidate before obtaining/mutating the live session. For the strongest import
contract, clone/build the candidate session and publish it to the live cache only after the
durable save succeeds.

### E02-B behavior established

- The built-in WebSocket plugin is always available/default-enabled for the gateway surface.
  Its setup validator is deliberately lightweight; runtime authentication and listener state are
  owned by the channel/gateway endpoint rather than the setup form.
- Default transport configuration is loopback-only, `websocket_requires_token=True`,
  `allow_from=["*"]`, bounded frame size, and bounded ping intervals. Static tokens,
  one-time issued tokens and explicitly configured trusted-proxy assertions are the handshake
  authentication mechanisms.
- The endpoint checks `allow_from` using the caller-supplied `client_id`; this is an
  authorization label, not an independent identity proof. Security therefore depends on the
  handshake authentication configuration when the listener is reachable by untrusted peers.
- One-time connection tokens are consumed on successful use. Bootstrap tokens carry a
  `webui` audience and are the only ordinary issued tokens that add the connection to the
  trusted WebUI mutation set. Plain client/static-token sockets cannot invoke privileged
  `webui_request` mutations unless a separately authorized mobile mutation allows the action.
- The local bootstrap path requires either a local-browser request, configured issue/static
  secret, or trusted-proxy authentication. API tokens are distinct from WebSocket tokens.
- Listener ownership is explicit. Initial bind failures such as `EADDRINUSE` fail rather
  than loop forever; a listener that was successfully serving and later loses its socket is
  recreated with bounded backoff. Shutdown closes the listener and connection-local writers.
- Each connection has a bounded 256-frame / 8 MiB outbound queue. Slow or failed connections
  are retired independently with send and close timeouts, so one client cannot indefinitely
  backpressure other subscribers through the channel's fan-out path.
- Connection cleanup is idempotent, cancels/drains its writer, detaches all chat subscriptions,
  removes gateway trust state and prevents buffered/stale envelopes from reviving a retired
  connection.
- Typed WebUI messages validate chat IDs, text/media ingress and workspace scope before bus
  publication. Trusted-only features such as user shell, quoted/session runtime context and
  WebUI mutations are gated by the bootstrap/trusted-proxy/mobile authority sets.
- Raw legacy frames remain supported. They are revalidated for an established typed mobile
  identity and otherwise flow through the base channel sender allowlist before publication.

### E02-F02 — P1 conditional — non-loopback WebSocket configurations can admit unauthenticated agent clients

**Evidence.** `WebSocketConfig.wildcard_host_requires_auth()` checks only the literal
wildcard hosts `0.0.0.0` and `::`; a listener bound directly to another non-loopback
address is not required to have any effective authentication. The handshake owner then accepts
all clients when there is no static `token` and `websocket_requires_token=False`.
On wildcard hosts, the validator can also be satisfied by `token_issue_secret` or
`trusted_proxy_auth` alone even though those do not make a direct untrusted handshake
mandatory when `websocket_requires_token=False`. Separately, with token-required mode,
a configured `token_issue_path` whose issue/static secret is empty explicitly issues a
connection token to any requester; the HTTP handler logs a warning but does not reject it.
The default sender allowlist is `["*"]`, and `client_id` is supplied by the peer.

**Consequence.** If an operator exposes the listener on a LAN/public interface using one of
those combinations, an unauthenticated remote peer can establish a WebSocket session and
submit agent turns as an allowed client. That can expose model output and exercise whatever
agent/tool capabilities the effective workspace and tool policies permit. This finding does
**not** establish arbitrary host control: privileged WebUI mutations remain separately gated
to WebUI/mobile authority, and normal tool/workspace/sandbox/approval policies still apply.

**Qualification.** The shipped default is materially safer: it binds to `127.0.0.1` and
requires a token. A non-empty static token is always enforced by the handshake even when
`websocket_requires_token=False`. Proper token-required issuance with a protected issue
secret and correctly configured trusted-proxy deployments are not the vulnerable case.
The trigger requires an explicitly network-reachable configuration whose effective client
authentication is disabled or publicly self-serviceable.

**Smallest later alternative.** Validate **effective** authentication for every non-loopback
bind rather than only wildcard literals. At minimum, reject non-loopback configurations where
a direct peer can connect without a static/issued token, and reject unauthenticated token
issuance on non-loopback listeners. If trusted-proxy assertion is the intended sole authority,
make direct non-proxy handshakes fail closed instead of letting `websocket_requires_token=False`
open a second path.

### E02-C behavior established

- Gateway composition centralizes one token store, HTTP handler, WebSocket endpoint, ingress
  policy, media service, transcript recorder, workspace controller and session projection.
  The transport and application routers share those objects instead of maintaining parallel
  authority state.
- WebSocket connection credentials and HTTP API credentials are distinct short-lived token
  namespaces. Issued WebSocket tokens are one-time; API tokens remain reusable until expiry.
  The HTTP token checker accepts either Bearer auth or the legacy/query-token form.
- Local-browser authority is based on the actual loopback peer, a loopback Host header and
  loopback-only forwarded identity values. Trusted-proxy authority instead requires an
  explicitly configured peer network plus a non-empty configured assertion header.
- WebUI text policy is measured in UTF-8 bytes and is deliberately separate from the raw
  WebSocket frame ceiling. Attachment compatibility wrappers delegate to the canonical
  attachment ingress/store and preserve whole-batch rejection semantics.
- Outbound event encoding is allowlisted rather than serializing arbitrary runtime metadata.
  Retry, recovery, compaction and turn-completion payloads explicitly choose their public
  fields and durability class.
- The outbound projector keeps runtime-model broadcasts, per-chat events, reconnect state,
  transcript persistence and turn-owner cleanup separate. Final turn completion is projected
  even without active subscribers so durable completion/transcript state is not dependent on
  a live browser.
- Session projection reads only persisted metadata required for attach/reconnect state:
  model preset, recovery state, last usage, actionable goal state and same-process active-turn
  status.
- Durable mutation replay records an `in_progress` entry before executing the effect,
  persists completed results before delivery, converts failed/timeout execution to an
  uncertain state, and fails closed on corrupt ledgers. Permission-sensitive mutations bind
  replay to canonical session source lifetime in the command router.
- Replay storage is bounded: completed results expire on the normal TTL, stale in-progress
  records become uncertain, and fresh in-progress records are not evicted merely to make
  capacity.
- WebSocket handshake logging suppresses only recognized peer disconnect/malformed-handshake
  noise under the exact "opening handshake failed" record while leaving other server-side
  handshake errors visible.

1. `DurableWebUIReplay` describes itself as process-safe but synchronizes only with an
   instance-local `threading.RLock` and caches the file contents in memory. Two live router
   processes sharing the same replay path could therefore race and overwrite one another's

### E02-F03 — P2 conditional — Windows media GC can delete generated assets that are still referenced

**Evidence.** `collect_referenced_media_paths()` scans transcript/index JSON strings but
discards every value that does not start with `"/"`. Persisted generated-media paths are
absolute host paths. On Windows, ordinary drive-letter paths such as
`C:\Users\...\media\generated\image.png` and UNC paths do not start with `/`, so
they never enter the `referenced` set. `garbage_collect_generated_media()` then treats
those files as unreferenced: after `generated_media_orphan_grace_days` they qualify for
orphan deletion, and an enabled byte quota may delete unreferenced files regardless of orphan
age. The shipped config default is a seven-day orphan grace period. The
`nanobot media-gc` CLI invokes this exact path.

**Consequence.** A Windows user can run the supported media-maintenance command and delete
generated images/videos that are still referenced by conversation transcripts or generated-
asset indexes. After deletion, historical gallery/thread links can no longer resolve the
artifact. With `generated_media_max_bytes > 0`, the same misclassification can also make
referenced files eligible for quota eviction before the seven-day orphan threshold.

**Qualification.** This is conditional on Windows-style absolute paths and execution of the
media GC path; this source-only stage did not establish an automatic periodic invocation.
Configured age-based retention is intentionally allowed to delete referenced assets and is not
part of the defect. POSIX absolute paths beginning with `/` follow the intended reference
collection path.

**Smallest later alternative.** Parse stored paths with platform-aware absolute-path logic
instead of a leading-slash test. On Windows, accept canonical drive-letter and UNC absolute
paths, resolve them, and retain only candidates under the instance media root before applying
orphan/quota policy.

### E02-F04 — P2 conditional — the global generated-assets library silently omits sessions after the first 200

**Evidence.** `load_all_generated_asset_groups()` documents that it returns indexed groups
for "every persisted WebUI session", but it sorts discovered session keys and iterates only

collected from those selected sessions, so a client cannot page into the omitted sessions.

**Consequence.** Once an instance has more than 200 persisted WebUI sessions, the global asset

**Qualification.** The defect triggers only when more than 200 persisted WebUI sessions are

truncation/continuation cursor so every session remains reachable.

### E02-F05 — P2 conditional — lossy WebUI transcript filenames collapse distinct valid chat IDs

**Evidence.** The WebUI protocol accepts both `:` and `_` in chat IDs; the source test
explicitly accepts values such as `a1b2_c:d-e` and `unified:default`.
`webui_session_key(chat_id)` produces distinct logical keys, but every transcript path,
segment directory and legacy thread path calls `SessionManager.safe_key()`, which replaces
`:` with `_` before applying `safe_filename()`. Thus the distinct valid session keys
`websocket:a:b` and `websocket:a_b` both map to the same
`websocket_a_b.{jsonl,json}` / `websocket_a_b.segments` storage identity. The generated-
asset index reviewed in E02-D uses the same lossy stem. In contrast, canonical session storage
uses reversible base64url `storage_key()`.

**Consequence.** Two distinct valid chats can read and append to the same WebUI display
transcript. Reads for either logical key can return the other chat's rows while labelling the
payload with the requested session key; deletion or rewrite/fork operations against one key can
remove or replace the shared display history; generated-asset indexing and transcript-derived
file-preview provenance can likewise be attributed to the wrong logical chat. Canonical agent
sessions remain separate, so model history and WebUI display history can disagree.

**Qualification.** Normal `new_chat` creation generates UUID chat IDs and therefore does not
naturally create this collision. The trigger requires caller-supplied, imported or legacy chat
IDs that differ only through characters collapsed by `safe_key()`, especially colon versus
underscore. The typed WebSocket `attach` and message paths accept arbitrary chat IDs that pass
the public validator, so the colliding IDs are within the protocol contract rather than invalid
filesystem input.

**Smallest later alternative.** Move WebUI transcript, segment, legacy-snapshot and asset-index
filenames to the same reversible/collision-resistant session-key encoding used by canonical
session storage, with a compatibility migration/read fallback for existing lossy filenames.
Do not infer an original logical key from a lossy stem when multiple valid keys can map to it.

### E02-F06 — P2 conditional — session deletion can report success while readable WebUI transcript residue remains

**Evidence.** `delete_webui_transcript()` independently unlinks the active transcript and
legacy JSON, removes the segment directory, and deletes the generated-asset index. Each
filesystem deletion catches `OSError`, logs, and continues. Its boolean means that **at least
one** artifact was removed, not that all artifacts are gone. `delete_webui_thread()` preserves
that any-success semantics. The session-delete route separately deletes the canonical session
and returns `{"deleted": bool(draft_deleted or session_deleted or transcript_deleted)}`.
Therefore successful canonical deletion can produce `deleted: true` even when every
transcript deletion failed, and partial transcript deletion can also return true while segments
remain. Separately, source tests explicitly establish that transcript-only sessions with no
canonical session file are still listed and their thread is still served; workspace scope falls
back to the default scope when session metadata is absent.

**Consequence.** Under a filesystem deletion failure (permission change, locked directory/file,
I/O error, etc.), the user can receive a successful session-deletion result while old display
messages/tool traces/media references remain recoverable through the authenticated WebUI
session/thread surface. This violates the intuitive data-removal boundary and can also leave
transcript-derived generated-asset/file-preview state reachable after the canonical session is
gone.

**Qualification.** This is conditional on an actual filesystem deletion failure; the normal
source-tested delete path removes both canonical and transcript files. It does not claim that
canonical session history survives—the defect is the successful API result plus remaining
WebUI persistence that is intentionally capable of standing alone.

**Smallest later alternative.** Make transcript deletion return structured complete/partial
status and have `session.delete` fail or explicitly report partial deletion while any expected
WebUI artifact remains. A deletion tombstone that prevents transcript-only recovery for a
successfully deleted session can provide a second fail-closed layer until cleanup succeeds.

### E02-F07 — P2 conditional — transcript rotation can duplicate completed turns after a mid-rotation write failure

**Evidence.** `_rotate_active_transcript_if_needed()` moves old turns in two durable steps:
first `_append_segment_turns()` writes/replaces one or more segment files and then the segment
manifest; only afterwards does `_write_records_to_path()` replace the active JSONL with the
kept tail. There is no transaction, overlap marker or rollback across those steps. If an
`OSError` occurs after a segment has been committed but before the active JSONL replacement,
the moved turns remain both in the segment set and in the unchanged active file. On the next
read, missing/stale manifests are rebuilt from segment files and `read_transcript_lines()`
simply concatenates segments plus active rows. The replay fold aliases a repeated closed
`turn_id` rather than deduplicating its records.

**Consequence.** A disk failure during rotation can leave persistent duplicate user/assistant
turns in WebUI history. Pagination/message counts and transcript-derived file references can be
duplicated, and later fork/rewrite operations can copy the duplicated display history. Because
the active file still contains the moved rows, repeated failed rotation attempts can add further
overlap before a successful active-tail replacement.

**Qualification.** The trigger requires a multi-turn active transcript above the rotation
threshold plus a write/replace/manifest failure in the window after at least one segment file
has committed. The normal rotation path is loss-averse and source behavior shows no duplication
when all writes succeed. This stage did not execute fault injection; the duplicate state follows
directly from the write ordering and read concatenation.

**Smallest later alternative.** Give rotation an explicit atomic generation boundary: stage the
new segment set/manifest and new active tail together, then switch one committed generation
pointer, or persist a rotation watermark/digest that lets reads suppress active rows already
committed to segments. Recovery should prefer either the pre-rotation generation or the
post-rotation generation, never both.

  also deliberately discoverable from active/segment JSONL files when their canonical session
  file is absent.
- Sidebar index reads hold the canonical session-files lock, use unique atomic temp files, cache
  file/activity signatures, rescan changed canonical/transcript sources, preserve workspace-
  scope missing-vs-null semantics, filter hidden previews/provider-state rows and isolate
  per-runtime index namespaces by the full sessions-directory path.
- The transcript-only sidebar scanner recovers colon-containing chat IDs from transcript
  `chat_id` fields. Because the underlying transcript stem remains lossy, E02-F05's
  collision consequence is strengthened: colliding canonical sessions can share one WebUI
  activity signature, and transcript-only recovery can attribute the shared stem to only one
  logical key.
- State invalidation maps session/workspace/recovery mutations to session refresh, settings /
  skill / automation / repository mutations to settings refresh, and sidebar mutations to the
  sidebar's own full projection. Unknown namespaces conservatively refresh session and settings
  caches.
- Temporary Chats use non-persistent, non-content-logging `SessionPolicy`, UUID identities,
  connection ownership, private source incarnations, disabled durable tools/commands, no
  transcript hydration/persistence, and request-bound Full permission references. Cache
  pressure is handled through the manager's weak overflow cache plus the controller's strong
  active-session reference.
- On discard, Temporary Chat permission state is retired, owner/session/media state is removed,
  the manager cache is invalidated and a local unbounded-queue runtime-control message requests
  active-session cancellation. Tombstones intentionally block late attach/message/transcript
  persistence after disposal.

### E02-F08 — P2 conditional — session search can return transcript-only results that read_session rejects

**Evidence.** `list_webui_sessions()` intentionally indexes WebUI transcripts that have no
canonical session file, and source tests establish transcript-only sessions are valid sidebar /
thread recovery state. `WebuiSessionAccess.search()` consumes those rows and calls
`_messages()`, which can build visible history directly from the WebUI transcript, so a
content query can return a transcript-only `session_key`. `SearchSessionsTool` exposes that
key/reference and explicitly tells the model to use `read_session` for more context. However,
`WebuiSessionAccess.read()` first calls `_metadata()`; with no canonical session metadata it
returns `None` before attempting the same transcript reader. `ReadSessionTool` therefore
reports that the session was not found.

**Consequence.** The supported search/read workflow can produce a dangling result: the agent
successfully finds a historical conversation excerpt and receives an exact session reference,
then cannot read additional history from that same recovered conversation. This is especially
visible after transcript-only recovery or after a canonical-session deletion that left display
history behind.

**Qualification.** The trigger requires a WebUI transcript with no canonical session record and
a search query matching its visible content. Ordinary canonical sessions and cross-channel
persisted sessions are unaffected. Transcript-only recovery itself is intentional; the defect
is the mismatch between search and read capability over that supported state.

**Smallest later alternative.** Either make `read()` support validated transcript-only WebUI
sessions using the same indexed source and transcript projection as `search()`, or exclude
transcript-only rows from `search_sessions` and clearly reserve them for UI-only recovery.
Search must not return a reference that its documented follow-up reader rejects.

### E02-F09 — P2 conditional — failed Temporary Chat attachment deletion is forgotten instead of retried

**Evidence.** Committed inbound media used by a Temporary Chat is passed to
`register_media()`, which records each stored path under that chat. On discard/connection
cleanup, `_discard_media()` first removes the entire path set with
`self._media_paths.pop(chat_id, set())`, then calls `Path.unlink(missing_ok=True)` per path.
Any `OSError` is only logged. The failed path is no longer present in `_media_paths`, so
later `close()` or another cleanup pass cannot retry it. Source lifecycle tests assert normal
temporary uploads are deleted on discard, confirming deletion is part of the privacy/lifecycle
contract.

**Consequence.** A filesystem failure during Temporary Chat disposal can leave uploaded private
attachments on disk after the chat/session has been discarded, with no process-local retry
record. The session and transcript are non-persistent, so the leftover media becomes detached
residue that can survive until some unrelated external/manual cleanup.

**Qualification.** Conditional on an actual unlink failure such as filesystem I/O/permission
failure or another platform-specific deletion error. The normal source-tested cleanup path
removes the attachment. This finding does not claim the leftover file is automatically exposed
to another principal; it is a persistence/privacy cleanup failure.

**Smallest later alternative.** Remove a path from tracking only after successful deletion, or
move failed paths into a bounded retry/quarantine set that is retried on later disposal,
gateway shutdown and/or dedicated media maintenance. Cleanup status should remain observable
until every Temporary Chat attachment is gone.

### E02-F10 — P2 conditional — discarded Temporary Chat tombstones grow without bound until gateway shutdown

**Evidence.** Every successful `create()` adds the generated chat ID to
`_known_transient_chat_ids`. The set is intentionally consulted after discard to reject late
messages/attaches and to suppress late transcript persistence. `discard()` removes owner,
incarnation, active-session and media state but never removes the chat ID from this tombstone
set. The only `clear()` is in `close()` at gateway shutdown, and there is no count cap, TTL,
generation compaction or completed-cancellation pruning. The trusted WebUI `new_temporary_chat`
path has no source-visible creation quota in this controller.

**Consequence.** A long-lived gateway accumulates memory linearly with every Temporary Chat ever
created, even after those chats and their media/sessions have been fully discarded. Normal
heavy Temporary Chat use or an authenticated local client repeatedly creating/discarding chats
can therefore create process-lifetime memory growth.

**Qualification.** Each tombstone is small, so ordinary low-volume use is not materially
affected. The trigger is a large number of Temporary Chats during one gateway lifetime; restart
clears the set. Retaining some late-event fence is necessary, so simply deleting the tombstone
immediately would weaken privacy.

**Smallest later alternative.** Tie tombstone lifetime to the corresponding runtime-discard /
turn-generation lifecycle and remove it once cancellation/finalization proves no late producer
can persist. If a time-based fallback is needed, use a bounded TTL/LRU plus an incarnation or
generation token so expired tombstones cannot make a stale late event authoritative.

### E02-F11 — P2 conditional — CLI-app WebUI state is not scoped to the gateway's explicit config path

**Evidence.** `cli_apps_api._manager(config_path)` correctly calls
`load_config(config_path)` to obtain that gateway's workspace and CLI runtime settings, but it
constructs `CliAppManager` without a `data_dir`. The manager therefore defaults to
`get_runtime_subdir("cli-apps")`, whose root is derived from the process-global
`get_config_path()`, not the explicit `config_path`. `load_config(explicit_path)` does not
update that global path. This conflicts with the surrounding WebUI settings architecture:
`WebUISettingsConfig` explicitly documents that each gateway reads/mutates its own config path
without consulting the process-global path. The wrapper also keeps
`_catalog_refresh_task` and `_catalog_refresh_last_started` as process-global singleton
state, so one gateway's refresh can suppress or masquerade as another gateway's refresh.

**Consequence.** When two gateway instances/config paths coexist in one process, or an embedded
gateway is composed with a config path different from the process-global path, CLI-app
`installed.json` and registry caches can be read/written under the wrong instance root.
Installed-state presentation, update/uninstall eligibility and catalog freshness can therefore
bleed across instances even though each gateway has a distinct explicit settings config and
workspace. The process-global refresh throttle can additionally leave one instance's stale cache
unrefreshed for the retry window.

**Qualification.** Normal CLI startup usually sets one process-global config path before
building one gateway, so the common single-instance process does not trigger the mismatch.
The defect matters for the codebase's explicit in-process/path-scoped gateway composition and
multi-instance testing/embedding model. Global package-manager installations themselves may be
host-wide; this finding is specifically about Nanobot's own per-instance installed/catalog
state and refresh ownership.

**Smallest later alternative.** Derive an explicit CLI-app runtime data directory from the
gateway/config instance and pass it into `CliAppManager`; never consult the process-global
config path inside this explicit-path WebUI operation. Move refresh task/throttle ownership into
a per-instance service keyed by the same runtime-data identity.

### E02-F12 — P2 conditional — successful WebUI build commands can leave a stale/missing bundle without failing startup

**Evidence.** `build_webui_bundle()` runs dependency installation and the frontend build with
`check=True`, then returns `inspect_webui_bundle(...)` directly. It does not require the
post-build status to be fresh or even require `dist/index.html` to exist. Consequently
`ensure_webui_bundle()` also returns a still-stale `WebUIBundleStatus` without raising
`WebUIBuildError`. The gateway preparation wrapper calls `ensure_webui_bundle()` for its side
effect and discards the returned status, treating any zero-exit build as success.

**Consequence.** If the frontend command exits zero but writes to the wrong output location,
becomes a no-op through a script/config regression, or otherwise fails to refresh the expected
bundle without returning nonzero, `nanobot webui`/gateway startup can continue while the
bundled WebUI remains missing or older than source. A missing bundle can make the embedded UI
unavailable; a stale bundle can run client code whose contract no longer matches the backend
source that just started.

**Qualification.** The shipped Vite config currently writes to the expected
`nanobot/web/dist` and normal Vite write failures should normally return nonzero, so this is a
failure/regression postcondition gap rather than the ordinary build path. Warn/skip modes are
intentionally allowed to proceed stale and are not part of this finding; it applies after a
build was actually attempted as the freshness remedy.

**Smallest later alternative.** After the build, require
`post.dist_available and not post.needs_build`; otherwise raise `WebUIBuildError` with the
remaining reason/newest-source evidence. The caller should only report/continue as a successful
auto build when that postcondition is satisfied.

### E02-F13 — P2 conditional — MCP WebUI credential/runtime state is not scoped to the gateway's explicit config path

**Evidence.** The WebUI settings service is explicitly path-scoped: MCP config reads and
mutations receive `WebUISettingsConfig.path` and serialized config changes use that path.
However, two pieces of MCP instance state bypass that path:

1. Built-in stdio preset materialization and cleanup call `get_runtime_subdir("mcp")`, whose
   data root is derived from the process-global config path rather than the explicit gateway
   config path.
2. OAuth status, sign-in storage and deletion use `MCPOAuthStorage` /
   `delete_mcp_oauth_credentials()`; their `auth/mcp.json` store is likewise derived from
   the process-global data directory and is keyed by server name (plus server-URL fingerprint
   inside the stored entry).

Thus a gateway composed against config A while the process-global path points at config B can
write/remove A's managed MCP runtime directory under B's data root and can read/write/delete OAuth
credential state in B's MCP credential store.

**Consequence.** In multi-instance embedding/tests or any in-process gateway whose explicit config
path differs from the process-global path, MCP cards can report authorization from the wrong
instance, a sign-in can persist credentials in another instance's store, replacement/removal can
delete that other instance's same-name OAuth credentials, and managed preset cleanup can target
the wrong runtime root. The normal single-instance CLI path usually aligns explicit and global
config paths, so ordinary one-gateway startup is not claimed broken.

**Qualification.** This is conditional on divergent explicit/global config paths. The OAuth store
itself has strong file locking, atomic writes, server fingerprints, generations and write leases;
those mechanisms prevent stale-flow resurrection but do not provide gateway/config-path
namespacing. Existing preset tests set the process-global path to the same temporary config before
asserting managed cwd/OAuth behavior, so they do not exercise the divergent-path case.

**Smallest later alternative.** Make MCP state roots explicit dependencies of the path-scoped
settings/runtime composition: derive managed MCP cwd and OAuth credential storage from the active
gateway config/data root (or pass an instance state root/storage object through the preset and
OAuth layers). Keep one canonical root derivation rather than mixing explicit config I/O with
process-global runtime storage.

## E02-F14 — P2 conditional — cancelled skills.sh installs can outlive their WebUI owner

authorization bypass.

## E02-F15 — P1 conditional — WebUI folder-grant authority is not scoped to the gateway's explicit config path

the explicit gateway's config/runtime. Because folder grants feed the live resource policy, this can
cross a filesystem-authority boundary rather than merely corrupt presentation state.

**Qualification.** The normal single-instance CLI path generally aligns the process-global config

storage is better scoped when a session manager supplies its sessions root, and this finding does
not claim that every workspace metadata file shares the same defect.

`WebUISettingsConfig.path` and pass it to every workspace authority store. At minimum,
`FolderGrantStore.for_workspace` needs an explicit `path`/`instance_root` from
`config_path.parent`; the private-root set should protect that same explicit config/credentials/

calling process-global config-path helpers inside path-scoped gateway composition.

## E02-L behavior established

- `WebUISettingsConfig` is explicitly path-scoped and serializes read-modify-write operations
  with a process lock plus a config-file lock. Ordinary settings reads and mutations receive that
  explicit path rather than consulting the process-global config location.
- The in-memory OAuth flow registry is per-gateway, bounded, thread-safe and cancels evicted,
  expired or cleared flows. This protects transient browser-flow lifetime, but not the persisted
  provider credential stores described in E02-F16.
- Provider settings redact API keys and structured secret-like keys on output and restore redacted
  placeholders when updating nested provider structures, avoiding accidental secret destruction.
- Model/provider mutations validate configured providers, model preset references, fallback order,
  bounded numeric values and custom-provider names. Model preset rename attempts to roll back the
  session-side rename if config persistence fails.
- Provider model discovery does not follow redirects and does not mutate config. It intentionally
  uses configured provider endpoints; the stronger question of whether a remote owner may redirect
  stored provider credentials to an arbitrary endpoint is retained as a D2/D4 authority-design
  question because the current owner contract already exposes similarly strong MCP custom-runtime
  authority.
- API settings require a key before binding the managed API service to a non-loopback address.
  Package-installing feature enablement remains gated by local browser or the explicit
  `webui_allow_remote_package_install` policy.
- Image-runtime hot apply catches failures and preserves a restart requirement. Channel feature
  hot reload similarly falls back to restart-required state instead of claiming successful live
  application.
- Remote-access pairing creation requires explicit full-control consent, and most pairing/enable
  controls are local-browser-only. Device revocation is intentionally owner-scoped so an already
  paired owner can revoke a device.
- Settings route tests intentionally exercise explicit config-path isolation and per-gateway OAuth
  flow-object isolation, but the reviewed tests do not establish equivalent isolation for persisted
  provider OAuth credentials, default remote-access authority state or LLM usage storage.

## E02-F16 — P1 conditional — provider OAuth credential authority is shared across explicit gateway configs

**Evidence.** The settings service accepts an explicit gateway config path, but provider OAuth
status/login/logout do not receive a credential-root owner. OpenAI Codex uses a canonical
`~/.nanobot/auth/openai-codex.json` store (unless an environment override is set), GitHub Copilot
uses `~/.nanobot/auth/github-copilot.json`, and xAI uses `get_data_dir()/auth/xai.json`, where
`get_data_dir()` is derived from the process-global config path. `oauth_provider_status()`,
login/reimport/logout and model catalogs call those global authorities directly. The live provider
implementations also fetch Codex/Copilot/xAI tokens from those same stores for actual model calls.
The operation registry exposes provider OAuth login/complete/logout to owner scope, while the
per-gateway OAuth registry isolates only transient flow objects.

**Consequence.** Two explicit gateway/config instances under the same process/user can see, use,
replace or logout the same provider credential even when their ordinary settings files are isolated.
A remote owner attached to one gateway can therefore change credential authority used by another
gateway, and one gateway can make billed/provider-authorized model calls using credentials that were
established through another config instance.

**Qualification.** This is conditional on treating explicit gateway config paths as independent
instance/security boundaries. The current Codex/Copilot compatibility design deliberately uses
user-home credential files, so final D2/D4 must decide whether provider OAuth identity is intended
to be user-global. Single-instance CLI use is not claimed broken. Environment overrides can create
a separate credential path but are process-wide rather than gateway-scoped.

**Smallest later alternative.** Introduce an explicit credential-profile/root owner in runtime
composition, derived from the active instance/config root unless a documented shared profile is
selected. Pass that owner to settings status/login/logout and provider runtime factories so a
gateway cannot silently inherit another gateway's credential authority.

## E02-F17 — P1 conditional — remote-access owner authority defaults to the process-global instance root

**Evidence.** `settings_remote.owner_paths()` uses configured `state_dir`/`socket_path` when
present, but otherwise falls back to `get_data_dir()/remote-access`; `RemoteAccessStore` and
`remote.composition.owner_socket_path()` use the same process-global fallback. The gateway
composition accepts an explicit `config_path` for settings but does not pass that instance root
into remote-access owner composition. Remote-access tests set explicit `stateDir` and
`socketPath`, so they bypass the default path. Device revocation is an enabled owner-scoped
operation, while local enable/pairing controls also operate on the resolved owner manager.

**Consequence.** With two explicit gateway configs whose remote-access paths are left at defaults,
both can address the same owner socket/admin-token/device store even though their settings files are
separate. One gateway can therefore observe or revoke another instance's paired devices, and local
management on either instance can enable/pair against shared owner authority.

**Qualification.** Conditional on divergent explicit/global config paths and default remote-access
paths. Supplying distinct `state_dir`/`socket_path` avoids the collision. Normal single-instance
CLI startup generally aligns the process-global and gateway config roots.

**Smallest later alternative.** Resolve default remote-access state/socket paths from the same
explicit instance root as `WebUISettingsConfig.path`, and inject that owner into both settings and
gateway/mobile composition. Keep explicit `state_dir`/`socket_path` as overrides.

## E02-F18 — P2 conditional — settings usage accounting is not scoped to the explicit gateway config

**Evidence.** `system_settings_payload()` and `settings_usage_payload()` call
`llm_usage_payload()` with only timezone information. The default usage store path is
`get_data_dir()/llm_usage.sqlite3`, and `record_llm_call()` writes to that same process-global
store. No explicit gateway config/root is passed through settings or runtime usage callbacks.

**Consequence.** Multiple explicit gateway/config instances can merge token/request/provider usage
into one database and expose each other's accounting summaries through the settings/usage surfaces.
The resulting totals and provider breakdowns no longer describe the selected config instance.

**Qualification.** Conditional on multiple logical instances under one user/process-global data
root. If usage is intentionally user-global, this becomes a product-contract/documentation question
rather than a defect; current path-scoped settings semantics do not state that exception.

**Smallest later alternative.** Inject an instance-scoped `LLMUsageStore`/path from runtime
composition and use the same store for recording plus WebUI reads. A separately named shared/global
usage view can be offered explicitly if desired.

## E02-F19 — P2 conditional — a truthy non-boolean remote-access “disable” value enables remote access

**Evidence.** The `/api/settings/remote-access/enable` handler computes
`enabled = bool(body.get("enabled"))` instead of validating a boolean. Therefore JSON values such
as the string `"false"`, a non-empty list or another truthy value are interpreted as `True`;
the handler then calls `manager.set_enabled(True)` and persists `remote_access.enabled=True`.
The reviewed tests cover real boolean `True` but no invalid/non-boolean enable value.

**Consequence.** A malformed or compatibility client attempting to disable remote access with a
truthy non-boolean representation can do the opposite and enable it. The route is local-browser-only
under the reviewed transport, so this is an authenticated/local control-plane correctness defect,
not a remote unauthenticated escalation.

**Qualification.** Conditional on a non-boolean payload. The shipped UI is expected to send a JSON
boolean and is not claimed to trigger this during normal use.

**Smallest later alternative.** Require `type(value) is bool` (or a shared strict boolean parser
with an explicitly documented string contract) before mutating owner/config state.
