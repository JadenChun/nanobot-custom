## Initial architecture observations — not findings

- Browser/mobile bootstrap installs runtime transport before rendering and keeps service-worker
  registration as progressive enhancement. LAN HTTP uses a randomUUID compatibility shim.
- `ClientProvider` keeps the latest token in a ref and exposes a stable `getToken()`; it is a
  UI transport helper, not an authority boundary by itself.
- `NanobotClient` multiplexes chats over one socket but keeps per-chat run generation,
  unsettled-turn identity, canonical-completion fences, side-channel ownership and temporary-chat
  state separate.
- Optimistic client run ownership is reconciled against server `message_accepted` /
  `user_message` facts. If another client wins the run, the local optimistic owner is
  disowned rather than treated as authority.
- HTTP/canonical reconciliation fences completed turn IDs before mutating optimistic run state,
  preventing delayed websocket frames for completed turns from changing newer UI state.
- WebUI mutation requests preserve the exact serialized frame/request ID across reconnect so
  the server can join/replay idempotently. Ordinary message sends use a different
  queued/sent/unknown/accepted lifecycle and are not blindly replayed after a write whose
  disposition is unknown.
- Socket close code 1009 is attributed to a concrete message only when exactly one
  unacknowledged send matches the last written message; otherwise the UI emits an uncorrelated
  size error rather than rolling back several chats.
- Pending inbound events without a mounted chat subscriber are bounded to 2,000 per chat.
- `api.ts` routes HTTP reads with bearer auth and WebUI mutations through the authenticated
  socket transport. Workspace Once/mode/grant flows validate exact server receipts/projections
  (runtime ID, revisions, source/task/path/access facts) before accepting them into UI state.
- `useNanobotStream.ts` keeps streamed answer/reasoning/tool/file-edit phases turn-correlated,
  treats `turn_end` as the definitive lifecycle boundary, and clears optimistic activity at
  explicit recovery boundaries. Upload-first attachment sending falls back to the inline
  envelope after upload failure; M01 must determine ownership/reclamation of any partial
  successful uploads before this can be called a leak.
- `useSessions.ts` uses history lineage/semantic-overlap guards and independent read-version
  fences for workspace access/permission projections; older-page reads cannot rewrite the
  latest-turn lifecycle state.
- `App.tsx` keeps Full-mode activation server-confirmed through prepare/activate receipts and
  uses the authenticated mutation transport for pairing/session/settings operations. A failed
  bootstrap re-auth moves UI state to the auth surface but does not explicitly close the
  already-created client; whether an open socket remains authorized is an E02 server contract
  and is not promoted here.

No authority bypass, duplicate-message defect, or reconnect-loss defect is promoted from this
slice. Server-side WebSocket admission, request-id idempotency and authentication remain E02
contracts and must be reconciled before any U01 security conclusion.

### U01-F01 — P2 — attachment-only queued guidance is skipped by automatic FIFO flush

**Source-established functional queue defect; no data-loss or authority claim.**

Trigger:
1. A turn is actively streaming.
2. The user queues a valid prompt containing one or more ready attachments and no text.
3. The active turn becomes idle. If a later queued item contains text, that later item may also
   exist behind the attachment-only item.

Mechanics:
- `canQueueGuidance` treats attachment-only composer content as queueable.
- `queueGuidancePrompt` explicitly accepts `!text && readyImages.length > 0` and stores the
  encoded attachments.
- `sendQueuedPrompt` manually sends a queued item when it has text **or** attachments.
- The automatic idle transition calls `sendNextQueuedPrompt`, but that function selects:
  `queuedPrompts.find(prompt => prompt.text.trim() && !held...)`.
  It therefore excludes a valid attachment-only item.
- Existing source tests establish the intended behavior that queued guidance auto-sends one item
  at a time in queue order; the image-guidance test covers image + text but there is no
  attachment-only auto-flush case.

Impact:
- An attachment-only queued item can remain stranded after the current run finishes.
- If a later text-bearing queued item exists, auto-flush can skip the earlier attachment-only
  item and send the later item first, violating queue order.
- The attachment is not proven lost: the item remains in the queue and can still be manually
  guided, edited or deleted.

History qualification:
The queued-guidance/second-Enter history already allowed queued image content; later attachment
expansion broadened supported media. Nothing in the bounded history establishes that automatic
flush intentionally excludes attachment-only prompts.

Smallest repair direction for later discussion:
make automatic selection use the same sendability predicate as `sendQueuedPrompt`
(text **or** attachments) and preserve first eligible queue order. Add source tests for an
attachment-only first item and a mixed attachment-only/text queue. No repair is authorized by
this audit.

### U01-F02 — P2 — session asset pagination can append an old session page after switching chats

**Source-established cross-session display/data-integrity race. No cross-user authorization
bypass is claimed.**

Trigger:
1. The generated-assets sheet is open for session A and has a `next` cursor.
2. The user starts `loadMore()` for session A.
3. Before that request resolves, the surrounding `ThreadShell` switches to session B while the
   same `GeneratedAssetsSheet` instance remains mounted/open.
4. B's initial asset fetch/reset occurs, then A's older pagination request resolves later.

Mechanics:
- `useSessionGeneratedAssets` resets `groups/total/next` when `sessionKey` changes.
- Its primary fetch effect has a local `cancelled` fence and therefore ignores an old initial
  request after session change.
- `loadMore`, however, captures the old `sessionKey`/cursor and commits its result with
  `setGroups(current => [...current, ...payload.groups])` without AbortController,
  generation/session identity, or cursor validation.
- `ThreadShell` passes changing `historyKey` as a prop; it does not key/unmount the sheet.
  `GeneratedAssetsSheet` owns its `open` state, so an open sheet can survive the prop change.
- The rendered flat/group views consume the hook's merged `groups` directly, so the stale A page
  becomes visible inside B's session-scoped gallery and its signed link/path actions remain
  available.

Intent/history:
The original generated-assets implementation commit
`90a6e2fcb751f672676f154cc10c4a989877f65e` explicitly records the frontend task
"Abort on close/session change" and acceptance around session-change refetching. Existing
`generated-assets-sheet.test.tsx` covers normal pagination but does not exercise an in-flight
load-more request across a session switch.

Impact:
- Assets from session A may be displayed as if they belong to session B until refresh/reopen.
- A user may open or copy the wrong generated asset/link/path from the contaminated gallery.
- This is same-user cross-session presentation/integrity exposure from current evidence; do not
  claim cross-account access or server authorization failure.

Smallest repair direction for later discussion:
fence every pagination commit by a request generation/session key (or AbortController), and
clear/cancel active load-more work on session change/close. Add a source test where A's
pagination resolves after B's initial page and assert no A group is appended. The all-session
library hook has a related stale-page-after-refresh shape and should share the same request
generation helper if simplification is justified.

**U01-F04 — P2 — Skill-detail mutation completions can corrupt or close a newly selected skill**

close a newly opened B sheet. The server mutation remains targeted at the originally captured A;
the established defect is cross-skill UI state/lifecycle integrity, not a demonstrated
server-authority bypass.

### New provisional finding

**U01-F05 — P2 — Failed sidebar persistence can remain indefinitely optimistic and unsaved**

`useSidebarState.update()` applies every sidebar edit optimistically to `stateRef` and React
state, then places the full snapshot in `pendingPersistenceRef`. `flushPersistence()` sends
`client.setSidebarState(next)`. If that mutation rejects, the catch handler restores `next` to
`pendingPersistenceRef` only when no newer snapshot is queued, but it does not call
`flushPersistenceRef.current()`, schedule a retry, roll back the optimistic state, or surface an
error.

This is reachable without a reconnect: `requestMutation()` rejects an ordinary non-OK
`webui_response` while the socket can remain open, and it can also time out after 20 seconds.
Because the only automatic retry trigger in this hook is a later `open` status event, a failed
save on an otherwise-open connection can remain displayed as if persisted for the rest of the
session. With no subsequent sidebar edit or reconnect, a reload can therefore discard the local
change.

Smallest repair shape for later discussion: classify retryable vs terminal failures, retry
retryable pending snapshots with bounded backoff while still open, and surface or reconcile a
terminal rejection instead of keeping an indefinitely optimistic state.

### New provisional finding

**U01-F06 — P2 — An empty turn can stamp completion metadata onto an older legacy assistant row**

`stampLastAssistantCompletion()` scans backwards for an assistant row but does not stop at a
user-message boundary. When a `turnId` is supplied, it also accepts any assistant whose
`turnId` is absent. The live `turn_end` handler always calls this helper with `completedAt`
and any latency/usage/context metadata.

A new turn is submitted by appending only its user row; no assistant placeholder is created until
assistant/reasoning/activity output arrives. Therefore a failed or otherwise empty turn can reach
`turn_end` with no assistant row after its current user prompt. In a session containing an older
legacy assistant row without `turnId`, the backward scan crosses the current user boundary,
accepts that older row as compatible with the new turn, and overwrites it with the new turn's
completion metadata. This can misattribute latency, usage, round usage, context-window and
completion time in the UI/history projection.

The compatibility rule for an assistant lacking `turnId` is still useful within the current
turn, but it does not require crossing a user boundary. Smallest repair shape for later
discussion: stop the completion scan at the first user row, then apply the existing turn-ID
compatibility only to assistant rows within that current turn.
