## T01-A behavior established

- `Tool` and `Schema` define the local model-facing tool contract, schema-driven coercion/validation,
  structured result/error types and optional turn-context injection.
- The built-in schema DSL is deliberately small; `tool_parameters_schema()` defaults built-in parameter
  objects to `additionalProperties: false`.
- `ToolRegistry` owns exact-name lookup, preparation/coercion/validation, managed-capability admission,
  structured terminal error semantics, receipt filtering and execution-result normalization.
- `ToolLoader.load()` uses the explicit foreground factory for built-ins, then installed
  `nanobot.tools` entry points; it validates plugin scope/enablement/construction/name/schema, checks all
  produced names for collision, and only then mutates the registry.
- External plugins receive a fresh, detached, frozen/slotted data-only context. The context intentionally
  reconstructs the full `ToolsConfig` plus workspace/timezone/sandbox status and withholds foreground
  managers/services.
- Production loop composition creates one shared registry, loads the default tools once, then derives
  per-turn filtered registries and installs the live managed-dispatch guard.

## Provisional findings

### T01-F01 — P2 — generic/external tool schemas can advertise constraints the local validator does not enforce

**Evidence.** `Tool.parameters` is documented as JSON Schema and `Tool.to_schema()` forwards that
schema to the model. `Schema.validate_json_schema_value()`, however, implements a bounded subset
(type/nullability, enum, numeric bounds, string length, object properties/required/additionalProperties,
array items/count) without rejecting unsupported keywords. `resolve_json_schema_type()` also reduces an
arbitrary type list to its first non-null member. Neither `ToolRegistry.register()` nor external plugin
construction asserts that a raw parameter schema belongs to the locally enforced subset; plugin setup
checks only that `to_schema()` is a dict whose schema name matches the produced tool name.

**Consequence.** A raw/external tool may send a valid JSON Schema constraint to the model while local
pre-dispatch validation silently under-enforces it (for example an unsupported constraint), or may locally
interpret a multi-non-null type union more narrowly than the advertised schema. That breaks the advertised
schema/validation equivalence at the generic plugin boundary.

**Qualification.** No shipped built-in defect is claimed here. The built-in schema DSL emits the supported
local vocabulary, and the inspected tests cover that supported subset plus nullable string/null forms. This
finding is about the public/raw/external schema contract.

**Reference check.** Pinned DSH makes the subset explicit and calls `assertSupportedJsonSchema()` at the
registration boundary; its contract states unsupported or misplaced keywords reject instead of being
accepted without enforcement. Pinned Codex likewise finalizes typed tool specs/runtimes before routing;
feature parity is not implied.

### T01-F02 — P2 conditional — loader registration is publication-atomic, not construction-lifetime atomic

**Evidence.** `ToolLoader.load()` first constructs the complete built-in/plugin list and only afterward
checks duplicate names/existing registry collisions and registers the tools. The inspected collision tests
correctly prove that the destination registry remains clean on failure. But `Tool.create()` and external
plugin `create()` have no standard disposer/rollback result, `Tool` has no close/dispose lifecycle
contract, and the loader performs no cleanup for already constructed tools when a later construction,
schema/name check or final collision aborts the load.

**Consequence.** If a tool/plugin constructor acquires a resource, starts a helper, or registers an external
callback during construction, a later setup failure can leave that construction side effect outside the
registry even though registry publication is atomic. The same API has no loader-owned unload contract for
successful installed plugins.

**Qualification.** This is a lifecycle/ownership gap, not evidence that a currently shipped built-in leaks a
resource. T01-A did not inspect every concrete constructor; the risk is concrete for arbitrary in-process
external plugin `create()` implementations because that hook is part of the supported API.

**History/reference check.** Commit `e171362c34242d2e44ca01d0fec28e5ec0f158a9`
("isolate external tool plugin construction") deliberately added the detached plugin context, sanitized
setup stages, reserved names and clean pre-registration collision handling, but no disposer protocol.
Pinned DSH's registry returns an exact unregister/disposer from `register()` and ties registration/executor
selection to scoped effects, providing a useful lifetime contrast.

## Retained observations / final-discussion questions

1. **Installed-plugin trust boundary.** Tests intentionally prove that the detached external context contains
   the full `ToolsConfig`, including image/search credentials and MCP env/header credentials. This is not
   promoted as a security defect: an installed Python plugin is already in-process code. Final D2/D4
   discussion should make the trust model explicit; if plugins are meant to be less than fully trusted,
   narrowing only this context object is not a sandbox.
2. **Mutable definition cache.** `ToolRegistry.get_definitions()` caches and returns the same mutable
   list/dicts. Current inspected runner/provider callers read it or copy before mutation, so no active
   corruption path is promoted. Pinned DSH deep-clones model-facing schemas; revisit only if a later caller
   supplies a mutation path.
3. **Legacy discovery surface.** `ToolLoader.discover()` scans built-in package modules, while production
   `load()` constructs built-ins through the explicit foreground factory. Keep this as a simplification/
   compatibility question until later T01 code establishes whether discovery remains externally relied on.
