## T01-A behavior established

- `Tool` and `Schema` define the local model-facing tool contract, schema-driven coercion/validation,
  structured result/error types and optional turn-context injection.
- The built-in schema DSL is deliberately small; `tool_parameters_schema()` defaults built-in parameter
  objects to `additionalProperties: false`.
- `ToolRegistry` owns exact-name lookup, preparation/coercion/validation, managed-capability admission,
  structured terminal error semantics, receipt filtering and execution-result normalization.
- `ToolLoader.load()` uses the explicit foreground factory for built-ins, then installed
  `nanobot.tools` entry points; it validates plugin scope/enablement/construction/name/schema, checks all
  produced names for collision, and only then mutates the registry.
- External plugins receive a fresh, detached, frozen/slotted data-only context. The context intentionally
  reconstructs the full `ToolsConfig` plus workspace/timezone/sandbox status and withholds foreground
  managers/services.
- Production loop composition creates one shared registry, loads the default tools once, then derives
  per-turn filtered registries and installs the live managed-dispatch guard.

## T01-B behavior established

- `ForegroundAgentManager` owns synchronous planner/worker/reviewer/explorer/crawler role execution,
  per-turn delegation budgets, role-specific tool registries, a shared file-lock registry, lazy read-only
  MCP connection state, and child source/artifact routing.
- Canonical turns receive a fresh `DelegationBudget` at admission. Compatibility-only direct callers use
  task-local ContextVars for the legacy budget/current foreground context, avoiding cross-task sharing.
- Planner/reviewer/explorer registries are rebuilt per role invocation from immutable capability profiles.
  They contain bounded read/search/web/browser/device capabilities plus already-connected read-only MCP
  wrappers where the role permits them. `DelegatedReadOnlyPolicy` rechecks the complete emitted batch and
  cannot be elevated by parent approval.
- Worker delegation is narrower: read/list/write/edit only, no shell/browser/device/web/MCP/message/cron
  or nested delegation. `WriteScope.from_raw()` constrains declared targets to workspace-relative
  paths; write/edit tools enforce those scopes and share the foreground `FileLockRegistry`.
- Canonical foreground roles create direct child source streams. Explicit artifact references are issued
  as invocation-local downward grants from the admitted parent reader, and terminal/handoff metadata is
  retained through `ToolOutcome`.
- `build_foreground_dependencies()` creates one coherent context-manager/resource-policy/file-lock/
  foreground-manager graph. `validate_foreground_dependencies()` rejects split ownership, workspace or
  restriction state before powerful tools are registered.
- Internally constructed foreground managers are owned and closed by `AgentLoop` after active work is
  cancelled/drained; an injected dependency bundle is explicitly not owned by that loop.
- `construct_core_tools()` exposes the foreground `plan_task`, `delegate_task`, `review_work` and
  `explore` capabilities. It deliberately does **not** expose `spawn`.
- `SubagentManager` / `SpawnTool` remain dormant compatibility code: the retained adapter still asks
  `ToolLoader` for `scope="subagent"`, while the current loader deliberately rejects all non-core
  runtime scopes. Tests explicitly require the production registry to exclude `spawn` and
  `spawn_pipeline`; this is retirement scaffolding, not a live production failure.

## Provisional findings

### T01-F01 — P2 — generic/external tool schemas can advertise constraints the local validator does not enforce

**Evidence.** `Tool.parameters` is documented as JSON Schema and `Tool.to_schema()` forwards that
schema to the model. `Schema.validate_json_schema_value()`, however, implements a bounded subset
(type/nullability, enum, numeric bounds, string length, object properties/required/additionalProperties,
array items/count) without rejecting unsupported keywords. `resolve_json_schema_type()` also reduces an
arbitrary type list to its first non-null member. Neither `ToolRegistry.register()` nor external plugin
construction asserts that a raw parameter schema belongs to the locally enforced subset.

T01-B adds a concrete built-in contract example: delegation artifact-reference schemas advertise
`pattern` and `uniqueItems`, neither of which the local generic validator enforces. The downstream
artifact-grant boundary separately parses exact artifact-reference syntax, caps the list at 16 and rejects
duplicates, so no artifact-authority bypass is claimed.

**Consequence.** Raw/external tools can send constraints to the model that local pre-dispatch validation
silently under-enforces, or can locally interpret unsupported unions differently from the advertised
schema. The artifact case demonstrates model/local schema drift even though a later domain boundary
correctly restores the relevant safety checks.

**Qualification.** No artifact delegation escalation is claimed. The built-in schema DSL itself emits the
supported local vocabulary; ad-hoc built-in/raw schemas can additionally contain non-enforced keywords,
and external plugins can supply arbitrary raw parameter schemas.

**Reference check.** Pinned DSH makes its enforced JSON Schema subset explicit and rejects unsupported or
misplaced keywords with `assertSupportedJsonSchema()` at registration. Pinned Codex likewise finalizes
typed tool specs/runtimes before routing; feature parity is not implied.

### T01-F02 — P2 conditional — loader registration is publication-atomic, not construction-lifetime atomic

**Evidence.** `ToolLoader.load()` constructs the complete built-in/plugin list before final collision
checking and registry publication. `Tool.create()` / external plugin `create()` have no standard
disposer result, `Tool` has no generic close/dispose lifecycle contract, and the loader has no rollback
hook for an already constructed tool when a later setup step fails.

**Consequence.** An arbitrary installed plugin that acquires a resource or registers a callback in
`create()` can leave that side effect outside the registry after a later setup failure, despite registry
publication itself remaining atomic.

**Qualification.** T01-B materially narrows this concern for the core foreground graph:
`build_foreground_dependencies()` does not activate external resources; foreground MCP is lazy; ownership
is explicit; and `AgentLoop.aclose()` closes its internally owned foreground manager after draining work.
No shipped foreground constructor leak is claimed. The residual finding remains about the supported
generic/external plugin construction API.

**History/reference check.** Commit `e171362c34242d2e44ca01d0fec28e5ec0f158a9`
isolated external plugin construction and sanitized failures without adding a disposer protocol. Pinned
DSH registration returns an exact unregister/disposer and ties registrations to scoped effects.

### T01-F03 — P2 — concurrent first-use foreground MCP initialization can silently omit configured tools

**Evidence.** `ForegroundAgentManager._connect_read_only_mcp()` treats both “already connected” and
“another task is connecting” as an immediate return. The first caller sets `_mcp_connecting=True` and
awaits `connect_mcp_servers()`; a concurrent caller that enters before completion returns immediately and
then builds its planner/reviewer/explorer registry from the still-empty or incomplete
`_read_only_mcp_tools`. The shared manager can serve different sessions concurrently because loop
admission locks are keyed per session, not globally.

**Consequence.** On process/manager first use, two concurrent foreground read-only delegations can receive
different capabilities despite identical configured MCP state. The losing call silently proceeds without
configured read-only MCP tools; later calls see the completed set. This is nondeterministic capability loss
and reliability drift, not privilege widening.

**Qualification.** The connection helper correctly propagates cancellation and cleans failed connection
state, and the normal loop shutdown drains active turns before closing the owned manager. The finding is
specifically the readiness handoff between concurrent first callers; no targeted test covering that race
was found in the inspected source.

**History/reference check.** The boolean `_mcp_connecting` gate was retained through the migration-era
MCP lifecycle change in `e58230d4dbf0af5788c33fb15b6289e77edb4ab3`; later managed-MCP trust work did
not add a shared readiness wait. Pinned Codex exposes an exact-tool `wait_until_ready` hook, while pinned
DSH couples delegation-tool visibility to provider lifecycle and rechecks provider identity before child
activation. A shared initialization task/future or lock with a double-check would be the smaller ownership
shape to discuss later.

## Retained observations / final-discussion questions

1. **Installed-plugin trust boundary.** The detached external plugin context intentionally contains the full
   `ToolsConfig`, including configured credentials. This is not promoted as a security defect because an
   installed Python plugin is already in-process code; final D2/D4 discussion should state the trust model.
2. **Mutable definition cache.** `ToolRegistry.get_definitions()` caches and returns the same mutable
   list/dicts. Current inspected callers do not establish a mutation path; revisit only if later T01 code
   supplies one.
3. **Legacy discovery / retired spawn surface.** `ToolLoader.discover()` still finds `SpawnTool`, and
   `SpawnTool.create()` remains callable, while production construction never registers it and its real
   subagent loader scope is intentionally closed. Consider whether dormant compatibility code should be
   made non-discoverable, moved behind an explicit legacy adapter or removed after compatibility review.
4. **Dead parallelism spelling.** `_ForegroundTool.supports_parallel_calls=False` is not the `Tool`
   concurrency contract (`concurrency_safe`). Current foreground tools remain sequential anyway because
   the base default is non-read-only/non-concurrency-safe; this is cleanup rather than a behavior defect.
5. **Recoverable budget/scope denials.** Delegation-budget exhaustion and invalid worker scopes return plain
   `"Error: ..."` strings rather than structured terminal errors. Under the current structured-error
   contract that lets the parent model recover and continue; retain as an observability/API-contract
   question rather than promoting it without contrary evidence.
