## A01-A behavior established

- `ProcessCompletionRuntime` journals process ownership before launch, retains captured session route and
  workspace scope, marks interrupted waiting/dispatching work unknown rather than replaying it, and only
  schedules one continuation per process completion.
- The gateway installs this runtime only when `gateway.process_continuations` is enabled; `ExecSessionManager`
  calls `started()` synchronously before spawn and `finished()/cancelled()` synchronously from async process
  lifecycle paths.
- The process journal uses synchronous SQLite opens, transactions and `PRAGMA synchronous=FULL`; those calls
  therefore execute on the event-loop thread at the live caller sites above.
- Sustained-goal state is session metadata with explicit turn-local mutation permission. Goal creation/replacement
  rolls metadata back if session persistence fails; completion/cancel/block revoke mutation permission.
- Goal continuation is bounded to twelve internal continuation slices and only activates after durable
  `goal_state.status == "active"`; hidden continuation inputs are not persisted as ordinary user input.
- The shipped command router still advertises and handles `/goal`, but the explicit core tool manifest contains
  neither `create_goal` nor `update_goal`. The source test for goal tools explicitly asserts they require
  manual registration; no alternate first-party production registration path was found in the inspected tree.
- `CronCompletionProjector` keeps the occurrence ledger as computation authority, writes detached projections
  under descriptor-bound private POSIX paths, fsyncs file/root durability boundaries and refuses to project a
  claimed/uncertain occurrence as success.
- Cron job hooks execute configured argv without a shell, bound verifier output/time, and keep post-delivery/owner
  alert callbacks once-only through `CronCallbackStore`.

## Provisional findings

### A01-F01 — P1 — process-completion persistence performs synchronous SQLite durability work on async gateway/exec paths

**Evidence.** `ProcessCompletionRuntime._connect()`, `get()`, `_save()` and `_transition()` synchronously
open SQLite, execute transactions and close the database with `PRAGMA synchronous=FULL`. Production gateway
composition installs the runtime as the exec-session completion sink. `ExecSessionManager.start()` invokes
`sink.started()` synchronously before spawning the process; its async completion monitor invokes
`sink.finished()` / `sink.cancelled()` synchronously after process settlement. `_continue()` also performs
synchronous journal reads/transitions before and after awaiting the canonical local-trigger turn.

**Consequence.** Enabling process continuations allows filesystem/SQLite latency and lock contention to block the
event-loop thread during process admission, settlement and continuation bookkeeping. This can delay unrelated
gateway work sharing that loop. The current source proves the blocking ownership mismatch; it does not quantify
runtime frequency or latency.

**Qualification.** The journal's effect/recovery semantics are conservative: state is durable before process launch,
interrupted/dispatching work becomes unknown rather than replayed, and unknown effects are retained for inspection.
The finding is responsiveness/ownership, not a durability or duplicate-effect claim. The earlier audit's ~163 ms
contention observation remains historical and is not treated as current runtime evidence.

**Smallest later alternative.** Keep the same state machine and durable-before-launch ordering, but move journal
operations behind one async persistence owner (for example a dedicated worker/task or bounded thread owner with
ordered acknowledgements) so event-loop callers await completion instead of running SQLite directly.

### A01-F02 — P2 — the shipped `/goal` command advertises sustained-goal behavior that default production composition cannot activate

**Evidence.** The built-in command router registers `/goal` and grants turn-local goal mutation permission while
marking the inbound turn `goal_requested`. Durable activation, however, requires `CreateGoalTool` to write
`goal_state.status="active"`; completion/replacement requires `UpdateGoalTool`. The explicit
`construct_core_tools()` manifest registers neither tool. The targeted goal-tool source test explicitly asserts
that the accepted foreground manifest omits both tools and manually registers them only inside the test. No
alternate first-party production registration path was found in the inspected source tree.

**Consequence.** In default product composition, `/goal <task>` can enter an ordinary turn with goal-request
metadata but cannot establish the durable active-goal state required by the bounded continuation policy. The
advertised long-running-goal command therefore degrades to ordinary turn execution rather than the persistent
sustained-goal contract its UI text describes.

**Qualification.** The goal tools themselves remain usable to an SDK/custom composition that explicitly registers
them, and their state/permission mechanics are internally coherent when registered. This is a shipped
capability/registration mismatch, not a defect in the goal-state mutation implementation.

**Smallest later alternative.** Either register the two goal tools in the intended first-party composition when
`/goal` is available, or hide/retire the `/goal` command and sustained-goal runtime guidance from default
product surfaces until an explicit enablement path exists.

## Additional provisional findings

### A01-F03 — P1 — gateway cron polling performs synchronous full-history durable filesystem work on the event loop

**Evidence.** Production `GatewayCron.run()` awaits `CronRuntime.run_timer()`. The timer loop calls
`await self.scheduler.wake_once()` on each poll. Before its first await, `wake_once()` synchronously calls
`SchedulerStore.read()` and `CronOccurrenceStore.inspect_records()`. Scheduler reads default to durable
reproof and execute `os.fsync()` on both the state file and root directory. `inspect_records()` walks every
retained occurrence and calls `_read_record(..., durable=True)`; each record read fsyncs the record and root.
The configured production poll interval defaults to 1 second and may be as low as 50 ms.

**Consequence.** With gateway cron enabled, ordinary timer polling can block the gateway event-loop thread on
filesystem I/O even when no job is due. The work grows with retained occurrence history, so unrelated channel,
gateway and agent tasks sharing that loop can experience increasing latency. The source establishes the ownership
and scaling mismatch; it does not quantify actual storage latency.

**Qualification.** Gateway cron is disabled by default, and the fsync/reproof rules protect important crash and
tamper invariants. The finding is not an argument to weaken pre-effect durability. It is about executing that
durable filesystem work synchronously inside the shared async owner, especially the repeated full-history scan.

**Smallest later alternative.** Keep the same durable proofs, but move blocking ledger work behind one ordered async
persistence owner/bounded worker and avoid re-fsyncing the complete historical occurrence set on every idle poll
when unchanged evidence can be reproved by a narrower owned checkpoint.

### A01-F04 — P1 provisional — append-only scheduler evidence has a finite hard lifetime in the live timer path

**Evidence.** `SchedulerStore` caps scheduler state at 1 MiB, 1,024 cursors, 4,096 classifications and 4,096
trigger requests. `Scheduler._advance()` appends one classification for every claimed/observed timer fire and for
acquisition/new-revision classification. `compare_scheduler_held()` explicitly requires retained classifications
and requests to remain prefix-append-only and preserves immutable cursor evidence. The reviewed live
`Scheduler`/`SchedulerStore` path has no compaction/epoch rollover operation. Once a successor crosses one of
the structural/byte bounds, `_encode()`/`_validate()` rejects publication; the timer exception propagates out of
`GatewayCron.run()` and marks that owner failed.

**Consequence.** A continuously used cron runtime has a finite evidence horizon: at or before the global
classification/state bound, a later otherwise-valid timer advancement can no longer be committed and the gateway
cron owner fails. Dense schedules or many jobs reach the bound sooner. Trigger request history has the same
append-only exhaustion shape for manual/system execution.

**Qualification.** This remains provisional until later A01 maintenance/migration files are read for any explicit
operator rollover/archive path. No such reclamation is present in the live scheduler owner reviewed here, and the
ordinary gateway timer path does not invoke one. The issue is retained evidence lifetime, not occurrence replay or
cursor correctness.

**Smallest later alternative.** Introduce an explicit stopped-owner epoch/checkpoint rollover that preserves a
cryptographic/semantic predecessor anchor plus current cursor/request authority while archiving old proof, or split
unbounded append evidence from the bounded active scheduler snapshot. Do not silently delete history in-place.

  “dormant” module comments in `canonical_execution.py` and `composition.py` are stale documentation, not

  durably complete the occurrence.

- Live gateway composition preflights all frozen delivery destinations before computation and currently admits only
  receipt-capable Telegram delivery. The shared primary `channelMeta` thread id is applied only when a delivery
  destination exactly matches the frozen primary channel/target; additional destinations do not inherit that topic.
- Receipt delivery is conservative: preflight failures mean confirmed-not-sent, permanent channel rejection is
  permanent-not-sent, partial bundles become uncertain, malformed/mismatched receipts propagate into the delivery
  runtime's uncertain/reconciliation-required path, and no automatic resend is performed here.
- Multi-destination delivery claims the latest destination revision one destination at a time in frozen order.
  Ordinary sender exceptions are durably classified by the delivery runtime and represented as content-free
  `UnknownOutcome` while later frozen destinations continue.
- The older `bound_runner.py`/session-bound runner and `delivery.py` message-fanout helpers are compatibility
  surfaces at this pin. The reviewed production gateway composition does not use them; `CronService.write_run_record`

  to `invoking` before external observer code runs, ordinary observer failure becomes `failed`, and cancellation
  deliberately leaves `invoking` for explicit `observed`/`abandoned` reconciliation rather than reinvocation.
- Delivery authority is split cleanly between the durable outbox store and runtime sender adapter. A destination
  must be durably claimed and then durably marked `sending` under a task/PID-bound per-destination send fence
  before channel code receives an immutable request.
- Sender cancellation, timeout, malformed results, partial bundles and arbitrary sender exceptions are all joined
  before the durable attempt is classified. None of those paths permits a late sender success to silently become
  confirmed delivery; uncertain effects become `unknown` and require reconciliation.
- Same-claim concurrent dispatches across runtime adapters sharing one store are coalesced through one store-scoped
  dispatch registry so the sender is invoked once. Reentrant same-claim dispatch is detected and fenced.
- The outbox is one immutable completed-occurrence input plus replayable transition history. Attempts, action IDs,
  request digests, receipts and reconciliation evidence are exact and deterministic; each state transition bumps
  a contiguous record revision and the reader replays the retained history to prove the current destination state.
- Offline delivery reconciliation is explicitly operator-gated. Inspection is existing-only/redacted; imported
  evidence is content-addressed; plans bind exact authority inodes and predecessor revision/action/request identity;
  application requires the exact plan id plus an outcome-specific confirmation literal.
- Interruption recovery never replays an abandoned cron model turn. It requires a uniquely matching claimed
  legacy-fresh occurrence plus matching canonical session/source evidence, archives the interrupted tail under both
  occurrence and session ownership, resets only to the proven prefix, and otherwise leaves a per-job recovery fence.
- Quota recovery is whole-job and narrow: only Codex rate-limit errors with no tools and no explicit sends qualify,
  retry budget is capped at three, `dispatching` becomes `unknown` across restart, and unknown intents require
  stopped-writer operator reconciliation.
- Runtime inspection exposes existing-only occurrence/scheduler evidence without granting compute/delivery
  authority. Occurrence reconciliation requires explicit external evidence plus a stopped scheduler writer.
- Visible-session linking occurs only after a durable completed canonical text occurrence and validates frozen
  route/completion identity before publishing retryable scheduled-run metadata.

### A01-F05 — P2 — completed delivery dispatch entries are retained for the lifetime of the outbox store

**Evidence.** `CronDeliveryRuntime` attaches one shared `_DispatchRegistry` to the exact
`CronDeliveryOutboxStore`. Every new `DeliveryClaim` inserts an `_DispatchEntry` keyed by `id(claim)`;
that entry strongly retains the claim, dispatch task and sender task. The only runtime removal path is a defensive
id-reuse branch when an entry with the same integer key refers to a different claim. The terminal
`dispatch()` `finally` retrieves a finished task exception but does not remove the entry. By contrast,
`CronDeliveryOutboxStore.settle()` explicitly consumes `_issued_claims[id(claim)]` on both success and error,
and reconciliation removes matching issued claims after consuming the predecessor. Source tests establish
same-claim coalescing and retry with a newly issued claim but contain no terminal registry eviction contract.

**Consequence.** A long-lived gateway with successful/retryable cron delivery accumulates one runtime registry
entry per unique delivery attempt. Each retained entry keeps at least the consumed claim and completed task/future
objects reachable for the lifetime of the outbox store. This is process-memory/lifetime growth, not duplicate-send
authority: durable send authority has already been consumed by the store.

**Qualification.** Keeping a completed entry also makes a late same-process call using the exact old claim return
the already-completed dispatch task, which can be viewed as post-acknowledgement idempotence. That behavior does
not require retaining the full claim/task/sender-task graph without bound; a bounded terminal-result cache or
waiter-aware eviction could preserve it. No runtime heap measurement was performed.

**Smallest later alternative.** Remove terminal entries once all coalesced waiters have observed completion, or
replace them with a small bounded/timed immutable result cache keyed by the claim's deterministic action identity.

### A01-F07 — P2 — shipped local-trigger commands queue work that the default gateway never consumes

**Evidence.** `cmd_trigger` is a registered built-in command and creates a `LocalTriggerStore` even when the
agent loop has no injected store, returning a concrete `nanobot trigger <id> "message"` command to the user.
The CLI `trigger` command resolves the workspace and durably enqueues the supplied message. In the production
foreground gateway, `AgentLoop.from_config(...)` is constructed without `local_trigger_store`, and the owned
task list starts config watch, agent, channels, client monitor, optional process completion, optional gateway cron,
health and WebUI tasks—never `run_local_trigger_queue`. Source tests explicitly preserve pending trigger files
across default gateway startup and forbid `claim_deliveries`/`recover_processing_deliveries` from being called.

**Consequence.** The shipped UI/CLI can report a trigger as created and a delivery as “Queued” even though the
normal gateway has no consumer that can advance that delivery to a session turn. Users or local automation can
accumulate apparently accepted work that remains inert indefinitely.

**Qualification.** An embedding/direct-SDK caller can explicitly start `run_local_trigger_queue` and wire
`submit_local_trigger_turn`; the finding is about the default foreground product composition at this pin, not
the impossibility of activating the substrate.

**Smallest later alternative.** Either activate the queue as an explicitly owned gateway feature with the safety
repairs below, or hide/disable `/trigger` and `nanobot trigger` unless a trigger runner is configured and ready.

### A01-F08 — P1 conditional — local-trigger restart recovery can replay an already committed turn and its effects

**Evidence.** A claimed delivery remains as a file under `processing` while `submit_turn(msg)` executes.
Only after that await returns does the runner record success and remove the processing file. A process crash after
the canonical turn commits/returns but before `complete_delivery()` therefore leaves the file behind.
`recover_processing_deliveries()` blindly classifies every surviving processing file as interrupted and moves it
back to the inbox with an incremented attempt count. The coordinator's same-delivery guard exists only in the
current process's `_waiters`; it is removed in `finally`, and replayed bus ingress creates a new `TurnRequest`
without binding `delivery_id` as `run_id`. Session history records the delivery id but does not serve as the
queue settlement authority on this path.

**Consequence.** If the local-trigger runner is activated, one crash window can execute the same automation turn
again after restart. Because the first turn may already have called tools, sent messages or changed external state,
this is an at-least-once side-effect boundary rather than merely duplicate chat history.

**Qualification.** The default foreground gateway does not currently activate this runner, so this is a conditional
activation blocker rather than a live default-gateway exploit. The existing recovery behavior is useful before a
turn has committed; the defect is that the queue cannot distinguish “claimed but never committed” from “committed
but acknowledgement file deletion was lost.”

**Smallest later alternative.** Add durable delivery settlement keyed by `delivery_id` and bind canonical run
identity to it. Recovery should requeue only deliveries whose durable turn outcome is provably absent; committed or
uncertain outcomes need idempotent acknowledgement/reconciliation rather than blind replay.

### A01-F09 — P1 conditional — local-trigger automation can affirm a pending risky-action approval

**Evidence.** Local-trigger ingress is classified as `TurnSource.SYSTEM_COMPAT` and is explicitly excluded from
trusted foreground activity. However, `execute_turn()` calls `ApprovalAdmission.snapshot(key, request.content)`
and later `consume(snapshot)` before source-specific turn processing. `ApprovalAdmission` has no source/sender
parameter: exact strings such as `yes`, `approve`, `go ahead`, `continue`, `do it` and `run it` are
classified affirmative for any caller sharing the pending session/channel alias. On affirmative consumption,
canonical admission sets `context.policy.approval_granted = True` and replaces the automation content with a
message asserting that the user approved the previously blocked risky action. A local trigger is bound to the same
session/channel/chat that created it, so it can intersect that pending approval namespace.

**Consequence.** If local-trigger execution is activated, an automated trigger payload can satisfy a human
risky-action confirmation gate and resume the blocked operation without a trusted foreground approval message.
This collapses the intended distinction between automation and explicit user authorization.

**Qualification.** The default foreground gateway currently leaves the local-trigger runner inactive. Direct SDK
composition or a future gateway activation would expose the boundary immediately. This finding does not require
replayed origin metadata to contain an approval grant; the issue is the source-blind approval text classifier
itself.

**Smallest later alternative.** Approval admission should require a trusted foreground/user provenance token in
addition to text/session matching. Automation sources including `SYSTEM_COMPAT`, cron, recovery and background
continuations should be unable to consume affirmative/negative approval replies.
