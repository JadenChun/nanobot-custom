## Behavior established

- `RemoteAccessStore` is the durable authority for remote enablement, device identities, scopes, revocation, refresh-token hashes, owned-entry metadata and bounded audit records. Authority-changing mutations increment a durable revision; audit-only writes deliberately do not.
- Remote state writes use a process/thread lock plus POSIX file locking when available, atomic replacement, private directory/file modes and fsync. Plaintext refresh credentials are not persisted.
- `TokenService` owns short-lived in-memory access grants and rotating plaintext refresh issuance. Access validation rechecks current durable enablement/device/revocation/scopes. Owner refresh credentials have no idle expiry and remain valid until revoke; legacy chat-only refreshes retain the bounded idle expiry.
- `RemoteAccessOwner` is separate from the agent/gateway. Startup creates/loads remote state, revokes legacy chat-only devices, starts private IPC and optionally starts the loopback HTTP pairing listener.
- Product owner pairing requires full-control consent. QR collection requires the high-entropy nonce and collector secret; manual fallback binds the full HTTPS origin plus the eight-digit code. Both paths still require desktop approval before credentials are issued.
- Pairing state is intentionally in memory while the approved device record and refresh-token hash become durable at `TokenService.issue()`. Pairing collection/approval is serialized and single-winner.
- `OwnerDelegationService` only accepts an enumerated delegated operation, rejects caller-supplied authority assertions, binds the request digest to the owner-derived installation identity, issues a short-lived one-use admission and records the authority revision. `consume()` rechecks the device and exact authority revision.
- `OwnerPermissionAdapter` uses that authorize→consume contract before returning an owner context to the existing gateway workspace permission owner. This preserves the owner process as device authority without making it the workspace/scope grant implementation.
- The private IPC boundary is same-UID Unix-socket authority plus roles; admin operations additionally require the durable admin token. Current source deliberately fails closed on platforms without `SO_PEERCRED`.
- `RemoteAuthorityCeiling` was fully read, but its active caller/use was not established in this substage. Its projection/task semantics remain a caller-tracing obligation for the transport/edge substage rather than a finding here.

## R01-F01 — P2 — pairing can durably commit a device before credential custody is established

**Evidence.** `PairingService.approve()` calls `TokenService.issue()`, which immediately persists the device and hash of the newly generated refresh credential, then keeps the only plaintext access/refresh pair in the in-memory challenge result. `PairingService.poll()` at `remote/pairing.py:444-478` rejects an already delivered result and sets `challenge.delivered = True` at line 465 **before** returning the plaintext credentials to its transport caller.

The IPC path calls `pairing.poll()` at `remote/ipc.py:270`, constructs the response, and only later writes it through `OwnerIPCServer._write()` (`ipc.py:195+`), whose socket write failure is swallowed. The HTTP path similarly calls `pairing.poll()` at `remote/http.py:271` and writes the body only afterward via `http.py:338+`. `RemoteAccessClient._call()` treats a connection loss/timeout as `OwnerUnavailableError`; a retry of `pair_poll` then receives `pairing_consumed`.

There is a second loss window with the same root: pairing challenges/results are memory-only. If the owner restarts after desktop approval/device persistence but before the phone obtains the plaintext pair, the durable device survives while the challenge/result disappears. The stored hash cannot reconstruct the refresh credential, and the same installation cannot simply collect again because it already has a device record.

**Consequence.** A transient owner restart, client disconnect or response-write failure at the approval handoff can leave a durable, apparently paired device for which the phone never obtained usable credentials. Recovery requires local revocation/re-pairing rather than an idempotent retry. This is a pairing reliability/recoverability defect, not an authorization bypass.

**Qualification.** The trigger is a failure after approval has durably created the device but before credential custody is confirmed. Normal successful poll is single-delivery by design. Local owner/admin access can revoke the stranded device, so the issue is recoverable and is classified P2 rather than P1.

**Smallest later alternative.** Make credential handoff explicitly resumable for a short bounded window: retain an approved result until a separate custody acknowledgement (or equivalent idempotent result token) is received, and allow identical authenticated polls to replay that same pair before acknowledgement. Only then consume/delete the plaintext result. Preserve bounded TTL, one installation binding and local revocation.

## Production transport established

- `GatewayEndpoint.process_request()` owns the production mobile front door. HTTP `/mobile/v1/*` requests enter `MobileGatewayEdge.handle()`; WebSocket upgrade at `/mobile/v1/ws` enters `MobileGatewayEdge.authorize_websocket()` and then the shared WebSocket protocol.
- Production typed WebSocket envelopes do **not** call `MobileGatewayEdge.handle_ws_frame()`. `nanobot/channels/websocket/runtime.py:866-867` routes parsed envelopes to `_dispatch_envelope()`, and the active path reaches `WebUICommandRouter.dispatch()` at line 914.
- The production `build_mobile_edge()` composition does not provide `OperationReplayCache` or a legacy `mutation_handler`. Mobile WebUI mutations instead use `WebUICommandRouter` and its durable WebUI replay ledger. The in-memory `OperationReplayCache` is therefore a staging/legacy mechanism in the current composition, not the normal production mutation owner.
- Standard owner GET dispatch is double-bounded: the edge requires an owner identity and downstream `GatewayHTTPHandler.mobile_standard_payload()` re-runs `load_registry().match_read(raw_path)` before dispatch. The initial unrestricted-path concern was rejected.
- Private read/media HTTP responses use `_authorized_delivery()`, which performs an uncached owner validation immediately before returning private bytes. This is a useful revocation fence beyond the edge's short admission cache.
- The operations contract has 111 enabled registry entries: 32 reads, 69 mutations, nine WS-frame entries and one attachment entry. The registry bounds standard feature reads and owner mutation metadata, but it is not the only actual production transport contract because shared WebUI protocol commands coexist with it.

## R01-F02 — P1 — mobile WebSocket commands bypass granted chat/media scopes

**Requirement/current contract.** Remote credentials expose distinct `chat.read`, `chat.write`, `media.read`, `attachment.write`, `device.self.logout` and `owner` scopes. The versioned route table declares `GET /mobile/v1/ws` as requiring `chat.read`, and pairing approval can narrow the offered scopes.

**Reachable call chain.** `GatewayEndpoint.process_request()` accepts the mobile WebSocket at `webui/gateway_endpoint.py:68-74`. `MobileGatewayEdge.authorize_websocket()` at `remote/edge.py:255-265` validates only that the bearer token is current; it does not require `chat.read`. The established connection then enters the ordinary WebSocket loop, whose typed envelopes route from `channels/websocket/runtime.py:866-867` to `WebUICommandRouter.dispatch()`.

The shared command router revalidates current device identity but does not enforce the scope appropriate to the command. At `webui/inbound_commands.py:611` an `attachment` envelope reaches `_handle_attachment_upload()`; line 617 accepts `new_chat`; line 684 accepts `attach`; and line 790 accepts `message`. `_handle_attachment_upload()` at line 524+ commits mobile attachment ingress and registers it to the installation without checking `attachment.write`. Chat attach/hydration and message admission likewise lack `chat.read`/`chat.write` checks.

**Concrete trigger.** Owner pairing can approve a strict subset of the originally offered scopes. `remote/pairing.py:374-376` only requires the approved set to be a subset and, for owner-only pairing, retain `owner`. A locally approved owner record can therefore retain `owner` while omitting `chat.read`, `chat.write` or `attachment.write`. The same structural bypass also applies to any otherwise-valid device whose durable scopes are later reduced.

**Impact.** A credential carrying less authority than a command requires can still create/attach/hydrate chats, submit messages and upload attachments through the production WebSocket protocol. This breaks the server-side scope boundary; UI behavior is not an adequate authorization control. Classified P1 because the defect permits actions outside explicitly granted remote capability scopes.

**Counterevidence/qualification.** Owner pairing defaults to the full owner pairing scope set, so a default owner device does not visibly exceed its grant. HTTP read/media paths do enforce their scopes, and current device state is revalidated during WebSocket command dispatch. Those protections do not repair the missing per-command scope checks. Tests that call `MobileGatewayEdge.handle_ws_frame()` directly exercise a different path and therefore do not establish scope enforcement for production typed envelopes.

**Smallest later alternative.** Define one authoritative mapping from production WebSocket command/action to required remote scope and enforce it immediately after each mobile identity revalidation, before any hydration, attachment staging or mutation admission. Also require `chat.read` during `authorize_websocket()` if the route contract is retained. Reuse that policy from the WebUI router rather than maintaining a second unused `handle_ws_frame()` policy.

## R01-F03 — P2 — refresh rotation can strand an otherwise valid paired device on ambiguous delivery

**Evidence.** `TokenService.refresh()` at `remote/auth.py:118-139` validates the old refresh credential, creates a new pair, persists only the new refresh hash via `store.rotate_refresh()` at line 126, removes all existing access grants at line 129, and then returns the new plaintext pair. Owner IPC `refresh_access` calls this mutation at `remote/ipc.py:297-320` before the IPC response is written. The loopback/private owner listener similarly rotates before its HTTP response is delivered. The mobile edge's refresh wrapper at `remote/edge.py:491-514` cannot make that state change idempotent.

The actual Android client uses the owner listener: `NativeNetworkPlugin.requestRefresh()` sends `/remote/v1/refresh` and only calls `custody.saveRefreshedTokens()` after a successful response. A network/connection failure after server rotation but before client persistence therefore leaves the client holding the invalid old refresh credential and an invalidated old access credential while the owner stores only a hash of the unknown new refresh credential.

**Impact.** Normal long-lived credential refresh can convert a healthy paired device into an unrecoverable remote session. The user must locally revoke and pair again. This is separate from R01-F01 because it occurs after successful enrollment during ordinary credential rotation.

**Counterevidence/qualification.** A successful refresh is intentionally single-use, and tests correctly reject reuse of the old token after success. The defect requires ambiguous response delivery, not an ordinary successful round trip. Local owner recovery remains available, so this is P2 rather than an authority-bypass classification.

**Smallest later alternative.** Make refresh rotation retry-safe: bind a bounded refresh operation identity to the presented credential and retain/replay the resulting credential pair until client custody is acknowledged or a short expiry passes. Do not invalidate the sole recoverable credential before the replacement is safely retrievable.

## R01-F04 — P2 — the versioned mobile route contract contradicts the production edge

**Evidence.** `remote/protocol.py` states that it is the single source of truth for the mobile wire contract. Its ROUTES table declares POST `/mobile/v1/bootstrap` (line 362), POST `/mobile/v1/mutation` (366), POST `/mobile/v1/attachment` (368), POST `/mobile/v1/logout` (370), and GET `/mobile/v1/ws` (371). `mobile/contracts/mobile-v1.json` mirrors those declarations, and `tests/remote/test_protocol.py` asserts exact equality between the JSON route list and ROUTES.

Production `MobileGatewayEdge.handle()` has no HTTP branch for bootstrap, mutation, attachment or logout. Mutation/attachment/logout exist in `handle_ws_frame()`, but production typed mobile WebSocket commands bypass that helper and enter the shared WebUI command router instead. `tests/remote/test_edge.py` explicitly asserts that HTTP `/mobile/v1/logout` returns 404 while the protocol test simultaneously asserts that POST logout is a canonical route.

**Impact.** The published/versioned route registry cannot be used as an accurate runtime API contract. Client generation, parity checks, qualification tooling or future maintenance can conform to the declared contract and still call endpoints production does not serve. Conversely, important production shared-WebUI command semantics are absent from that purported source of truth.

**Qualification.** The current Android application already uses the shared WebSocket/WebUI protocol and `/remote/v1/refresh` for its live flows, so this is not evidence that every current UI action is broken. It is a concrete first-party contract/source-of-truth defect and maintenance/compatibility hazard.

**Smallest later alternative.** Choose the actual supported transport as canonical. Either implement and test every declared HTTP route, or remove obsolete routes and generate/document the shared WebSocket command contract that production really consumes. Runtime parity tests should verify the registry against production route dispatch, not merely JSON against Python constants.

## R01-F05 — P2 — the isolated mobile data server exercises materially different authorization and recovery semantics

**Evidence.** `remote/data_server.py` describes itself as a live qualification data plane that exercises the same owner validation, mobile edge routes, refresh rotation and replay cache. Its POST handler does not match production:
- every POST is first gated by a current bearer token;
- its `/mobile/v1/refresh` branch at line 218 reads the refresh token from JSON after bearer validation, whereas production mobile refresh intentionally requires no current bearer and the Android product uses `/remote/v1/refresh`;
- its HTTP `/mobile/v1/mutation` branch at line 230 invokes `OperationReplayCache.execute(... authorize=_always_true ...)` at line 248 without the production operation-registry, mobile-action or owner-scope admission path;
- it implements HTTP `/mobile/v1/logout` at line 254 although the production edge returns 404 for that route;
- its staging WebSocket handler validates access only on connection and does not reproduce production per-envelope revalidation/command routing.

`tests/remote/test_data_server.py` codifies those staging-specific behaviors by refreshing with the old bearer plus JSON refresh token, submitting HTTP mutation directly and using HTTP logout.

**Impact.** This harness can pass while the production transport has different authorization, recovery and route behavior. Evidence produced from it cannot substantiate production mobile transport/custody claims without separate production-path verification.

**Qualification.** The main emulator qualification script explicitly says it is fixture-only and does not claim transport/custody behavior, and no ordinary product caller of `MobileDataServer` was established. The defect is therefore bounded to staging/qualification fidelity, not a direct production request path.

**Smallest later alternative.** Make the qualification server host the same `GatewayEndpoint`/production mobile-edge and shared WebUI command path, with only side-effect handlers replaced by fixtures. Remove independent route/auth semantics from the staging server.

## R01-F09 — P2 — mobile HTTP completions can arrive before request correlation is armed

**Requirement/current contract.** Both the shared mobile HTTP runtime and the plugin's synchronous helper calls rely on request-ID correlation: after a request is admitted, its one terminal `http_response`/`http_error` event must resolve the matching waiter rather than becoming an unrelated event.

**Native ordering.** `Core.HTTP()` starts `go c.doHTTP(...)` at `mobile/native-network/internal/broker/http.go:73` and only then returns the request ID at line 74. The worker can therefore emit a fast response/error concurrently with the JNI/Kotlin/Capacitor return path.

**Android helper race.** `NativeNetworkPlugin.jsonRequest()` calls `NativeNetwork.http(...)` at `NativeNetworkPlugin.kt:1303`; only after that call returns does it create a future at line 1305 and insert `pendingNative[requestId]` at line 1306. The independent poller can consume the response during that gap. At line 1171 it removes the request ID from `pendingNative`; if no waiter exists yet, line 1177 forwards the event to generic JS listeners. There is no replay into a future that is registered afterward, so `jsonRequest()` waits until its timeout.

**Normal product HTTP has the same ordering.** The public plugin `http()` submits native work at line 699 and returns the ID to Capacitor. In `webui/src/lib/mobile-runtime.ts:180`, `execute()` awaits that bridge return and only installs its JS `pending` entry at line 188. The shared event listener can receive an HTTP completion before line 188; if `pending.get(request_id)` is empty, the event is fanned out but not retained for later correlation.

**Additional lifecycle gap.** On Android-helper timeout, `jsonRequest()` only removes `pendingNative` in its `finally`; it does not cancel the native request. `stopInternal()` also cancels the poller/native core without explicitly failing existing `pendingNative` futures. Those callers can therefore wait for the full helper timeout after a transport restart/logout, and a late completion can surface only as an unrelated generic event.

**Concrete trigger.** A sufficiently fast Tailscale/local response or immediate transport error can complete within the native-to-JS/Kotlin bridge return window. The poller runs every 20 ms, so there is no source-level ordering barrier guaranteeing registration wins.

**Impact.** Ordinary mobile HTTP can intermittently report a 30-second timeout despite the response having reached the device. Pairing/owner helper calls can similarly fail after successful server processing. For `remote_refresh`, the lost completion can be materially worse: the owner may already have rotated the refresh credential while Android fails to persist the replacement, reproducing the credential-stranding consequence of R01-F03 from a distinct client-local race.

**Counterevidence/qualification.**
- Native HTTP requests are context-bounded and the event queue is bounded.
- The shared JS runtime does issue `transport.cancel(requestId)` after its own timeout.
- Existing Android instrumentation helpers submit a request and only then begin polling serially, so they cannot reproduce a concurrently running poller consuming the event before waiter registration.
- Existing WebUI unit tests use fake transports that return IDs without synchronously emitting a completion.
- The race requires a completion inside a relatively small bridge-registration window; this is why it remains P2 rather than a deterministic outage.

**Smallest later alternative.** Make correlation atomic with admission. Options include allocating/registering the request ID before the worker may emit, retaining unmatched terminal HTTP events in a small bounded request-ID map until the waiter attaches, or adding a native request primitive whose completion is delivered directly to its owning callback/future. Apply the same ordering guarantee to the JS runtime. Transport stop/restart should explicitly fail/cancel all pending helper waiters.

## R01-F10 — P2 — a valid large WebSocket frame can permanently wedge the JNI event pump

**Requirement/current contract.** The Android transport explicitly configures `max_ws_frame_bytes = 37_748_736` at `NativeNetworkPlugin.kt:1250`, matching the project's roughly 36 MiB desktop/mobile WebSocket frame budget. Frames at or below that bound are therefore admitted transport data, not oversized attacks.

**Native event encoding.** The Go WebSocket read loop rejects only frames larger than `MaxWSFrameBytes` and encodes each accepted frame inside a JSON event as base64 (`mobile/native-network/internal/broker/ws.go:182-200`). Base64 expands bytes by roughly one third.

**JNI bottleneck.** `NativeNetwork_pollEvent` first allocates 512 KiB. On `ErrBufferSmall` it retries once with a fixed 12 MiB buffer (`native_network_jni.c:136-152`). If that second buffer is still too small, the negative error is converted to length zero and `copy_bytes()` returns null.

**Head-of-line wedge.** The Go event queue deliberately retains a too-large pending event until a later poll supplies a large enough buffer (`events.go:27-31`). The Kotlin poller treats JNI null as "no event" and simply returns from that scheduled iteration at `NativeNetworkPlugin.kt:1166`. The next iteration supplies the same maximum 12 MiB buffer, receives the same null, and repeats indefinitely. The oversized-but-valid frame remains at the head of the event queue, so later HTTP, node and WebSocket events cannot be delivered through this core.

A raw **9 MiB** frame already expands to 12 MiB of base64 before JSON field overhead, so the practical JNI ceiling is below 9 MiB even though the configured native frame ceiling is about 36 MiB.

**Impact.** A valid server WebSocket frame in the unsupported middle range can freeze the Android event pump until the transport is restarted/app is reopened. Pending HTTP correlations then also time out, and the native event queue can subsequently fill. This is an availability/interoperability defect inside the advertised frame contract, not an authority bypass.

**Counterevidence/qualification.**
- The broker correctly rejects frames above its configured 36 MiB ceiling.
- The Go broker's buffer-retention test proves that a too-small poll should preserve the event for a later larger buffer; the defect is the JNI caller never allocating such a buffer.
- `TestWebSocketAllowsAttachmentSizedFrame` exercises only a 3 MiB echo while its helper uses a 12 MiB poll buffer. The Android WS instrumentation test verifies socket opening but does not send a >12-MiB encoded event through JNI.
- Later media work streams signed media outside the JS event bridge, reducing one source of large events, but the 36 MiB WebSocket contract remains configured.
- A large inbound WS frame is required, so severity remains P2.

**Smallest later alternative.** Make JNI event retrieval size-aware: query/return the required event length, grow up to a single authoritative event maximum, or expose a streaming/chunked event ABI. At minimum the JNI maximum must safely hold the JSON/base64 representation of every frame admitted by `MaxWSFrameBytes`; otherwise lower the admitted frame ceiling to the actual bridge-safe value. Never convert a second `ErrBufferSmall` into an indistinguishable null/no-event result.

## R01-F11 — P2 — Android logcat receives replayable signed-media bearer capabilities

**Requirement/current contract.** WebUI media paths use HMAC-signed `/api/media/<sig>/<payload>` URLs so the browser can retrieve a specific file without exposing arbitrary filesystem reads. Possession of the complete URL is therefore the authorization material for that media route.

**Capability construction.** `nanobot/webui/media_api.py:113-115` base64url-encodes the media-root relative path, computes a truncated HMAC-SHA256 over that payload and returns `/api/media/<sig>/<payload>`. No expiry, nonce or per-request token is included in the signed value. The response is explicitly cacheable for one year as private/immutable.

**Replay semantics.** `serve_signed_media()` at `media_api.py:198+` verifies the supplied HMAC against the payload and then resolves/serves the file. It does not require a separate WebUI API token. `ws_http.py:2177-2190` dispatches a matching `/api/media/<sig>/<payload>` route directly to this signed-media handler, likewise without a separate `check_api_token()` gate.

**Android production path.** Every WebView request passes through `NanobotWebViewClient.shouldInterceptRequest()`, which delegates to `NativeMediaInterceptor`. Once a signed media stream opens successfully, `NativeMediaInterceptor.kt:60-63` executes an unconditional INFO log:
`open ${request.url} status=... cached=...`.
`request.url` contains the complete signature and payload.

**Concrete trigger.** Viewing any signed image/video/media item in the Android WebView causes its replayable media capability to be written to Android logs. The log entry also exposes the encoded relative media path.

**Impact.** Any actor or diagnostic/log collection path that can read that device's logcat and can reach the desktop media endpoint can replay the logged URL to retrieve the referenced private media without possessing the normal WebUI API token. Because the signature itself carries no expiry, replay remains valid while the server-side media signing secret/file remain current. This is a P2 secret/privacy exposure: it requires access to device logs plus network reachability and does not grant broader owner authority.

**Counterevidence/qualification.**
- Android app-private storage and normal modern Android log permissions limit which ordinary apps can read another app's logs.
- The leaked capability is scoped to one media path, not owner APIs or arbitrary filesystem paths.
- The media HMAC is strong and path traversal is separately contained.
- A desktop restart/new `WebUIMediaGateway` secret can invalidate old signatures, so "non-expiring" does not mean permanent across all server lifetimes.
- The native media request itself still uses the current owner access token; the defect is that the logged desktop signed URL can be replayed through the direct signed-media route.

**Smallest later alternative.** Never log the full media URL/capability. Log only coarse fields such as status, cached flag, byte/range information and, if correlation is necessary, a short non-secret digest. As defense in depth, future signed-media capabilities could include an expiry/version component, but removing the credential-bearing URL from logs is the immediate repair.

## R01-F12 — P2 — global native `last_error` storage is unsafe under concurrent Android calls

**Requirement/current contract.** JNI callers use `NativeNetwork.lastError()` immediately after a failing native operation to reject the owning Capacitor call with the corresponding diagnostic. The Android bridge deliberately invokes native operations from multiple threads: a dedicated poll executor, a cached operation executor, Capacitor/plugin calls and WebView media interception.

**Shared mutable state.** `mobile/native-network/cmd/lib/main.go:18-23` declares one process-global `lastErrC *C.char` and `lastErr string`. `setError()` at lines 28-35 writes the Go string, frees the prior C string and replaces `lastErrC`. It does **not** acquire `managerMu` or any error-specific mutex.

**Ineffective read-side lock.** `nanobot_network_last_error()` at `main.go:259-265` acquires `managerMu`, initializes the pointer if needed and returns `lastErrC`. Because `setError()` never takes that mutex, the read-side lock does not serialize against pointer replacement/free.

**JNI use-after-free window.** `native_network_jni.c:169-173` calls `nanobot_network_last_error()`, receives the library-owned pointer, then calls `NewStringUTF()` after the Go function has returned and its mutex is released. Another native call can execute `setError()` in that interval and free the pointer before JNI copies it.

**Writer/writer corruption window.** Two concurrent failing calls can both observe the same non-null `lastErrC` and both execute `C.free()` on it, or one can free/replace while the other is mutating the same global pointer. That creates a native double-free/use-after-free/data-race risk, not merely a stale message.

**Concrete product concurrency.** `NativeNetworkPlugin` has a single-thread scheduled poller plus `Executors.newCachedThreadPool()` for owner/pairing/refresh helpers, and WebView media calls native functions on interception/stream threads. The plugin calls `NativeNetwork.lastError()` after failures in status, HTTP admission, cancel, WebSocket open/send/close/ping, transport start and synchronous helper admission. R01-F10 can also repeatedly drive `ErrBufferSmall` through `setError()` from the poller while another thread handles an unrelated failure.

**Impact.** Concurrent native failures can return the wrong diagnostic to the wrong operation, and the unmanaged C-string lifetime can crash/corrupt the Android process. This is P2 availability/reliability because it requires overlapping error paths; no owner-authority bypass or credential disclosure is established.

**Counterevidence/qualification.**
- The happy path does not touch `last_error`.
- Most UI calls only read it immediately after a nonzero/zero failure return, narrowing the race window.
- The C ABI smoke and Android instrumentation tests exercise `last_error` sequentially; no concurrency test was found.
- Core objects and handle lookup themselves use mutexes; this finding is specifically the separate global diagnostic buffer.
- The ABI documentation already says the returned C string is library-owned and valid only until the next error/stop. That contract is workable serially but cannot be honored safely with concurrent writers unless ownership/serialization is added.

**Smallest later alternative.** Remove the shared raw C-string lifetime. Prefer an error copy API that writes into a caller-owned buffer under one lock, or return per-call error text/status directly. If `last_error` remains, protect **both** `setError()` and reads with a dedicated mutex and ensure JNI copies the bytes while that lock is held; thread-local error storage would preserve operation affinity better.

## R01-F13 — P2 — bounded broker event pressure can silently drop admitted operation completions

**Requirement/current contract.** Once native HTTP/WS admission returns a request/socket ID, the Android/JS runtime relies on terminal events to reconcile what actually happened: `http_response`/`http_error` resolve the request; `ws_closed` tells the browser-like wrapper that the socket is dead.

**Queue behavior.** `events.go:38-45` implements `emit()` as a non-blocking channel send and returns `ErrQueueFull` if the bounded queue is full.

**HTTP admission is only a point-in-time check.** `http.go:57-59` rejects a new request if the channel is already full, but after admission line 73 launches the HTTP worker asynchronously. Other requests, node events and WebSocket frames can fill the queue before that worker completes.

**Terminal result is then discarded.**
- Successful HTTP completion calls `c.emit(...)` at `http.go:141` and ignores the returned error.
- `emitHTTPError()` at lines 160-168 explicitly assigns `_ = c.emit(...)`.
- In both cases `doHTTP()` returns and its deferred `removeRequest(id)` removes the cancellation entry even if no terminal event was delivered.

The JavaScript runtime then waits until its 30-second timeout and tries `transport.cancel(requestId)`; the native request is already absent. Android `jsonRequest()` similarly waits for its helper timeout.

**WebSocket control state has the same terminal-event weakness.** If an inbound frame cannot be queued, `ws.go:195-208` closes the actual native socket and then attempts `ws_error`; `close()` also attempts `ws_closed` at lines 231+, but these emits happen while the same queue is saturated and their results are ignored. The shared `MobileWebSocket` wrapper relies on `ws_closed` to retire a remotely closed socket; without it, it can remain logically open until a later send fails or foreground recovery pings/reopens it.

**Concrete high-value consequences.**
- An owner `remote_device_revoke` POST can succeed server-side but its response event can disappear, leaving the user seeing a timeout despite the revoke having happened.
- An approved pairing poll can consume/deliver the single-winner owner result server-side while the native response event is dropped, amplifying the recovery failure already captured in R01-F01.
- A refresh response can be dropped after server-side rotation, producing the credential-stranding consequence of R01-F03 through a distinct broker-backpressure root cause.

**Trigger.** Queue occupancy is shared across HTTP, node state and WS frames. The default queue holds 128 events while Android polls one event every 20 ms. A burst of completions/frames can therefore fill it after an operation was admitted even though the pre-admission length check passed.

**Impact.** Native and server state can advance while the owning Android/JS caller has no terminal evidence and eventually reports a timeout/stale socket. This is P2 reliability/recovery rather than an authorization bypass.

**Counterevidence/qualification.**
- HTTP requests are rejected immediately if the queue is already full at admission.
- Queue capacity is 128 by default and Android polls continuously, so ordinary low-rate traffic has substantial slack.
- WS read-loop overflow closes the native socket rather than accepting unbounded memory growth.
- Existing `TestBoundedQueuesAndBufferRetention` proves non-blocking overflow and retained oversized-event behavior, while `TestHTTPQueueFull` proves admission rejection when already full. Neither covers the post-admission race where a terminal HTTP/WS event itself is dropped.
- Some WS stale-state cases recover on a later outbound send or foreground ping.
- The finding is distinct from R01-F09: F09 is response arrival before a waiter is registered; F13 is loss inside the broker after admission because the terminal event cannot enter the bounded queue.

**Smallest later alternative.** Terminal request/socket lifecycle events need guaranteed bounded delivery semantics. Options include reserving terminal-event capacity per admitted operation, a separate completion channel/map keyed by request ID, replacing lower-priority stream events to make room for terminal events, or propagating queue-full synchronously while the operation is still cancellable. WS close/error state should likewise have a delivery/reconciliation path that cannot be silently discarded.

## R01-F14 — P2 — the 512 MiB native media-cache budget is enforced only after unbounded single-file writes

**Requirement/current contract.** Native media streaming advertises a bounded on-device cache with `mediaCacheBudget = 512 << 20` at `media.go:30`. The cache lives under the native state directory, which production constructs from Android `context.filesDir/network-state/<installation>`, not the OS-evictable cache directory.

**Write path has no active budget.** For a full 200 response, `OpenMediaStream()` wraps the response in `cachingBody()` at `media.go:107-109`. `cachingBody()` creates a temp file under the media-cache directory and `cacheTee.Read()` writes every consumed response chunk to it at lines 324-330. There is no per-file size check, current-cache accounting or free-space/budget check while writing.

**Budget runs only after EOF.** The cache entry is finalized only when the source reaches EOF. The finalizer fsyncs/closes the complete temp file, renames it into place, writes metadata and only then calls `trimMediaCache()` at line 305. `trimMediaCache()` computes the total and evicts old entries only after the full new object already exists.

**Server signing does not supply a corresponding size cap.** `nanobot/webui/media_api.py` can sign an existing media-root file or stage an arbitrary authorized file without a media-size limit. The signed-media GET path also does not reject the file based on a native-cache-sized ceiling. Images and videos are explicit supported media types.

**Concrete trigger.** Opening/streaming a signed video or other allowed media file larger than the remaining cache budget causes the native temp file to grow past 512 MiB before trimming is possible. A single file larger than 512 MiB is fully written before `trimMediaCache()` can immediately evict it. Multiple concurrent full streams can grow separate temp files at the same time.

**Impact.** Playback can consume substantially more than the claimed cache budget and can drive the app's persistent internal storage to ENOSPC. Other custody/Tailscale/app writes can then fail until the stream closes/finalization removes the failed temp or storage is otherwise recovered. This is P2 local availability/resource exhaustion, not remote authority escalation.

**Counterevidence/qualification.**
- The temp file is removed when a stream closes before successful EOF/finalization.
- Once a cache write itself errors, `cacheTee` stops further cache writes and the finalizer removes the temp file.
- Completed entries are LRU-trimmed after finalization; the defect is transient peak usage and absence of a hard single-stream cap, not permanent intentional growth beyond 512 MiB.
- The trigger requires a sufficiently large signed media response and enough playback/reading to grow the temp file.
- No `mediaCacheBudget`, `OpenMediaStream`, `ReadMediaStream` or cache-trim test exists in the current `broker_test.go`; current Android media qualification uses a tiny fixture.
- Desktop signed-media serving itself may become a separate upstream bottleneck for huge files; that does not create a hard client-side disk bound.

**Smallest later alternative.** Track bytes written by each cache tee plus reserved/in-progress cache bytes. Stop caching and remove the temp file as soon as the per-object or global cache budget would be exceeded, while continuing to stream the response to the WebView. Run trimming/reservation before writing a new entry, not only after EOF.

## R01-F15 — P2 — phone-side Pairing Cancel is not durable and can resume into approval after restart

**Expected UI contract.** While a phone pairing attempt is connecting/waiting, the bootstrap displays a button labeled **Cancel**. Its in-process generation fencing is designed to prevent stale asynchronous pairing work from resurrecting the canceled UI.

**Native collection becomes durable.** In the QR/link pairing path, `NativeNetworkPlugin.pairStart()` collects the pairing offer and then calls `custody.savePendingPairing(...)` before resolving the plugin call. The encrypted custody record retains pairing id, origin and encoded challenge. This persistence was added specifically so process death can resume polling.

**Bootstrap Cancel only clears volatile JS state.** `mobile-bootstrap.js:712-720` handles Cancel by:
- incrementing `generation`,
- stopping timers,
- clearing `lastLink`, `lastManual` and in-memory `pendingSetup`,
- returning the panel to `idle`,
- restarting the deep-link watcher.

It never calls a native operation that clears the encrypted pending pairing, and no cancel/clear-pending pairing operation is exposed by the bootstrap transport.

**Restart automatically resurrects it.** On the next bootstrap, `restorePendingPairing()` at lines 669-691 calls `plugin.pendingPairing()`. The plugin loads the encrypted pending record, decodes it back into `activePairing`, and returns the pairing id/challenge. The bootstrap sets state to waiting and immediately resumes `pairPoll()`.

**The race also exists when Cancel happens before pairStart returns.** Existing generation checks correctly ignore a late `pairStart` result in the browser. They do not cancel the already-running native operation. The native operation can still finish collection and persist `pendingPairing` after the user pressed Cancel, leaving state that the next process launch restores.

**Concrete trigger.**
1. Phone scans/submits a valid owner pairing challenge.
2. Pairing collection succeeds or is still completing.
3. User presses **Cancel** before approval is consumed.
4. The encrypted pending record remains (or is written by the still-running native call).
5. Desktop owner approves that pairing while the phone is no longer polling.
6. Phone process/app is restarted while the pairing remains eligible.
7. Startup restores the canceled pairing, polls automatically and can persist the approved access/refresh credentials without a new phone-side pairing action.

**Impact.** An explicit phone-side cancellation does not reliably withdraw the phone's pending consent. A pairing the phone user canceled can become fully paired on a later launch if the desktop owner approves it. This is P2 consent/state-recovery integrity: the original user did initiate the challenge, owner approval is still required, eligibility is time-bounded and local logout/revoke can recover; it is not an unauthenticated external takeover.

**Counterevidence/qualification.**
- In-process generation fencing is good: late pairStart/pairPoll UI completions after Cancel are ignored.
- Focused WebUI tests explicitly cover those late in-memory completion/rejection cases.
- Those tests use mocked plugins with no encrypted pending-pairing persistence; they therefore do not exercise the state added later by the native pending-pairing feature.
- Successful approval clears pending pairing.
- Corrupt pending pairing is cleared on load.
- Manual-code pairing is not persisted at all, which is the separate R01-F08 recovery defect; F15 concerns the persisted QR/link path.
- Server pairing eligibility/expiry limits the time window.

**History evidence.** The in-process stale-work cancellation fencing landed before the later commit that introduced encrypted pending-pairing restoration. The persistence feature added restart recovery but did not add a corresponding durable Cancel path or update the cancellation tests to model native custody.

**Smallest later alternative.** Add an explicit native `cancelPendingPairing` operation that clears `activePairing` and encrypted pending pairing, and call/await it from Cancel. If server-side collection cancellation is available later, invoke it too; local durable clearing is the minimum requirement so restart cannot resume a canceled attempt. An in-flight `pairStart` also needs a generation/cancellation fence before it persists pending state.

## R01-F16 — P2 — release signing material is exposed to dependency-rich pre-sign build steps

**Requirement/current intent.** The release wrapper comment says it builds/signs/verifies the APK “without committing key material.” Only the Android release-signing phase needs access to the keystore and its password.

**Credential export happens before unrelated builds.**
- `build-release.sh:17-21` enables `set -a` while sourcing the private release environment, exporting every assignment from that file.
- Line 41 explicitly exports `NANOBOT_MOBILE_KEYSTORE`.
- Alias/password/password-file values are already environment variables by contract; `app/build.gradle` reads `NANOBOT_MOBILE_KEYSTORE_PASSWORD` or the password file plus the keystore path/alias.

**Those credentials then flow through all child processes before Gradle signing.**
- line 44 runs `build-native-network.sh`, which executes `go test ./...`, `go vet ./...` and Go build;
- line 45 runs `build-shared-webui.sh`, which executes `bun install --frozen-lockfile` and `bun run build`;
- line 49 runs `bunx cap sync android`;
- only line 54 finally invokes the Gradle release build that actually needs signing material.

Every child inherits the keystore path and either the plaintext password or a readable password-file path. The child runs as the same user that can read the 0600 keystore.

**Concrete consequence.** A compromised/malicious pre-sign build dependency, plugin, test or host tool only needs code execution during those ordinary build steps to read and exfiltrate both the release keystore and its password. Theft of that material can enable signing malicious future APKs with the legitimate app identity.

**Impact.** This materially widens the release-signing trust boundary from Gradle/signing to the entire Go/WebUI/Capacitor build graph. It is retained as P2 because exploitation requires a compromised build-time process/dependency or equivalent code execution on the release host; no current dependency is alleged malicious.

**Counterevidence/qualification.**
- The release env and keystore files themselves are required to be mode 0600.
- Password values are not printed by these scripts.
- Dependency versions are lockfile-pinned, and native code uses Go module checksums.
- Gradle necessarily needs the signing material; the defect is exposure **before** that phase to unrelated tools.
- A same-user attacker with arbitrary filesystem access can already read the 0600 keystore; this finding is specifically about unnecessary exposure to executable third-party/build dependency code that otherwise need not receive signing authority.

**Smallest later alternative.** Build all unsigned/native/shared assets first in an environment with signing variables unset. Scope the keystore path/alias/password only to the final Gradle release invocation (or a separate signing step) using a minimal `env ... ./gradlew ...` command. Do not `set -a` the whole release env across the build graph.

## R01-F17 — P2 — the “pinned” mobile toolchain accepts stale/unverified cached tools and an ambient Bun

**Declared contract.** `bootstrap-toolchain.sh` describes itself as reproducibly installing the pinned mobile toolchain, and `toolchain.lock.json` records exact JDK, Go, Android and Bun versions.

**Existing tools bypass verification.**
- `bootstrap-toolchain.sh:36-39` accepts any executable at `toolchain/jdk21/bin/javac` as “already present,” without version/hash verification.
- lines 52-55 do the same for Go.
- lines 68-71 do the same for uv.
- lines 85-88 do the same for Android cmdline-tools.
- `install_android_sdk()` at line 111 gates the **entire** SDK component install on only `platform-tools/adb` being executable. If adb exists, the script does not verify/install the locked platform, build-tools, emulator, system image, NDK or CMake set.

**Build preflight checks existence, not versions.** `mobile-env.sh:27-39` verifies only executability of javac, Go, adb and emulator. It does not compare versions to `toolchain.lock.json`.

**Bun is recorded but not managed.** The lock records Bun **1.4.2**, but bootstrap does not install it and `mobile_require_toolchain()` does not check it. `build-shared-webui.sh:12-13` runs ambient `bun`; debug/release run ambient `bunx`.

**Concrete trigger/consequence.** Reusing a checkout-local `mobile/toolchain` from an older/newer setup, partially restoring it from cache, or invoking the release build on a host with a different Bun can still pass preflight and produce a release with compiler/package-manager behavior different from the recorded lock. Some missing Android components fail later, but stale compatible versions can silently execute.

**Impact.** Build evidence can claim the frozen source was produced with a pinned/reproducible toolchain when the actual JDK/Go/cmdline-tools/Bun differs. This is P2 release qualification/supply-chain integrity, not a runtime authorization defect.

**Counterevidence/qualification.**
- Fresh JDK/Go/uv/cmdline-tools downloads are digest-checked.
- App Gradle and native build scripts independently pin important Android/NDK/CMake/build-tools version strings; an absent wrong component often causes a hard build failure.
- Package dependency versions are lockfile-frozen.
- The concern is silent reuse of compatible but non-recorded tooling, especially Bun/JDK/Go, rather than arbitrary dependency resolution.

**Smallest later alternative.** Make `mobile_require_toolchain()` verify exact versions/digests against `toolchain.lock.json`; verify every required SDK package, not just adb presence. Install or explicitly locate the locked Bun 1.4.2 inside `mobile/toolchain` and invoke it by absolute path. A cached tool that fails validation should be replaced or fail closed.

## R01-F18 — P2 — Gradle wrapper distribution is not cryptographically pinned

**Current wrapper configuration.** `mobile/android/gradle/wrapper/gradle-wrapper.properties:3` pins the URL path to `gradle-8.14.3-all.zip`, and line 5 enables `validateDistributionUrl=true`.

**Missing integrity field.** The properties contain no `distributionSha256Sum`. `toolchain.lock.json` records only the Gradle version, not an archive digest.

**Production path.** Both debug and release invoke checked-in `./gradlew`. When the Gradle distribution is absent from the local wrapper cache, the wrapper fetches the external distribution from `services.gradle.org` and executes it without comparing the archive to a repository-pinned checksum.

**Concrete consequence.** A compromised upstream distribution/CDN/TLS trust path that can replace the bytes served for that version can inject code into the build. On the release path Gradle legitimately receives the signing material, so a malicious distribution can alter the APK and access signing credentials.

**Impact.** This is P2 build supply-chain integrity. HTTPS, the versioned distribution path and Gradle's URL validation substantially narrow the threat; there is no evidence that the current upstream artifact is compromised.

**Counterevidence/qualification.**
- The wrapper URL is HTTPS and version-specific.
- `validateDistributionUrl` is enabled, but that validates the distribution URL/reachability rather than pinning artifact bytes.
- The wrapper JAR itself is checked into the repository; the finding concerns the downloaded Gradle distribution.
- Maven/Bun/Go dependencies have their own ecosystem integrity mechanisms; this finding is specifically the Gradle runtime archive.

**Smallest later alternative.** Add Gradle's official SHA-256 for 8.14.3 as `distributionSha256Sum=...` and track/update it whenever the Gradle version changes.
