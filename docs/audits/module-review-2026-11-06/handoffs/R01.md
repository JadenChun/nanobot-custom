## Behavior established

- `RemoteAccessStore` is the durable authority for remote enablement, device identities, scopes, revocation, refresh-token hashes, owned-entry metadata and bounded audit records. Authority-changing mutations increment a durable revision; audit-only writes deliberately do not.
- Remote state writes use a process/thread lock plus POSIX file locking when available, atomic replacement, private directory/file modes and fsync. Plaintext refresh credentials are not persisted.
- `TokenService` owns short-lived in-memory access grants and rotating plaintext refresh issuance. Access validation rechecks current durable enablement/device/revocation/scopes. Owner refresh credentials have no idle expiry and remain valid until revoke; legacy chat-only refreshes retain the bounded idle expiry.
- `RemoteAccessOwner` is separate from the agent/gateway. Startup creates/loads remote state, revokes legacy chat-only devices, starts private IPC and optionally starts the loopback HTTP pairing listener.
- Product owner pairing requires full-control consent. QR collection requires the high-entropy nonce and collector secret; manual fallback binds the full HTTPS origin plus the eight-digit code. Both paths still require desktop approval before credentials are issued.
- Pairing state is intentionally in memory while the approved device record and refresh-token hash become durable at `TokenService.issue()`. Pairing collection/approval is serialized and single-winner.
- `OwnerDelegationService` only accepts an enumerated delegated operation, rejects caller-supplied authority assertions, binds the request digest to the owner-derived installation identity, issues a short-lived one-use admission and records the authority revision. `consume()` rechecks the device and exact authority revision.
- `OwnerPermissionAdapter` uses that authorize→consume contract before returning an owner context to the existing gateway workspace permission owner. This preserves the owner process as device authority without making it the workspace/scope grant implementation.
- The private IPC boundary is same-UID Unix-socket authority plus roles; admin operations additionally require the durable admin token. Current source deliberately fails closed on platforms without `SO_PEERCRED`.
- `RemoteAuthorityCeiling` was fully read, but its active caller/use was not established in this substage. Its projection/task semantics remain a caller-tracing obligation for the transport/edge substage rather than a finding here.

## R01-F01 — P2 — pairing can durably commit a device before credential custody is established

**Evidence.** `PairingService.approve()` calls `TokenService.issue()`, which immediately persists the device and hash of the newly generated refresh credential, then keeps the only plaintext access/refresh pair in the in-memory challenge result. `PairingService.poll()` at `remote/pairing.py:444-478` rejects an already delivered result and sets `challenge.delivered = True` at line 465 **before** returning the plaintext credentials to its transport caller.

The IPC path calls `pairing.poll()` at `remote/ipc.py:270`, constructs the response, and only later writes it through `OwnerIPCServer._write()` (`ipc.py:195+`), whose socket write failure is swallowed. The HTTP path similarly calls `pairing.poll()` at `remote/http.py:271` and writes the body only afterward via `http.py:338+`. `RemoteAccessClient._call()` treats a connection loss/timeout as `OwnerUnavailableError`; a retry of `pair_poll` then receives `pairing_consumed`.

There is a second loss window with the same root: pairing challenges/results are memory-only. If the owner restarts after desktop approval/device persistence but before the phone obtains the plaintext pair, the durable device survives while the challenge/result disappears. The stored hash cannot reconstruct the refresh credential, and the same installation cannot simply collect again because it already has a device record.

**Consequence.** A transient owner restart, client disconnect or response-write failure at the approval handoff can leave a durable, apparently paired device for which the phone never obtained usable credentials. Recovery requires local revocation/re-pairing rather than an idempotent retry. This is a pairing reliability/recoverability defect, not an authorization bypass.

**Qualification.** The trigger is a failure after approval has durably created the device but before credential custody is confirmed. Normal successful poll is single-delivery by design. Local owner/admin access can revoke the stranded device, so the issue is recoverable and is classified P2 rather than P1.

**Smallest later alternative.** Make credential handoff explicitly resumable for a short bounded window: retain an approved result until a separate custody acknowledgement (or equivalent idempotent result token) is received, and allow identical authenticated polls to replay that same pair before acknowledgement. Only then consume/delete the plaintext result. Preserve bounded TTL, one installation binding and local revocation.

## Production transport established

- `GatewayEndpoint.process_request()` owns the production mobile front door. HTTP `/mobile/v1/*` requests enter `MobileGatewayEdge.handle()`; WebSocket upgrade at `/mobile/v1/ws` enters `MobileGatewayEdge.authorize_websocket()` and then the shared WebSocket protocol.
- Production typed WebSocket envelopes do **not** call `MobileGatewayEdge.handle_ws_frame()`. `nanobot/channels/websocket/runtime.py:866-867` routes parsed envelopes to `_dispatch_envelope()`, and the active path reaches `WebUICommandRouter.dispatch()` at line 914.
- The production `build_mobile_edge()` composition does not provide `OperationReplayCache` or a legacy `mutation_handler`. Mobile WebUI mutations instead use `WebUICommandRouter` and its durable WebUI replay ledger. The in-memory `OperationReplayCache` is therefore a staging/legacy mechanism in the current composition, not the normal production mutation owner.
- Standard owner GET dispatch is double-bounded: the edge requires an owner identity and downstream `GatewayHTTPHandler.mobile_standard_payload()` re-runs `load_registry().match_read(raw_path)` before dispatch. The initial unrestricted-path concern was rejected.
- Private read/media HTTP responses use `_authorized_delivery()`, which performs an uncached owner validation immediately before returning private bytes. This is a useful revocation fence beyond the edge's short admission cache.
- The operations contract has 111 enabled registry entries: 32 reads, 69 mutations, nine WS-frame entries and one attachment entry. The registry bounds standard feature reads and owner mutation metadata, but it is not the only actual production transport contract because shared WebUI protocol commands coexist with it.

## R01-F02 — P1 — mobile WebSocket commands bypass granted chat/media scopes

**Requirement/current contract.** Remote credentials expose distinct `chat.read`, `chat.write`, `media.read`, `attachment.write`, `device.self.logout` and `owner` scopes. The versioned route table declares `GET /mobile/v1/ws` as requiring `chat.read`, and pairing approval can narrow the offered scopes.

**Reachable call chain.** `GatewayEndpoint.process_request()` accepts the mobile WebSocket at `webui/gateway_endpoint.py:68-74`. `MobileGatewayEdge.authorize_websocket()` at `remote/edge.py:255-265` validates only that the bearer token is current; it does not require `chat.read`. The established connection then enters the ordinary WebSocket loop, whose typed envelopes route from `channels/websocket/runtime.py:866-867` to `WebUICommandRouter.dispatch()`.

The shared command router revalidates current device identity but does not enforce the scope appropriate to the command. At `webui/inbound_commands.py:611` an `attachment` envelope reaches `_handle_attachment_upload()`; line 617 accepts `new_chat`; line 684 accepts `attach`; and line 790 accepts `message`. `_handle_attachment_upload()` at line 524+ commits mobile attachment ingress and registers it to the installation without checking `attachment.write`. Chat attach/hydration and message admission likewise lack `chat.read`/`chat.write` checks.

**Concrete trigger.** Owner pairing can approve a strict subset of the originally offered scopes. `remote/pairing.py:374-376` only requires the approved set to be a subset and, for owner-only pairing, retain `owner`. A locally approved owner record can therefore retain `owner` while omitting `chat.read`, `chat.write` or `attachment.write`. The same structural bypass also applies to any otherwise-valid device whose durable scopes are later reduced.

**Impact.** A credential carrying less authority than a command requires can still create/attach/hydrate chats, submit messages and upload attachments through the production WebSocket protocol. This breaks the server-side scope boundary; UI behavior is not an adequate authorization control. Classified P1 because the defect permits actions outside explicitly granted remote capability scopes.

**Counterevidence/qualification.** Owner pairing defaults to the full owner pairing scope set, so a default owner device does not visibly exceed its grant. HTTP read/media paths do enforce their scopes, and current device state is revalidated during WebSocket command dispatch. Those protections do not repair the missing per-command scope checks. Tests that call `MobileGatewayEdge.handle_ws_frame()` directly exercise a different path and therefore do not establish scope enforcement for production typed envelopes.

**Smallest later alternative.** Define one authoritative mapping from production WebSocket command/action to required remote scope and enforce it immediately after each mobile identity revalidation, before any hydration, attachment staging or mutation admission. Also require `chat.read` during `authorize_websocket()` if the route contract is retained. Reuse that policy from the WebUI router rather than maintaining a second unused `handle_ws_frame()` policy.

## R01-F03 — P2 — refresh rotation can strand an otherwise valid paired device on ambiguous delivery

**Evidence.** `TokenService.refresh()` at `remote/auth.py:118-139` validates the old refresh credential, creates a new pair, persists only the new refresh hash via `store.rotate_refresh()` at line 126, removes all existing access grants at line 129, and then returns the new plaintext pair. Owner IPC `refresh_access` calls this mutation at `remote/ipc.py:297-320` before the IPC response is written. The loopback/private owner listener similarly rotates before its HTTP response is delivered. The mobile edge's refresh wrapper at `remote/edge.py:491-514` cannot make that state change idempotent.

The actual Android client uses the owner listener: `NativeNetworkPlugin.requestRefresh()` sends `/remote/v1/refresh` and only calls `custody.saveRefreshedTokens()` after a successful response. A network/connection failure after server rotation but before client persistence therefore leaves the client holding the invalid old refresh credential and an invalidated old access credential while the owner stores only a hash of the unknown new refresh credential.

**Impact.** Normal long-lived credential refresh can convert a healthy paired device into an unrecoverable remote session. The user must locally revoke and pair again. This is separate from R01-F01 because it occurs after successful enrollment during ordinary credential rotation.

**Counterevidence/qualification.** A successful refresh is intentionally single-use, and tests correctly reject reuse of the old token after success. The defect requires ambiguous response delivery, not an ordinary successful round trip. Local owner recovery remains available, so this is P2 rather than an authority-bypass classification.

**Smallest later alternative.** Make refresh rotation retry-safe: bind a bounded refresh operation identity to the presented credential and retain/replay the resulting credential pair until client custody is acknowledged or a short expiry passes. Do not invalidate the sole recoverable credential before the replacement is safely retrievable.

## R01-F04 — P2 — the versioned mobile route contract contradicts the production edge

**Evidence.** `remote/protocol.py` states that it is the single source of truth for the mobile wire contract. Its ROUTES table declares POST `/mobile/v1/bootstrap` (line 362), POST `/mobile/v1/mutation` (366), POST `/mobile/v1/attachment` (368), POST `/mobile/v1/logout` (370), and GET `/mobile/v1/ws` (371). `mobile/contracts/mobile-v1.json` mirrors those declarations, and `tests/remote/test_protocol.py` asserts exact equality between the JSON route list and ROUTES.

Production `MobileGatewayEdge.handle()` has no HTTP branch for bootstrap, mutation, attachment or logout. Mutation/attachment/logout exist in `handle_ws_frame()`, but production typed mobile WebSocket commands bypass that helper and enter the shared WebUI command router instead. `tests/remote/test_edge.py` explicitly asserts that HTTP `/mobile/v1/logout` returns 404 while the protocol test simultaneously asserts that POST logout is a canonical route.

**Impact.** The published/versioned route registry cannot be used as an accurate runtime API contract. Client generation, parity checks, qualification tooling or future maintenance can conform to the declared contract and still call endpoints production does not serve. Conversely, important production shared-WebUI command semantics are absent from that purported source of truth.

**Qualification.** The current Android application already uses the shared WebSocket/WebUI protocol and `/remote/v1/refresh` for its live flows, so this is not evidence that every current UI action is broken. It is a concrete first-party contract/source-of-truth defect and maintenance/compatibility hazard.

**Smallest later alternative.** Choose the actual supported transport as canonical. Either implement and test every declared HTTP route, or remove obsolete routes and generate/document the shared WebSocket command contract that production really consumes. Runtime parity tests should verify the registry against production route dispatch, not merely JSON against Python constants.

## R01-F05 — P2 — the isolated mobile data server exercises materially different authorization and recovery semantics

**Evidence.** `remote/data_server.py` describes itself as a live qualification data plane that exercises the same owner validation, mobile edge routes, refresh rotation and replay cache. Its POST handler does not match production:
- every POST is first gated by a current bearer token;
- its `/mobile/v1/refresh` branch at line 218 reads the refresh token from JSON after bearer validation, whereas production mobile refresh intentionally requires no current bearer and the Android product uses `/remote/v1/refresh`;
- its HTTP `/mobile/v1/mutation` branch at line 230 invokes `OperationReplayCache.execute(... authorize=_always_true ...)` at line 248 without the production operation-registry, mobile-action or owner-scope admission path;
- it implements HTTP `/mobile/v1/logout` at line 254 although the production edge returns 404 for that route;
- its staging WebSocket handler validates access only on connection and does not reproduce production per-envelope revalidation/command routing.

`tests/remote/test_data_server.py` codifies those staging-specific behaviors by refreshing with the old bearer plus JSON refresh token, submitting HTTP mutation directly and using HTTP logout.

**Impact.** This harness can pass while the production transport has different authorization, recovery and route behavior. Evidence produced from it cannot substantiate production mobile transport/custody claims without separate production-path verification.

**Qualification.** The main emulator qualification script explicitly says it is fixture-only and does not claim transport/custody behavior, and no ordinary product caller of `MobileDataServer` was established. The defect is therefore bounded to staging/qualification fidelity, not a direct production request path.

**Smallest later alternative.** Make the qualification server host the same `GatewayEndpoint`/production mobile-edge and shared WebUI command path, with only side-effect handlers replaced by fixtures. Remove independent route/auth semantics from the staging server.
