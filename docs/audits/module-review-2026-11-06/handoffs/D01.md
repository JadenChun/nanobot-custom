### Architecture observations

- The Python desktop pipe is a strict bounded NDJSON protocol: duplicate keys, non-v1 frames,
  unknown fields/operations and oversized frames are refused with bounded error codes.
- Desktop admission is independently revalidated in the child. Managed desktop mode requires
  loopback gateway/WebSocket listeners, WebUI authentication, non-conflicting ports, provider
  setup and runtime preflight.
- Tauri preserves uncertain-dispatch semantics instead of assuming a timed-out write did not
  happen. Start/stop/status results remain bound to the captured lifecycle handle; quit refuses
  to exit while start/stop disposition is unknown.
- Native shell authority is fail-closed: private runtime/socket directories, kernel singleton
  lock plus session-bus owner verification, generated ACL that denies Tauri commands to the
  remote gateway origin, constrained navigation, and WebUI cleanup confirmation before
  hide/destroy.
- Desktop setup UI mirrors the controller's selection/admission/stop locks and renders paths/status
  through text content; it does not install or update the backend.
- TUI desktop connection resolution validates the selected gateway identity and loopback HTTP/WS
  endpoints before exposing credentials to the client. TUI detach/exit intentionally disconnects
  only the terminal client; the selected Desktop backend remains persistent.

### Provisional findings

**D01-F01 — P2 — Automatic follow-up dequeue can lose a queued prompt when the send fails**

`PromptQueue.takeFollowUp()` destructively shifts the FIFO. `NanobotTui.sendNextFollowUp()`
takes that item first and only then calls `sendPrompt()`. If `client.send()` throws because the
socket has become non-open, `sendPrompt()` marks the composer as “Not sent” but does not put the
already-dequeued queued prompt back into the queue or composer. The user's queued text is therefore
no longer present anywhere actionable; pressing Enter to retry has an empty composer.

This is specifically the automatic follow-up path: direct composer sends retain their composer
content when `client.send()` throws. Smallest repair shape for later discussion: peek and commit
dequeue only after a successful send, or re-enqueue/restore the exact prompt on send failure.

Evidence: `tui/src/prompt-queue.ts:25–27`,
`tui/src/app.ts:1016–1044`, and `tui/src/app.ts:1576–1582`.

**D01-F02 — P2 — Context-panel completion can overwrite a newly switched session**

`openContext()` captures the current chat only as the argument passed to
`fetchSessionContext()`, then unconditionally applies the returned token/context snapshot and
opens the panel after the await. Unlike `openBranch()`, `refreshSessionMetadata()`,
`refreshContextEstimate()`, and older-history loading, it has no chat/generation check before
commit. The TUI remains interactive while the fetch is pending, so a user can open/switch sessions
before the old context response settles. The old session's context summary/tokens can then appear
inside the newly active session and can overwrite the header context estimate.

Smallest repair shape: capture the chat ID/request generation and discard a completion when the
active chat no longer matches.

Evidence: `tui/src/app.ts:2727–2755`; comparison fences at
`tui/src/app.ts:2417–2427`, `2757–2779`, `2781–2797`, and `2816–2848`.
