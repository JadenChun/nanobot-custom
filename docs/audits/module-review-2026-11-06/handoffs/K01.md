## K01-A behavior established

- `ContextBuilder` composes the system prompt from identity/bootstrap files, configured context repositories,
  repository-catalog metadata, memory, managed run-state, always-active skills and a bounded skill summary. Explicit
  `$skill` references are attached only to the fresh user turn as runtime context rather than mutating the system
  prompt or prior history.
- Managed WebUI prompt metadata is intentionally bounded: the saved-root/folder-map section is capped at roughly
  8 KiB, catalog prompt rows cap at 24 entries, and repository discovery caps depth/visited/candidates at
  4/512/32 without following discovered directory symlinks.
- `ResourceAccessPolicy` distinguishes managed mode from ordinary `restrict_to_workspace` mode. Its normal file
  validator enforces workspace confinement in the latter, but prompt/skill loaders do not consistently call that
  validator outside managed mode.
- Context-repo manifests define local context/skill entrypoints, writable/protected/proposal/store policy, target
  repositories, optional execution denial and sync metadata. Invalid manifest objects fail closed rather than
  downgrading to an unrestricted legacy repo.
- Repository catalog storage is bounded/typed, revisioned and fsync-published under a lock. Catalog metadata does
  not itself grant filesystem access; tool list/remember/forget resolve through the file-access owner and managed
  WebUI remember turns into a folder-approval proposal.
- `save_knowledge` requires a catalog entry of kind `knowledge`, confines the destination below its canonical
  repo root, rejects `../.git` escapes and probable credentials, serializes same-file appends, uses the canonical
  writer publication path, and reports local-save vs auto-sync state separately.
- Context-budget governance can reject an irreducibly oversized assembled prompt with
  `ContextWindowExceededError` before provider invocation. That narrows unbounded prompt-source size from a
  provider-overflow claim to local synchronous I/O/memory/availability behavior.

## K01-A provisional findings

### K01-F01 — P1 conditional — prompt/skill loading has confinement gaps outside centralized resource-policy validation

**Evidence.** `ResourceAccessPolicy.validate_path()` explicitly rejects non-managed reads outside the workspace
when `restrict_to_workspace=True`. The prompt loaders do not uniformly use that boundary. In
`ContextBuilder._load_bootstrap_files()`, bootstrap/profile files are read directly and
`_validate_home_prompt_file()` is called only when the separate `managed` flag is true.
`ManagedContextRepo.context_files()` accepts `entrypoints.context` by joining the manifest value to the repo
path without requiring that the resolved file remain under the repo; an absolute path or `../` path can therefore
produce an external file. `ContextBuilder` validates those context files only in managed mode. Likewise
`SkillsLoader._skill_entries_from_dir()` follows normal directory/file resolution, while
`_skill_read_allowed()` immediately returns true whenever `policy.managed_mode` is false; it does not consult
`policy.restrict_to_workspace`. A symlinked workspace/context skill can therefore resolve outside the restricted
root and still be loaded.

**Consequence.** In a non-managed agent configured with `restrict_to_workspace=True`, a workspace/context repo
that contains a crafted symlink or manifest entrypoint can cause an otherwise out-of-scope local file to be read
into the system prompt or explicit/always skill context. That bypasses the file-tool confinement contract and can
send the file contents to the configured model provider.

**Qualification.** Managed WebUI mode is materially stronger: prompt files and non-builtin skill paths are resolved
and validated through the resource policy, so this specific bypass is a non-managed restricted-mode issue.
Unrestricted/full-host configurations also intentionally permit broader OS reads. Exploitation requires control of
a workspace/context-repo symlink or manifest content.

**Smallest later alternative.** Whenever a `ResourceAccessPolicy` exists, resolve every bootstrap, context,
memory/run-state and non-builtin skill file through that policy using the effective turn scope, independent of
`managed_mode`. Separately require manifest context/skill entrypoints to resolve below their owning context repo
unless the schema explicitly declares a different trusted target mechanism.

### K01-F02 — P2 conditional — `save_knowledge` does not enforce the active project's `knowledge_repos` association

**Evidence.** Repository entries have a validated `knowledge_repos` relationship, the catalog prompt exposes
that relationship, and `SaveKnowledgeTool.description` tells the model to use the current project's associated
knowledge repos. `SaveKnowledgeTool.execute()`, however, receives only the requested repository name and checks
that the global catalog entry exists and has `kind == "knowledge"`. It does not resolve the current workspace
scope/project catalog entry and never verifies that the selected knowledge repository appears in that project's
`knowledge_repos` list. The source tests verify filesystem confinement and use a correctly associated project,
but do not assert that an unrelated knowledge repo is rejected.

**Consequence.** When multiple writable knowledge repositories are visible to one agent, a turn in project A can
persist durable notes into project B's knowledge repository if that repository is named directly. With `auto_sync`
enabled this can also publish the misplaced note through that repository's configured sync path. Filesystem
authorization still applies; the defect is project-to-knowledge ownership/integrity, not arbitrary path escape.

**Qualification.** If `knowledge_repos` is intended to be advisory discovery metadata rather than an authority
boundary, this becomes a product-contract/documentation issue. The current tool description and validated
association model make project-scoped enforcement the stronger reading; later K01 instruction/template review may
clarify intent.

**Smallest later alternative.** Bind `save_knowledge` to the effective project/workspace, resolve its catalog
entry, and require the destination repository to be one of that entry's `knowledge_repos`. If global knowledge
writes are intentional, expose them through a separate explicit capability or document the association as
non-authoritative.

## K01-B finding reconciliation

### K01-F03 — P2 — runtime skill discovery does not enforce the shipped skill validation contract before shadowing/activation

**Evidence.** `quick_validate.validate_skill()` and the creator instructions define a concrete runtime package
identity: valid hyphen-case `name`, name equals directory, nonempty <=1024-character `description`, allowed
frontmatter/root layout and (for packaging) no symlinks. `SkillsLoader` already has
`valid_skill_metadata(metadata, name)` implementing the core name/description identity rule, but
`list_skills()`, `load_skill()`, explicit `$skill` resolution and always-skill selection never call it.
Discovery accepts any directory containing `SKILL.md`; workspace entries are added to `seen_names` before
library/plugin/built-in entries, so an invalid local skill can shadow a valid built-in solely by directory name.
Missing/malformed metadata falls back to the directory name as the summary description, while explicit invocation
can still load the full body. Existing loader tests deliberately verify workspace-over-builtin precedence but
contain no invalid-metadata/name-mismatch rejection case.

**Consequence.** A typo, partially initialized skill or malformed local/library skill can silently suppress a valid
built-in/plugin skill of the same name while still appearing selectable/explicitly invokable. The authoring and
packaging tools can report that such a skill is invalid, yet the live runtime accepts it, making capability
availability and triggering depend on whether the skill arrived through packaging versus direct workspace/library
files.

**Qualification.** This is primarily reliability/configuration integrity, not an arbitrary remote-code execution
boundary. Workspace/library precedence is intentional, and K01-F01 separately covers path/symlink confinement.
Users may also intentionally keep compatibility skills that do not meet the newer package contract.

**Smallest later alternative.** Validate identity metadata before a candidate enters `seen_names` or shadows a
lower-precedence skill. Invalid candidates should be omitted with a bounded diagnostic, or accepted only through an
explicit compatibility mode. Reuse `valid_skill_metadata()` or one shared validator so authoring/package/runtime
contracts cannot drift.

### K01-F04 — P2 — the cron skill misdocuments both reminder execution and default timezone semantics

**Evidence.** The skill describes three modes and says a “Reminder” message is “sent directly to user,” but the
`cron` tool exposes no reminder/task mode selector: text jobs are stored as the same payload, and the canonical
gateway path builds the claimed fresh request and calls `execute_silent_cron_turn()` before result settlement and
delivery. The skill also says that omitting `tz` uses “the server's local timezone.” The live tool instead uses
`ctx.timezone`; configuration defaults to manual `UTC`, and only explicit `timezone_mode=auto` calls system
timezone detection. The tool's own runtime description correctly reports its effective configured timezone.

**Consequence.** An agent following the skill can promise stronger semantics than the runtime provides: a reminder
is model-executed rather than a raw direct-send primitive, so its text/output depends on the fresh agent turn and
provider outcome. It can also schedule a timezone-less expression at the wrong civil time if it assumes server
local time while the configured agent timezone is UTC or another manual zone.

**Qualification.** For installations using `timezone_mode=auto`, the timezone statement can happen to match the
server timezone. An agent-executed reminder may also normally echo the intended reminder faithfully; the defect is
the documented contract, not proof of frequent wrong output.

**Smallest later alternative.** Describe all current text jobs as fresh agent turns whose result is delivered to
the originating route, and state that omitted timezone uses the configured agent timezone. If exact raw reminder
delivery is desired, add a distinct runtime payload/mode and test it rather than documenting a mode the tool does
not expose.

### K01-F05 — P2 — the ClawHub skill installs and manages skills in the default workspace instead of the effective agent workspace

**Evidence.** Every ClawHub install/update/list command hardcodes
`--workdir ~/.nanobot/workspace` and calls that path “critical.” Nanobot's workspace is a configurable
`agents.defaults.workspace`; runtime skill discovery uses the effective configured workspace passed to the agent,
not an unconditional home-directory default. The adjacent `update-setup` skill already demonstrates the safer
pattern by using the absolute `<agent-workspace>` emitted in the system prompt. ClawHub also notes that Node/`npx`
is required but declares no `metadata.nanobot.requires.bins` requirement, unlike the GitHub/weather/summarize/tmux

**Consequence.** On a non-default workspace, a requested install can succeed into
`~/.nanobot/workspace/skills` while the active agent watches a different `<agent-workspace>/skills`; restarting
the session then does not activate the skill the user was told was installed. Update/list likewise operate on the
wrong collection and can modify a separate default workspace.

**Qualification.** The instructions work on the default workspace, which remains the standard configuration.
Missing `npx` availability metadata is secondary reliability evidence, not a separate finding.

**Smallest later alternative.** Use the effective `<agent-workspace>` from the system prompt for every ClawHub
workdir and declare `npx` as a binary requirement so the runtime can hide or mark the skill unavailable when Node

### K01-F07 — P2 — mobile testing skills require both platform toolchains even though each supports either platform

**Evidence.** Both \`mobile-app-testing\` and \`mobile-dogfood\` declare
\`metadata.nanobot.requires.bins=["npx","xcrun","adb"]\` while their instructions explicitly support either local
iOS simulators or local Android emulators. \`SkillsLoader._check_requirements()\` applies \`all()\` across the
binary list, and explicit \`$skill\` resolution uses the filtered available-skill set. The underlying
\`AgentDeviceTool\` only resolves \`npx\` itself and dispatches the selected platform to agent-device.

**Consequence.** A valid Android-only host without Xcode/\`xcrun\`, or an iOS-only Mac without Android
\`adb\`, has both mobile skills marked unavailable and cannot explicitly activate them even though the documented
single-platform workflow and wrapper can otherwise be usable. This makes Android support especially misleading on
non-macOS hosts, where \`xcrun\` is normally absent by construction.

**Qualification.** Hosts with Node, Xcode command-line tooling and Android platform tools installed together are
unaffected. This finding concerns skill discovery/activation, not proof that every downstream agent-device command
works on every platform.

**Smallest later alternative.** Declare only the common launcher requirement (\`npx\`) at skill level and let the
selected platform path report its own missing dependency, or extend requirement metadata with an explicit
platform/any-of form so iOS and Android prerequisites are alternatives rather than conjunctive requirements.

### K01-F08 — P1 conditional — video-understanding silently bypasses Nanobot provider routing for semantic frame analysis

**Evidence.** The skill tells the agent to run \`extract_keyframes.py\` as the default entry point, and the script
sets semantic processing on unless \`--no-semantic\` is supplied. When \`OPENAI_API_KEY\` exists, it imports
\`OpenAI\`, creates \`OpenAI(api_key=api_key)\`, base64-encodes sampled local frames and calls
\`client.chat.completions.create(model=semantic_model,...)\`; the default semantic model is
\`gpt-5.4-mini\`. It never calls Nanobot's provider factory. The normal provider path resolves the configured
provider/model, API base, proxy, fallback chain and \`ProviderPolicy\` before constructing a client.

**Consequence.** A user running Nanobot on a local, Anthropic, Azure, proxied or otherwise non-OpenAI route can
still have local video frames transmitted to OpenAI merely because \`OPENAI_API_KEY\` is present in the process
environment. That secondary request also sits outside the configured provider-policy/request-accounting path and
can incur model use that is not governed by the active Nanobot route. Semantic-call failures are swallowed into
the fallback storyboard, so the caller may not learn that the secondary provider path was attempted.

**Qualification.** No external semantic request occurs when \`OPENAI_API_KEY\` is absent, the SDK cannot import,
\`--no-semantic\` is used, or the call fails before dispatch. If the active user-selected route is already OpenAI
and external frame analysis is expected, the provider-surprise aspect is smaller; the hardcoded out-of-band route
still remains architecturally separate.

**Smallest later alternative.** Keep the extractor local to FFmpeg/OCR/frame selection and let the already active
Nanobot model inspect the selected frames, or inject a host-owned semantic callback/provider resolved through the
normal configured provider path. Do not make a second provider call from the standalone skill script merely
because an environment key exists.

### K01-F09 — P2 — webapp-testing recommends a caller-supplied CDP mode that the live browser wrapper always blocks

**Evidence.** The skill says that when the user wants an existing Chrome session, the agent should prefer
\`--auto-connect\` or \`--cdp\`. \`AgentBrowserTool\` classifies \`--cdp\` as a configuration-owned option and
returns \`policy_blocked\` before launching agent-browser whenever the caller supplies it. The wrapper already
injects its configured CDP URL automatically when shared-browser attachment is enabled.

**Consequence.** Following the shipped skill literally can produce a deterministic policy failure on one of its
recommended attachment paths, wasting a turn/retry and misrepresenting which browser-session controls the model
actually owns.

**Qualification.** This does not block browser testing generally: ordinary isolated operation, configured shared
attachment and potentially \`--auto-connect\` remain separate paths. Upstream \`--auto-connect\` authority semantics
were not independently pinned in this source-only slice.

**Smallest later alternative.** Remove caller-supplied \`--cdp\` from the skill and document that CDP/session/pin
configuration is operator-owned and automatically applied by the wrapper. Reconcile \`--auto-connect\` separately
with that same authority invariant before recommending it as an attachment override.

### K01-F10 — P2 conditional — non-positive video max-gap values can spin forever before frame capping

**Evidence.** \`--max-gap-seconds\` is parsed as an unconstrained float. \`_add_gap_frames()\` loops while the
current gap is greater than \`max_gap_seconds\` and advances \`prev_time\` by exactly \`max_gap_seconds\`. At zero,
\`prev_time\` never advances; at a negative value it moves backward, so any ordinary positive gap keeps the loop
true indefinitely. \`_cap_events()\` is reached only after this loop, so \`--max-frames\` cannot bound the failure.

**Consequence.** A user or agent supplying \`--max-gap-seconds 0\` or a negative value can turn the bundled
extractor into a CPU-bound non-terminating process until an outer command timeout/cancellation intervenes, with no
storyboard produced.

**Qualification.** The default value is \`6.0\`, so ordinary documented use is safe. This requires an explicit
non-positive override; it is a robustness/input-validation defect rather than a default-path outage.

**Smallest later alternative.** Reject non-positive max-gap values at argument parsing (and preferably validate
the other numeric extraction parameters coherently) before any FFmpeg or event-selection work begins.

### K01-F11 — P2 — live prompt guidance advertises retired search/edit tools absent from the default registry

**Evidence.** The always-rendered \`agent/identity.md\` tells the model to search the history log with the built-in
\`grep\` tool. The always-rendered \`agent/tool_contract.md\` directs discovery through \`find_files\` or
\`list_dir\`, content search through \`grep\`, and makes \`apply_patch\` the default code-editing path including a
\`dry_run\` mode. The memory skill repeats concrete \`grep\` calls. The pinned
\`construct_core_tools()\` manifest registers \`read_file\`, \`write_file\`, \`edit_file\`, \`list_dir\` and the
other current capabilities but not \`grep\`, \`find_files\` or \`apply_patch\`. T01 independently traced the
explicit-factory migration that retired the legacy grep/find owner and dropped \`apply_patch\`.

**Consequence.** In default production composition, the model is instructed to emit tool calls that do not exist.
The history-search workflow is especially direct: the system prompt supplies the history path and then tells the
model to use a missing built-in search tool. Calls can fail through the unknown-tool path and consume recovery
turns, or the model can fall back to broader/less suitable mechanisms despite the prompt claiming a narrower
first-party capability.

**Qualification.** An optional installed plugin could theoretically provide a compatible name in a customized
deployment; this finding is about the shipped default registry. \`list_dir\`, \`read_file\` and other supported
tools remain available, so this is capability/prompt integrity rather than loss of all filesystem access. The
\`apply_patch\` portion cross-references **T01-F10** and should be counted once during integrated review; the novel
K01 evidence is the live prompt/skill contract and the missing \`grep\`/\`find_files\` workflow.

**Smallest later alternative.** Derive tool-specific prompt guidance from the actual admitted registry, or restore
the intended capabilities. Remove retired names from unconditional system text and give history search one
currently registered, bounded search capability.

### K01-F12 — P1 conditional — degraded compaction can elevate raw transcript/tool text into the future system prompt

**Evidence.** \`MemoryArchiver.archive()\` calls \`raw_fallback()\` on provider exception, incomplete/error output,
tool calls or empty summary. The fallback builds a bounded \`[RAW]\` checkpoint from
\`public_history_messages(source_messages)\`; that helper removes trusted runtime-context suffixes but leaves
ordinary user and tool-result contents intact. The compaction source tests explicitly assert that a failed second
archive stores the combined previous checkpoint plus \`[Newly archived raw context]\` in
\`metadata["_last_summary"]["text"]\`. On the next normal turn, \`ContextBuilder.build_system_prompt()\` appends
that text verbatim under \`[Archived Context Summary]\` inside the system message, after the live tool/skill
instructions. There is no typed lower-authority message boundary or an instruction saying raw archived text is
quoted/untrusted data.

**Consequence.** If an archived user message or external/tool result contains imperative prompt-injection text, an
otherwise recoverable compaction failure can persist that text into later requests at system-message authority.
That can make stale or adversarial data compete with current user intent and system policy long after the original
tool result/user turn was archived. Tool admission/policy still constrains actual side effects; this is an
instruction-authority escalation, not proof of automatic command execution.

**Qualification.** The normal successful summarizer path can rewrite the evidence into a compact checkpoint and is
not the specific trigger. Exploitation requires a raw-fallback condition plus instruction-like content in the
archived chunk. The visible \`[RAW]\`/section labels may help a capable model infer data semantics, but they are not
an authority-preserving message boundary.

**Smallest later alternative.** Never splice raw fallback text into the system instruction body. Preserve degraded
evidence as a lower-authority user/data message or typed checkpoint whose renderer quotes/delimits each role and
explicitly states that archived raw content is evidence, not instructions. Keep the bounded fallback and recovery
semantics while preserving source-message authority.

### K01-F13 — P1 conditional — Dream can persist skill instructions outside its own audit and restore boundary

**Evidence.** \`agent/dream.md\` explicitly directs Dream to create or merge reusable
\`skills/<name>/SKILL.md\` workflows, and \`MemoryStore.build_dream_tools()\` gives write/edit/apply-patch tools an
\`allowed_dir\` of the workspace \`skills/\` tree. The source suite explicitly asserts
\`test_dream_can_write_workspace_skills\`. However, Dream's Git owner tracks only \`SOUL.md\`, \`USER.md\`,
\`memory/MEMORY.md\` and cursor bookkeeping; \`_DREAM_CONTENT_PATHS\` likewise excludes skills.
\`dream_content_diff()\`, \`GitStore.auto_commit()\` and \`GitStore.revert()\` therefore omit skill edits.
\`cmd_dream\` advances the cursor after normal completion and reports "no memory changes" when that narrowed diff is
empty. The Dream prompt simultaneously claims that \`/dream-log\` is derived from the real file diff and that
unconfirmed edit claims will be absent from the durable audit record.

**Consequence.** A manual Dream run, or a periodic Dream run when enabled, can make persistent behavior-changing
skill edits that are invisible to Nanobot's Dream change log and cannot be undone with \`/dream-restore\`. A
skill-only run can be reported as having no memory changes even though an instruction file changed, and the
processed history cursor can advance so the same source batch will not naturally be reconsidered.

**Qualification.** Periodic Dream is disabled by default, but manual \`/dream\` remains a first-party path and
enabling scheduled Dream makes the same behavior background-capable. An independent outer VCS may happen to record
the workspace, but that does not satisfy the product's own Dream log/restore contract. A new skill is not
automatically equivalent to code execution; its later influence depends on discovery/activation and is separately
subject to the skill-loader findings.

**Smallest later alternative.** Choose one owner. Either remove skill mutation from Dream and keep Dream strictly
inside its audited memory files, or expand the Dream transaction/audit/restore boundary to include exactly the
skill paths it is authorized to change, with those diffs included before cursor advancement and user-facing
success/no-change reporting.
