## K01-A behavior established

- `ContextBuilder` composes the system prompt from identity/bootstrap files, configured context repositories,
  repository-catalog metadata, memory, managed run-state, always-active skills and a bounded skill summary. Explicit
  `$skill` references are attached only to the fresh user turn as runtime context rather than mutating the system
  prompt or prior history.
- Managed WebUI prompt metadata is intentionally bounded: the saved-root/folder-map section is capped at roughly
  8 KiB, catalog prompt rows cap at 24 entries, and repository discovery caps depth/visited/candidates at
  4/512/32 without following discovered directory symlinks.
- `ResourceAccessPolicy` distinguishes managed mode from ordinary `restrict_to_workspace` mode. Its normal file
  validator enforces workspace confinement in the latter, but prompt/skill loaders do not consistently call that
  validator outside managed mode.
- Context-repo manifests define local context/skill entrypoints, writable/protected/proposal/store policy, target
  repositories, optional execution denial and sync metadata. Invalid manifest objects fail closed rather than
  downgrading to an unrestricted legacy repo.
- Repository catalog storage is bounded/typed, revisioned and fsync-published under a lock. Catalog metadata does
  not itself grant filesystem access; tool list/remember/forget resolve through the file-access owner and managed
  WebUI remember turns into a folder-approval proposal.
- `save_knowledge` requires a catalog entry of kind `knowledge`, confines the destination below its canonical
  repo root, rejects `../.git` escapes and probable credentials, serializes same-file appends, uses the canonical
  writer publication path, and reports local-save vs auto-sync state separately.
- Context-budget governance can reject an irreducibly oversized assembled prompt with
  `ContextWindowExceededError` before provider invocation. That narrows unbounded prompt-source size from a
  provider-overflow claim to local synchronous I/O/memory/availability behavior.

## K01-A provisional findings

### K01-F01 — P1 conditional — non-managed prompt/skill loading can bypass `restrict_to_workspace`

**Evidence.** `ResourceAccessPolicy.validate_path()` explicitly rejects non-managed reads outside the workspace
when `restrict_to_workspace=True`. The prompt loaders do not uniformly use that boundary. In
`ContextBuilder._load_bootstrap_files()`, bootstrap/profile files are read directly and
`_validate_home_prompt_file()` is called only when the separate `managed` flag is true.
`ManagedContextRepo.context_files()` accepts `entrypoints.context` by joining the manifest value to the repo
path without requiring that the resolved file remain under the repo; an absolute path or `../` path can therefore
produce an external file. `ContextBuilder` validates those context files only in managed mode. Likewise
`SkillsLoader._skill_entries_from_dir()` follows normal directory/file resolution, while
`_skill_read_allowed()` immediately returns true whenever `policy.managed_mode` is false; it does not consult
`policy.restrict_to_workspace`. A symlinked workspace/context skill can therefore resolve outside the restricted
root and still be loaded.

**Consequence.** In a non-managed agent configured with `restrict_to_workspace=True`, a workspace/context repo
that contains a crafted symlink or manifest entrypoint can cause an otherwise out-of-scope local file to be read
into the system prompt or explicit/always skill context. That bypasses the file-tool confinement contract and can
send the file contents to the configured model provider.

**Qualification.** Managed WebUI mode is materially stronger: prompt files and non-builtin skill paths are resolved
and validated through the resource policy, so this specific bypass is a non-managed restricted-mode issue.
Unrestricted/full-host configurations also intentionally permit broader OS reads. Exploitation requires control of
a workspace/context-repo symlink or manifest content.

**Smallest later alternative.** Whenever a `ResourceAccessPolicy` exists, resolve every bootstrap, context,
memory/run-state and non-builtin skill file through that policy using the effective turn scope, independent of
`managed_mode`. Separately require manifest context/skill entrypoints to resolve below their owning context repo
unless the schema explicitly declares a different trusted target mechanism.

### K01-F02 — P2 conditional — `save_knowledge` does not enforce the active project's `knowledge_repos` association

**Evidence.** Repository entries have a validated `knowledge_repos` relationship, the catalog prompt exposes
that relationship, and `SaveKnowledgeTool.description` tells the model to use the current project's associated
knowledge repos. `SaveKnowledgeTool.execute()`, however, receives only the requested repository name and checks
that the global catalog entry exists and has `kind == "knowledge"`. It does not resolve the current workspace
scope/project catalog entry and never verifies that the selected knowledge repository appears in that project's
`knowledge_repos` list. The source tests verify filesystem confinement and use a correctly associated project,
but do not assert that an unrelated knowledge repo is rejected.

**Consequence.** When multiple writable knowledge repositories are visible to one agent, a turn in project A can
persist durable notes into project B's knowledge repository if that repository is named directly. With `auto_sync`
enabled this can also publish the misplaced note through that repository's configured sync path. Filesystem
authorization still applies; the defect is project-to-knowledge ownership/integrity, not arbitrary path escape.

**Qualification.** If `knowledge_repos` is intended to be advisory discovery metadata rather than an authority
boundary, this becomes a product-contract/documentation issue. The current tool description and validated
association model make project-scoped enforcement the stronger reading; later K01 instruction/template review may
clarify intent.

**Smallest later alternative.** Bind `save_knowledge` to the effective project/workspace, resolve its catalog
entry, and require the destination repository to be one of that entry's `knowledge_repos`. If global knowledge
writes are intentional, expose them through a separate explicit capability or document the association as
non-authoritative.

## K01-B finding reconciliation

### K01-F03 — P2 — runtime skill discovery does not enforce the shipped skill validation contract before shadowing/activation

**Evidence.** `quick_validate.validate_skill()` and the creator instructions define a concrete runtime package
identity: valid hyphen-case `name`, name equals directory, nonempty <=1024-character `description`, allowed
frontmatter/root layout and (for packaging) no symlinks. `SkillsLoader` already has
`valid_skill_metadata(metadata, name)` implementing the core name/description identity rule, but
`list_skills()`, `load_skill()`, explicit `$skill` resolution and always-skill selection never call it.
Discovery accepts any directory containing `SKILL.md`; workspace entries are added to `seen_names` before
library/plugin/built-in entries, so an invalid local skill can shadow a valid built-in solely by directory name.
Missing/malformed metadata falls back to the directory name as the summary description, while explicit invocation
can still load the full body. Existing loader tests deliberately verify workspace-over-builtin precedence but
contain no invalid-metadata/name-mismatch rejection case.

**Consequence.** A typo, partially initialized skill or malformed local/library skill can silently suppress a valid
built-in/plugin skill of the same name while still appearing selectable/explicitly invokable. The authoring and
packaging tools can report that such a skill is invalid, yet the live runtime accepts it, making capability
availability and triggering depend on whether the skill arrived through packaging versus direct workspace/library
files.

**Qualification.** This is primarily reliability/configuration integrity, not an arbitrary remote-code execution
boundary. Workspace/library precedence is intentional, and K01-F01 separately covers path/symlink confinement.
Users may also intentionally keep compatibility skills that do not meet the newer package contract.

**Smallest later alternative.** Validate identity metadata before a candidate enters `seen_names` or shadows a
lower-precedence skill. Invalid candidates should be omitted with a bounded diagnostic, or accepted only through an
explicit compatibility mode. Reuse `valid_skill_metadata()` or one shared validator so authoring/package/runtime
contracts cannot drift.

### K01-F04 — P2 — the cron skill misdocuments both reminder execution and default timezone semantics

**Evidence.** The skill describes three modes and says a “Reminder” message is “sent directly to user,” but the
`cron` tool exposes no reminder/task mode selector: text jobs are stored as the same payload, and the canonical
gateway path builds the claimed fresh request and calls `execute_silent_cron_turn()` before result settlement and
delivery. The skill also says that omitting `tz` uses “the server's local timezone.” The live tool instead uses
`ctx.timezone`; configuration defaults to manual `UTC`, and only explicit `timezone_mode=auto` calls system
timezone detection. The tool's own runtime description correctly reports its effective configured timezone.

**Consequence.** An agent following the skill can promise stronger semantics than the runtime provides: a reminder
is model-executed rather than a raw direct-send primitive, so its text/output depends on the fresh agent turn and
provider outcome. It can also schedule a timezone-less expression at the wrong civil time if it assumes server
local time while the configured agent timezone is UTC or another manual zone.

**Qualification.** For installations using `timezone_mode=auto`, the timezone statement can happen to match the
server timezone. An agent-executed reminder may also normally echo the intended reminder faithfully; the defect is
the documented contract, not proof of frequent wrong output.

**Smallest later alternative.** Describe all current text jobs as fresh agent turns whose result is delivered to
the originating route, and state that omitted timezone uses the configured agent timezone. If exact raw reminder
delivery is desired, add a distinct runtime payload/mode and test it rather than documenting a mode the tool does
not expose.

### K01-F05 — P2 — the ClawHub skill installs and manages skills in the default workspace instead of the effective agent workspace

**Evidence.** Every ClawHub install/update/list command hardcodes
`--workdir ~/.nanobot/workspace` and calls that path “critical.” Nanobot's workspace is a configurable
`agents.defaults.workspace`; runtime skill discovery uses the effective configured workspace passed to the agent,
not an unconditional home-directory default. The adjacent `update-setup` skill already demonstrates the safer
pattern by using the absolute `<agent-workspace>` emitted in the system prompt. ClawHub also notes that Node/`npx`
is required but declares no `metadata.nanobot.requires.bins` requirement, unlike the GitHub/weather/summarize/tmux
skills.

**Consequence.** On a non-default workspace, a requested install can succeed into
`~/.nanobot/workspace/skills` while the active agent watches a different `<agent-workspace>/skills`; restarting
the session then does not activate the skill the user was told was installed. Update/list likewise operate on the
wrong collection and can modify a separate default workspace.

**Qualification.** The instructions work on the default workspace, which remains the standard configuration.
Missing `npx` availability metadata is secondary reliability evidence, not a separate finding.

**Smallest later alternative.** Use the effective `<agent-workspace>` from the system prompt for every ClawHub
workdir and declare `npx` as a binary requirement so the runtime can hide or mark the skill unavailable when Node

### K01-F06 — P1 conditional — the tmux skill recommends launching Codex with its approvals and sandbox disabled

**Evidence.** The tmux skill's coding-agent example launches
`codex --yolo 'Fix bug X'` and says Codex needs `--yolo` or `--full-auto` for non-interactive fixes. At the
pinned Codex reference, `--yolo` is the alias of
`--dangerously-bypass-approvals-and-sandbox`; Codex documents it as skipping all confirmation prompts and
executing commands without sandboxing, “EXTREMELY DANGEROUS” and intended solely when the environment is
externally sandboxed. Nanobot's pinned `RiskyActionPolicy` does not recognize `codex`, `--yolo` or nested-agent
delegation as risky; it sees only the outer `exec` launch, while later Codex shell/file actions are opaque to
Nanobot's per-tool approval policy.

**Consequence.** In an ordinary host/non-externally-sandboxed tmux session, following this built-in skill can hand a
nested coding agent unsandboxed, no-confirmation command authority without Nanobot obtaining a distinct approval
for that escalation. Subsequent destructive or out-of-scope actions can occur inside the nested process beyond
Nanobot's normal risky-action visibility.

**Qualification.** This is conditional on using the coding-agent section, having Codex installed and not already
running the tmux command inside a trustworthy external sandbox. A managed OS-level sandbox around the entire
Nanobot exec process can materially reduce the host impact. The finding is about the built-in instruction
recommending the bypass without proving that prerequisite.

**Smallest later alternative.** Do not recommend `--yolo` by default. Use a Codex mode that preserves its sandbox
and approval policy, or require an explicit user approval plus a positively established external sandbox before
allowing the bypass flag. Nanobot's risky-action classifier should also treat commands that disable a delegated
agent's sandbox/approval layer as an authority escalation.
