## E01-A behavior established

- Channel-package discovery reads dependency-free manifests first and lazily imports optional
  runtimes/connectors only when enabled. Built-in package names are reserved against legacy
  entry-point shadowing, target syntax is validated, package runtime/connector modules must stay
  inside their owning package, and runtime classes must be non-base `BaseChannel` subclasses
  whose declared channel name matches the descriptor.
- Legacy entry-point channels execute plugin code only when explicitly enabled. Missing or
  duplicate enabled entry points, malformed targets and unavailable dependencies fail closed
  rather than silently selecting another implementation.
- `BaseChannel.is_allowed()` uses exact allow-list tokens, supports explicit `"*"`, and then
  falls back to the pairing approval store. Empty or omitted `allowFrom` is intentionally
  pairing-only for ordinary channels; source tests explicitly preserve this behavior.
- `_handle_message()` can authorize on a room/group identity while retaining the original
  sender identity, and only publishes inbound work after authorization. Pairing-store I/O
  failure drops the unauthorized DM rather than replacing the approval store with an empty view.
- Channel management distinguishes single-instance plugin-owned `instances` data from explicit
  multi-instance management. Multi-instance adapters must return unique instance IDs and unique
  channel-scoped runtime names.
- Feature-instance projection strips configured secret values while retaining non-secret
  configured values and configured-field names. Descriptor-owned presentation overrides are
  restricted to display fields rather than runtime authority.
- Channel acquisition and startup are transactional: construction/startup failures roll back
  acquired/started channels with cancellation-resistant cleanup. Channel stop cancels that
  runtime's queued sends before stopping its transport.
- Ordinary outbound delivery is bounded to 256 pending tasks and 32 active sends, preserves FIFO
  per `(channel, chat_id)`, lets other destinations progress during one destination's retry
  wait, and propagates owner cancellation. Ordinary delivery remains best-effort and is distinct
  from the explicit receipt-bearing delivery API.
- Receipt-bearing text delivery is an opt-in capability with request-bound channel/target/action/
  request digests, contiguous message/part evidence, bounded receipt size and explicit partial
  delivery evidence. The canonical cron sender validates this strict binding and does not infer
  such receipts from ordinary `BaseChannel.send()`.
- Setup validation is explicitly non-authoritative. It can validate package-owned setup contracts
  and uses pinned target resolution for TCP probes; settings performs these blocking checks off
  the event loop.
- Notification-route persistence deliberately keeps only thread-address metadata needed for later
  session notifications, not sender identity or turn ownership.

## E01-F01 — P2 conditional — failed outbound delivery can poison origin duplicate suppression

**Evidence.** `ChannelManager._dispatch_outbound_loop()` calls
`_should_suppress_outbound()` before a message is admitted to the outbound send queue.
`_should_suppress_outbound()` immediately writes the normalized-content fingerprint into the
bounded LRU when a new `message_id` or `origin_message_id` is encountered. The subsequent
`_send_with_retry()` logs and returns normally after a non-retryable failure or after exhausting
its configured attempts; it does not report delivery success to the fingerprint owner and no
failure path removes the pre-send fingerprint. Normal turn delivery preserves inbound
`message_id` metadata, while system/background routing can carry `origin_message_id`; the
source test explicitly models the latter as a duplicate of the former. MessageTool support reads
also confirm that bus callback success is queue submission rather than remote delivery.

**Consequence.** If the first source-bound reply is fingerprinted and every actual transport send
fails, a later equivalent reply/recovery tied to the same source message can be suppressed as a
duplicate even though the user never received the original content. The fingerprint therefore
acts as delivered-state evidence despite being created before delivery.

**Qualification.** This requires source-message metadata participating in the duplicate contract,
an actual send failure after fingerprint insertion, and a later same-origin message with the same
normalized content. Separate turns with different source IDs are unaffected, and the cache is
bounded. The canonical receipt-capable cron path is separate and is not claimed to share this
best-effort ambiguity.

**Smallest later alternative.** Distinguish pending from delivered fingerprints. Reserve before
send if concurrent duplicate suppression is needed, but mark the fingerprint delivered only after
`_send_with_retry()` reports success and remove the pending reservation on terminal failure or
cancellation. Do not use queue admission as remote-delivery proof.

## E01-F02 — P1 conditional — shared channel runtime/validation/transcription can ignore the gateway's explicit config path

**Evidence.** `ChannelManager.__init__()` accepts and stores an explicit
`self._config_path`, and normal gateway composition passes that path into the manager. The WebUI
settings service likewise persists channel enable/config changes through its explicit
`WebUISettingsConfig.path`. However:

1. `ChannelManager.apply_channel_feature_action()` reloads proposed runtime config with
   `load_config()` and no path, so a hot apply after path-scoped settings persistence can
   inspect the process-global config instead of the manager's explicit config.
2. `validate_channel_config()` also calls global `load_config()`. The path-scoped settings
   router invokes this validator without supplying its config/path, so validation can merge form
   values with stored fields from another logical instance.
3. `BaseChannel.transcribe_audio()` resolves its current transcription/provider configuration
   via global `load_config()` on every call, rather than from the channel manager's explicit
   config owner.

`load_config(None)` resolves through the process-global current/default config path. Existing
tests deliberately set that global path to the test config or monkeypatch pathless
`load_config()`, so they do not exercise divergent explicit/global paths.

**Consequence.** In an embedded or multi-gateway process where gateway config A differs from the
process-global path B, a settings action for A can hot-start/stop a channel using B's saved
configuration/account credentials; validation for A can inspect B's retained secret/config
values; and inbound audio on A can use B's transcription provider credentials/settings. This
crosses external-account/credential authority between logical gateway instances rather than merely
presenting stale UI state.

**Qualification.** Normal foreground CLI startup obtains one global config path and passes the same
path into `ChannelManager`, so common single-instance startup is aligned and is not claimed
broken. The finding is conditional on the explicit manager/settings path being a meaningful
instance boundary and diverging from the process-global path. Adapter-specific pathless helpers
remain for their owning later substages and should strengthen this root finding rather than be
double-counted.

**Smallest later alternative.** Make the config owner explicit through the channel graph:
`apply_channel_feature_action()` should load `self._config_path`; setup validation should
accept a config/config-path and settings must pass its own path; transcription should receive an
injected path/config resolver from channel composition. Avoid pathless `load_config()` inside an
explicit-path channel runtime.

## E01-F03 — P2 conditional — truthy non-boolean enabled values activate packaged channels

**Evidence.** `ChannelsConfig` allows built-in/plugin channel sections as untyped extra mappings.
For packaged channels, `ChannelActivation.from_config()` reads an `enabled` value from that
mapping and normalizes it with Python `bool(raw_enabled)`; therefore non-empty strings such as
`"false"` or `"0"` become enabled. `channel_instance_specs()` uses that activation to decide
whether the manager constructs and starts the runtime. Bounded support reads of shipped Slack and
Telegram runtimes show that their constructors later Pydantic-parse the string to boolean false,
but their `start()` methods do not recheck `config.enabled`; they rely on manager activation and
will connect when required credentials are present. The activation tests cover actual booleans,
not false-like strings.

**Consequence.** A malformed/manual persisted configuration that visually/semantically says
`enabled: "false"` can still cause a packaged channel to connect to its external platform and
begin receiving/sending under configured credentials.

**Qualification.** Normal settings/config writers are expected to persist real JSON booleans, so
the trigger requires malformed/manual/non-typed channel configuration. Explicit legacy external
entry-point activation is stricter (`enabled is True`) and is not the affected discovery path.

**Smallest later alternative.** Require a real boolean at activation time and fail closed on any
other value, or use one strict shared parser with an explicitly documented string compatibility
contract before runtime admission. Do not use generic truthiness for channel enablement.

## E01-B behavior established

- Telegram supports polling and webhook startup. Polling uses separate long-poll and ordinary API
  request pools, tracks completed getUpdates round trips, rebuilds pools after a stale long poll,
  retries transient startup failures with bounded exponential backoff and treats invalid token /
  non-transient startup errors as terminal.
- Webhook mode requires a syntactically valid public HTTPS URL and a 1–256 character Telegram
  secret token. The secret is passed to python-telegram-bot's webhook listener.
- Sender authorization is stricter than the generic BaseChannel pairing policy. Telegram accepts
  exact numeric sender IDs, usernames or `"*"` from `allowFrom`; optional `allowChats`
  additionally restricts non-private chats. The manager deliberately refuses an enabled Telegram
  runtime with an empty effective `allowFrom`.
- Group messages default to mention/reply-to-bot admission. Topic messages derive
  `telegram:<chat>:topic:<thread>` session keys and ordinary inbound/outbound routing retains
  `message_thread_id`.
- Inbound updates are staged behind a short per-session reorder window and sorted by Telegram
  message ID/update ID before processing. Media groups are briefly aggregated into one turn.
- Telegram media downloads use provider `file_unique_id` when available, preserve the original
  filename extension for documents, and pass downloaded local files into the shared attachment
  adoption path. Voice/audio can invoke the shared transcription owner.
- Ordinary sends support media, reply parameters, topic routing, HTML/plain fallback, optional
  inline keyboards, optional Bot API rich messages, streaming previews, overflow rollover and
  per-chat streaming locks. Stream retries use manager-provided `_delivery_id` to avoid
  re-appending the same delta to an adapter buffer.
- The production progress hook emits empty `StreamEndEvent` payloads. Therefore the synthetic
  manager test where a non-empty end is coalesced into a preceding delta does not establish a live
  Telegram text-loss path.
- Fast commands execute only operator-configured argv after Telegram sender/chat authorization;
  user message arguments are not appended. Cancellation/timeout starts process-tree cleanup.
- The qualified cron delivery path remains a preserve result. It validates the complete receipt
  shape before the first provider call, performs no hidden provider retries, serializes receipt
  bundles per Telegram target, verifies provider chat/thread/message evidence, maps definite
  provider rejection separately from ambiguous failure, and retains acknowledged prefixes for
  partial/unknown settlement. This fresh full-body read is consistent with the earlier
  architecture-review receipt slice.

## E01-F04 — P2 conditional — Telegram enablement can persist a startup-invalid config and escape as SystemExit

**Evidence.** Telegram's package setup contract exposes `allowFrom` but declares only `token`
as required, and its validator checks the token/proxy without enforcing the manager's non-empty
Telegram `allowFrom` startup policy. A token-valid configuration with empty/missing
`allowFrom` can therefore validate as configured/connected and enable-capable. The generic
optional-feature enable path then persists `enabled=true` to the config before hot runtime
application. `ChannelManager.apply_channel_feature_action("enable", "telegram")` immediately
calls the Telegram authorization guard, which raises `SystemExit` for an empty effective
allow-list. The settings feature-enable flow and outer WebUI mutation wrapper catch
`Exception`, not `BaseException`, so this `SystemExit` is not converted to a normal settings
failure. Source tests deliberately pin the `SystemExit` behavior for startup/hot enable but do
not reconcile it with the package validator/persist-first settings flow.

**Consequence.** A local authenticated settings user can follow the normal Telegram setup/enable
flow, persist an enabled Telegram configuration that the gateway itself refuses, and then let the
process-level exit signal escape hot apply. Even if an embedding catches that exit, the persisted
configuration fails the same guard on the next gateway acquisition, leaving the gateway unable to
start normally until the config is repaired manually.

**Qualification.** The WebUI feature-enable path is local-browser restricted in the reviewed
settings router; this is not claimed as unauthenticated or remote-owner code execution. The trigger
requires Telegram to be enabled while its effective sender allow-list is empty/missing. A correctly
configured non-empty ID/username/`"*"` allow-list is unaffected.

**Smallest later alternative.** Put the Telegram authorization requirement into the package setup
contract/validator and validate the proposed configuration before persisting `enabled=true`.
Represent invalid hot enable as a normal typed configuration error rather than `SystemExit`; keep
hard startup refusal only as a final defensive boundary.

## E01-F05 — P1 conditional — inline-keyboard callbacks in Telegram forum topics lose topic session identity

**Evidence.** Ordinary Telegram topic messages derive
`telegram:<chat_id>:topic:<message_thread_id>` and pass that explicit session key plus
`message_thread_id` metadata into `BaseChannel._handle_message()`. The callback-query handler,
however, authorizes only sender/chat, then calls `_handle_message()` with the chat ID and button
label but without `session_key` and without `message_thread_id` in metadata. The generic base
channel therefore falls back to the chat-wide session key `telegram:<chat_id>`. Existing source
tests cover topic derivation and topic-preserving ordinary sends, but no callback-in-forum test was
found.

**Consequence.** When inline keyboards are enabled and a user clicks a bot button inside a Telegram
forum topic, that click can enter the chat-wide Telegram session rather than the topic session that
created the button. Callback turns from different topics can therefore converge on the same
conversation state, mixing context and tool/session continuity across topic boundaries and routing
the subsequent response outside the intended topic context.

**Qualification.** This requires Telegram forum/topic use plus `inline_keyboards=true` and a
callback button interaction. Private chats and non-topic group chats use the same chat-wide key
already and are unaffected. The finding is about nanobot session/topic isolation, not Telegram
sender authorization; sender and chat allow-lists are still checked.

**Smallest later alternative.** For callback queries backed by a Telegram `Message`, derive the
same topic session key and common message metadata used by normal messages, including
`message_thread_id`, before calling `_handle_message()`.

## E01-F06 — P2 conditional — Telegram ordinary delivery hides retries beneath the manager attempt cap

**Evidence.** The shared `BaseChannel.send()` contract says implementations should raise delivery
failures so the channel manager can apply retry policy in one place. The manager limits ordinary
delivery using `channels.sendMaxRetries` (with one initial attempt minimum). Telegram instead
wraps ordinary provider calls in its own fixed `_call_with_retry()` loop of three attempts for
`TimedOut` and `RetryAfter`. Text sends, media sends and rich-message API calls use this helper;
the manager may then retry the entire Telegram send again. Source tests explicitly require three
Telegram timeout attempts and describe earlier work only as reducing fallback amplification; they
do not bind those inner attempts to the configured manager cap. With opt-in rich messages,
`_try_send_rich()` additionally treats an exhausted timeout as a reason to fall back to the
legacy send path, which has its own three-attempt helper.

**Consequence.** `sendMaxRetries=1` still permits three Telegram provider attempts, and the
default manager value of three can permit up to nine attempts for the same ordinary operation
before considering rich fallback. Because a send timeout can be ambiguous after the provider has
accepted a message, hidden retries can also produce duplicate user-visible text/media; the rich
fallback can add a second rendering path after an ambiguous rich send.

**Qualification.** This is the ordinary best-effort channel path, not the receipt-bearing cron
sender. The qualified receipt path deliberately performs one provider attempt per part and
classifies timeout as unknown/partial instead of retrying. Duplicate delivery requires a timeout
whose provider-side effect actually completed before the response was lost; the finding does not
claim every timeout duplicates a message.

**Smallest later alternative.** Give ordinary Telegram sends one retry owner. Prefer propagating
transport ambiguity to the manager and make the manager's configured attempt budget authoritative;
if Telegram-specific RetryAfter handling must remain inside the adapter, account those attempts
against the same explicit budget and do not switch rendering paths after an ambiguous send without
an idempotency/evidence mechanism.

## E01-F07 — P1 conditional — DingTalk inbound filenames can escape the media root and overwrite arbitrary writable paths

**Evidence.** For file messages and rich-text attachments,
`NanobotDingTalkHandler.process()` passes DingTalk's `fileName` value directly to
`_download_dingtalk_file()`. That helper creates
`get_media_dir("dingtalk") / sender_id`, then forms `file_path = download_dir / filename` and
writes the downloaded bytes with `file_path.write_bytes`. It does not reduce the name to a
basename, reject absolute paths/`..` components, canonicalize the final path, or verify that the
resolved target remains below the DingTalk media directory. Python `Path` joining also permits an
absolute right-hand path to replace the intended base. Existing source tests exercise only a
benign `test.xlsx` filename.

**Consequence.** If DingTalk preserves a sender-controlled filename containing path separators,
parent traversal, or an absolute path, an inbound attachment can write the sender's uploaded bytes
outside the DingTalk media tree and overwrite any file writable by the gateway process. Because
the handler performs the download before shared sender authorization, this can also occur before
`allowFrom` rejects the sender.

**Qualification.** The path-escape consequence depends on DingTalk delivering an attacker-chosen
`fileName` containing path syntax; the pinned source does not establish whether every official
client/API preserves such names. If the provider always canonicalizes filenames to safe basenames,
the arbitrary-path portion does not activate, though E01-F08's pre-authorization download side
effect remains.

**Smallest later alternative.** Treat provider filenames as display metadata only. Derive a safe
basename (or generated identifier), reject absolute/`..` path components, resolve the candidate,
and require it to remain under a canonical per-channel/per-sender media root before writing.

## E01-F08 — P2 conditional — denied DingTalk senders can trigger unbounded inbound file download work before authorization

**Evidence.** Picture/file/rich-text attachments are downloaded synchronously inside
`NanobotDingTalkHandler.process()` before the handler extracts/finally forwards the sender into
`DingTalkChannel._on_message()`. Only `_on_message()` delegates to
`BaseChannel._handle_message()`, where `allowFrom`/pairing admission occurs. The inbound
`_download_dingtalk_file()` path obtains/refreshes the bot access token, exchanges the attacker
message's download code for a URL, then calls `self._http.get(download_url,
follow_redirects=True)`, materializes `file_resp.content` completely and writes it to disk. It
does not use the adapter's 20 MiB guarded remote-media helper, does not stream with a byte limit,
and does not apply that helper's redirect/target validation. Source tests cover benign download,
shutdown-during-download, and the guarded **outbound** remote-media helper, but no denied-sender
attachment case.

**Consequence.** A DingTalk account that can reach the bot but is not authorized by
`allowFrom` can still cause authenticated provider API calls, response buffering and disk writes
before its message is rejected. Repeated or large provider-accepted files can consume gateway
network, memory and storage; provider-returned redirects are followed by this path without the
adapter's normal remote-media policy.

**Qualification.** Practical amplification is bounded by whatever attachment/rate/URL constraints
DingTalk itself enforces, which are outside this source review. The finding does not claim an
attacker can directly choose an arbitrary download URL; that URL is returned by DingTalk's API.
E01-F07 separately covers the destination-path consequence if unsafe filenames are preserved.

**Smallest later alternative.** Resolve sender identity and perform the same sender/chat admission
before any attachment fetch. Then download through a bounded, streamed helper with explicit
redirect/target policy and a byte ceiling before committing a safe-root file.

## E01-F09 — P2 conditional — persistent DingTalk stream failures are reported as running

**Evidence.** `DingTalkChannel.start()` sets `self._running=True` before the stream SDK has
successfully connected. Its reconnect loop catches every ordinary exception from
`self._client.start()`, logs it, sleeps five seconds and retries while leaving `_running=True`.
The shared `BaseChannel.is_running` property returns only that flag, and
`ChannelManager.channel_runtime_status()` reports `state="running"` whenever it is true.
DingTalk has no package validator that verifies credentials/connectivity, so generic setup
validation marks required client credentials as configured/can-enable without proving the stream
can authenticate. The outer startup method also catches constructor/setup `Exception` and
returns normally, which leaves no manager-owned startup error for those failures.

**Consequence.** A persistent authentication/configuration/protocol failure can leave DingTalk
disconnected while management/status surfaces report it running, preventing operators from
distinguishing a live bot from an endless reconnect loop. Constructor/setup failures swallowed by
the outer catch can appear merely stopped rather than failed.

**Qualification.** Temporary network loss may intentionally be represented by a live reconnecting
supervisor, so the finding is about persistent/non-transient failures and setup failures that
cannot heal without configuration change. Source alone does not classify every SDK exception as
permanent.

**Smallest later alternative.** Separate desired/supervisor/reconnecting state from confirmed
transport readiness. Mark running only after a successful stream connection/ready signal, retain a
failed/degraded state with the last error across retries, and propagate terminal startup errors to
the manager.

## E01-F10 — P2 conditional — DingTalk retries replay already-delivered text/media after later part failure

**Evidence.** `DingTalkChannel.send()` sends message text first, then iterates media references
sequentially. Transport failures from `_send_batch_message()`, remote download, or upload are
deliberately re-raised. The shared manager then retries the entire `OutboundMessage` from the
beginning. DingTalk keeps no per-message completed-part receipt/cursor for ordinary delivery.
Therefore a transport failure on a later attachment occurs after earlier text or media may already
have been accepted by DingTalk, but the retry replays those successful parts. Source tests
explicitly require transport failures to propagate for manager retry, but do not cover failure
after an earlier part succeeded.

**Consequence.** A message containing text plus attachment(s), or multiple attachments, can produce
duplicate user-visible text/files when an early part succeeds and a later part fails
ambiguously/retryably. The duplicate risk is highest when the provider completed the later call but
the response was lost, because the manager cannot distinguish applied from not-applied effects.

**Qualification.** This requires a multipart ordinary outbound message and a retryable failure
after at least one earlier part completed. Single-part sends do not have the same intra-message
replay window. DingTalk has no qualified receipt-capable cron path, so this finding concerns its
ordinary best-effort manager retry contract.

**Smallest later alternative.** Give multipart delivery explicit part progress/effect evidence.
Resume only unsent parts after known failures and classify ambiguous provider outcomes rather than
blindly replaying the whole message; alternatively make the adapter own the whole multipart
attempt and expose a non-retryable partial/unknown outcome to the manager.

## E01-F11 — P2 conditional — DingTalk downloads inbound attachments but bypasses the canonical media/attachment pipeline

**Evidence.** `NanobotDingTalkHandler.process()` collects downloaded picture/file/rich-text paths
in `file_paths`, then appends those paths only to the textual `content` as a
`Received files:` list. It invokes `DingTalkChannel._on_message()` without a media argument,
and `_on_message()` calls `BaseChannel._handle_message()` without `media=`. The resulting
`InboundMessage.media` is therefore empty. The canonical agent restore path adopts channel media
only when `msg.media` is populated, creates attachment records/canonical paths there, and passes
media into provider current-message construction from that field. DingTalk source tests assert the
filesystem path appears in message text but do not assert `msg.media` or canonical attachment
adoption.

**Consequence.** DingTalk's advertised picture/file/rich-text download support does not feed the
normal attachment adoption or multimodal provider path. The model receives a local filesystem path
string rather than the attachment content/record; under normal workspace/file-access restrictions
that path may not be readable by tools, and images are not automatically supplied as image input.

**Qualification.** A sufficiently privileged agent with filesystem access may still choose to
open the textual path manually, so the attachment is not necessarily unusable in every deployment.
The defect is the bypass of the shared canonical attachment/multimodal path, not a claim that every
turn loses the bytes.

**Smallest later alternative.** Pass successful DingTalk download paths through
`media=file_paths` when calling `_handle_message()` and let the shared adoption/context layer
own canonicalization, persistence and provider projection. Keep any human-readable file marker
secondary to that structured media field.

## E01-F12 — P2 conditional — unauthorized Discord DMs can persist attachments before pairing authorization

**Evidence.** `_should_accept_inbound()` intentionally rejects unauthorized **guild** messages
early but returns true for DMs so `BaseChannel._handle_message()` can issue a pairing code.
`_handle_discord_message()` downloads every accepted message attachment before it calls
`_handle_message()`. Therefore an unauthorized DM reaches `_download_attachments()` first.
Each accepted attachment is saved under `get_media_dir("discord")`; only afterward does the base
authorization path decide the sender is unapproved and send a pairing response. Successful
downloads are not removed when the DM is denied.

**Consequence.** A Discord user who is not yet authorized can cause provider attachment downloads
and persistent local disk writes before pairing succeeds. Repeated DMs can accumulate files and
consume I/O/storage even though none of those message turns is admitted to the agent.

**Qualification.** Discord's declared attachment size is checked against the adapter's 20 MiB
per-file cap before `Attachment.save()`, so this is materially more bounded than E01-F08's
DingTalk path. Practical volume is also constrained by Discord's own attachment/rate policies,
which are outside this source review. Authorized DMs and guild messages rejected before download
are not affected.

**Smallest later alternative.** Separate “may receive pairing response” from “may materialize
attachments.” For unapproved DMs, run only the minimal identity/pairing path and defer attachment
download until sender authorization succeeds.

## E01-F13 — P2 conditional — Discord streaming silently loses deltas while the client is unready

**Evidence.** `DiscordChannel.send()` raises when the client is absent/unready specifically so
the shared manager can retry ordinary sends. `send_delta()` uses the opposite contract: when the
client is absent or `is_ready()` is false it logs “dropping stream delta” and returns normally.
The shared manager treats a normally returned stream send as success. The canonical streaming
turn publishes `StreamDeltaEvent` / `StreamEndEvent` pieces and then marks the final response
as `StreamedResponseEvent`; the manager deliberately does not call ordinary `channel.send()`
for that final marker. Thus there is no full-text fallback after silently dropped Discord stream
events.

**Consequence.** If Discord temporarily becomes unready during a streamed response—startup race,
reconnect, gateway interruption, or transient client readiness loss—one or more deltas, including
the end event, can be discarded without retry. If all visible pieces are dropped, the completed
agent answer may never reach Discord even though the channel manager records no send failure.

**Qualification.** The trigger is a streaming-enabled turn while `client.is_ready()` is false.
Discord streaming is enabled by default, but a deployment that disables streaming uses the
ordinary send path and receives manager retries instead. This finding does not claim Discord loses
already-sent preview text when only a later edit is skipped.

**Smallest later alternative.** Make unready streaming behave like ordinary delivery: raise a
retryable readiness error, or retain the adapter buffer until readiness returns. Preserve a final
full-text fallback if a stream cannot be committed.

## E01-F14 — P2 conditional — Discord attachment upload failures can be hidden as successful message delivery

**Evidence.** `DiscordBotClient._send_file()` catches every exception from
`channel.send(file=...)`, logs it and returns `False` instead of propagating the transport
failure. `send_outbound()` records the filename in `failed_media` but continues. Its
`_build_chunks()` emits attachment-failure text only when there is no ordinary content **and**
no media succeeded. If message text exists, it returns the text chunks and omits failed-media
markers; if at least one attachment succeeded and another failed with no text, it also emits no
failure marker. Because the outer call returns normally after those remaining sends, the manager
considers the whole outbound operation successful and cannot retry the failed attachment.

**Consequence.** A user can receive the textual response or some attachments while another
requested attachment is silently missing. Network/provider upload failures that would ordinarily
be manager-retryable are collapsed into local best-effort omission.

**Qualification.** A media-only message where **all** attachments fail receives a visible
`[attachment: ... - send failed]` fallback, which the source tests explicitly preserve. Missing
or oversized local files are also local deterministic failures and need not necessarily be
retried. The defect is transport/provider exceptions being collapsed into the same `False`
result and then hidden when other content succeeds.

**Smallest later alternative.** Distinguish deterministic local skip from retryable/ambiguous
provider failure. Propagate transport failures, or return structured per-part results so the
manager/caller can retry or visibly report every failed requested attachment.

## E01-F15 — P2 conditional — Discord multipart retries can duplicate already-delivered files or text chunks

**Evidence.** `send_outbound()` sends all attachments sequentially and then sends each 2,000-
character text chunk sequentially. Exceptions from text/channel resolution are propagated to
`DiscordChannel.send()`, which re-raises them so `ChannelManager._send_with_retry()` retries
the original `OutboundMessage` from the beginning. There is no per-part cursor or provider
receipt recording which earlier attachments/chunks already succeeded. Streaming finalization has
the same shape for overflow: it edits the first final chunk, then sends later chunks; a later
failure leaves the buffer and manager retry repeats finalization from its first extra chunk.

**Consequence.** If an early attachment or text chunk succeeds and a later send fails retryably,
the next manager attempt can resend the already-delivered earlier parts. Long responses and
media-plus-text messages can therefore produce duplicate Discord files/text after partial failure;
stream-overflow retries can duplicate extra final chunks as well.

**Qualification.** The trigger requires a multi-part ordinary or overflow-stream delivery with a
failure after at least one earlier part completed. Single-part sends do not have this particular
replay window. E01-F14 separately covers attachment failures that are swallowed rather than
propagated.

**Smallest later alternative.** Track completed part IDs/cursors for one manager delivery ID and
resume only unsent parts, or surface a typed partial/unknown outcome that prevents blind whole-
message replay.

## E01-F16 — P2 conditional — Discord startup failures are swallowed before manager failure accounting

**Evidence.** `DiscordChannel.start()` catches client-construction exceptions, logs them and
returns; after `self._running=True`, it also catches ordinary exceptions from
`self._client.start(token)`, logs “client startup failed,” then resets state and returns
normally. `ChannelManager._start_channel()` records `_channel_errors` only when
`channel.start()` raises. During hot apply the manager starts the task, yields once, checks
`_channel_errors`, and can report “applied without restart” when the adapter swallowed an
immediate failure. Later runtime-status projection sees an enabled channel with
`is_running=False` and no error, so it renders stopped rather than failed. Discord's setup
validator proves the token against REST but cannot prove all client/intents/proxy/gateway startup
conditions.

**Consequence.** A configuration that passes setup validation but fails the actual Discord client
startup can appear successfully applied or merely stopped without the actionable runtime error
that the manager contract otherwise exposes. Operators can therefore receive a false-positive hot
apply result and lose the startup failure reason from management state.

**Qualification.** A plainly invalid bot token submitted through the normal settings validator is
usually rejected before enablement, so this primarily concerns failures not covered by that REST
probe, stale credentials after validation, direct/manual startup, proxy/client construction, or
other gateway-start exceptions. The adapter does clean up the partial client correctly.

**Smallest later alternative.** Keep local cleanup in `finally`, but re-raise a sanitized/typed

## E01-E behavior established

- Email uses IMAP polling for inbound messages and SMTP for outbound replies/proactive sends.
  Explicit mailbox consent is required before start or send.
- Setup validation checks required fields, consent and TCP reachability for the configured IMAP
  and SMTP endpoints. Private/internal targets are filtered by the shared validation policy unless
  local-service access is explicitly allowed. Reachability warnings do not block enablement.
- Inbound polling first performs UID SEARCH, fetches only headers, rejects self-mail, applies
  Authentication-Results checks and sender authorization, and only then fetches the full body.
  Unauthorized senders therefore do not trigger body/attachment download.
- Accepted messages are parsed into an `[EMAIL-CONTEXT]` text envelope. Optional attachments use
  a MIME allow-list, count/size limits, sanitized filenames and the structured `media` field,
  so accepted files do enter the shared canonical attachment/adoption path.
- Sender identity is normalized from the RFC5322 `From` address and compared against
  `allowFrom` / the shared pairing approval store. Bot-owned From/SMTP/IMAP identities are
  suppressed to avoid self-mail loops.
- SMTP delivery has a 30-second adapter-owned socket timeout, supports TLS/SSL, preserves a
  source-bound subject override from outbound metadata, emits visible fallback text for
  deterministic local attachment omissions, and re-raises SMTP transport errors so the shared
  manager owns ordinary retry.
- IMAP stale-connection errors are retried once with a fresh connection. Missing mailboxes are
  treated as a skipped poll rather than crashing the channel.
- Post-actions support UID MOVE where available and UID-scoped delete/expunge with compatibility
  fallback. Broad EXPUNGE is only used when explicitly configured on servers without UIDPLUS.
- Historical date-range fetches use the same header/auth/allow-list/full-body pipeline but disable
  `\Seen` mutation and in-process UID dedupe.

  escaping the media root.

## E01-F17 — P1 conditional — Email anti-spoofing accepts SPF/DKIM pass results that are not bound to the allowed From identity

**Evidence.** Sender authorization is performed against the normalized RFC5322 `From` address.
Before that allow-list check, `_check_authentication_results()` scans every
`Authentication-Results` header and returns true as soon as any header text contains
`spf=pass` and/or `dkim=pass`. It does not identify a trusted receiver/authserv-id, does not
bind SPF's authenticated envelope domain to the visible From domain, does not bind DKIM
`header.d` to the visible From domain, and does not require a DMARC/alignment result. Source
tests themselves construct the raw message's `Authentication-Results` header directly and then
treat matching pass tokens as sufficient.

**Consequence.** If the mailbox delivers a message whose visible From address is allowlisted while
SPF/DKIM pass for some unrelated identity—or preserves a sender-injected Authentication-Results
header—the adapter can accept the message as the allowlisted sender. That crosses Email's sender
authorization boundary and admits attacker-controlled prompt/tool input under another address.

**Qualification.** Exploitation depends on the upstream mail path delivering the message instead
of enforcing/rewriting a stronger DMARC/authentication policy. A provider that strips all
untrusted Authentication-Results headers and rejects non-aligned spoofing can prevent the trigger.
The source nevertheless does not establish or enforce that prerequisite itself.

**Smallest later alternative.** Treat mail authentication as a trusted-receiver assertion. Accept
only Authentication-Results from a configured/trusted authserv-id and require DMARC pass or
explicit SPF/DKIM domain alignment with the normalized RFC5322 From domain before using From as
the channel authorization identity.

## E01-F18 — P2 conditional — Email acknowledges mailbox messages before durable agent processing

**Evidence.** `_fetch_messages_once()` appends an accepted message to the return list, records its
UID in the in-memory dedupe set and, with the default `mark_seen=true`, sets `\Seen` before
`_fetch_new_messages()` returns to the async poll loop. Only afterward does `start()` call
`_handle_message()`. The shared base handler merely enqueues the inbound object into the
unbounded in-memory MessageBus; it does not wait for turn persistence or successful agent
processing. Optional delete/move post-actions run after that enqueue returns, so a source message
can also be moved or UID-expunged before the agent consumes it. Source tests explicitly assert
that fetch marks accepted mail seen and separately call a successful `_handle_message()`
"delivery."

**Consequence.** A process crash, cancellation, agent-core failure or other loss after IMAP
acknowledgement/queue admission but before durable turn processing can remove the email from the
next `UNSEEN` poll. With delete/move post-action enabled, the original mailbox item may also be
relocated or removed while only an in-memory queue entry proves admission.

**Qualification.** The trigger requires failure in the window after source acknowledgement and
before durable processing. Setting `mark_seen=false` and avoiding post-actions preserves the
source, but then dedupe is only in-memory and restart replay becomes possible. This is an
at-most-once intake boundary, not a claim that normal successful processing loses mail.

**Smallest later alternative.** Separate fetched, durably admitted and source-acknowledged states.
Record a durable intake receipt first; only then mark seen/delete/move, with recovery able to
resume or reconcile an acknowledged-but-not-completed item.

## E01-F19 — P2 conditional — Email replies can attach to the wrong Message-ID when one sender has multiple in-flight emails

**Evidence.** Each inbound item carries its own source `message_id` and `subject` metadata, and
the agent's assembled outbound response preserves that metadata. `EmailChannel.send()` correctly
honors a source-bound `metadata["subject"]` override, but it ignores
`metadata["message_id"]` for threading. Instead it reads `_last_message_id_by_chat[to_addr]`,
a mutable cache keyed only by sender address. `start()` overwrites this cache for every fetched
message before/while enqueueing turns.

**Consequence.** If two emails from the same sender are fetched or arrive close together, the
response to the earlier turn can use the later email's Message-ID in `In-Reply-To` and
`References`. Mail clients may therefore attach the answer to the wrong thread, even though the
correct triggering Message-ID is already present in the outbound metadata.

**Qualification.** The recipient remains the same normalized sender, so this does not by itself
cross user principals. The trigger requires more than one source message from the same sender
before the earlier response is sent. The subject is less affected because source-bound outbound
metadata overrides the mutable subject cache.

**Smallest later alternative.** Prefer the outbound message's source-bound `message_id` metadata
for `In-Reply-To` / `References`; use mutable per-sender state only for truly proactive sends
that have no source message.

## E01-F20 — P2 conditional — persistent IMAP failures are reported as a running Email channel

**Evidence.** After local config checks, `EmailChannel.start()` sets `_running=True` before the
first IMAP login/select/search succeeds. Every ordinary exception from
`_fetch_new_messages()` is caught inside the poll loop, logged and retried forever while
`_running` remains true. The shared manager reports `state="running"` whenever
`channel.is_running` is true and only records a failed state when `channel.start()` raises.
Email setup validation performs TCP reachability only; a warning still yields `can_enable=true`,
and it does not authenticate to IMAP.

**Consequence.** Bad IMAP credentials, TLS/protocol/login failures or another permanent poll error
can leave an Email integration that receives nothing while settings/runtime status reports it
running and retains no manager-owned startup error.

**Qualification.** Temporary network failures may intentionally be represented by a live polling
supervisor. The finding is about persistent/non-healing failures requiring configuration or
operator action. SMTP health is separate.

**Smallest later alternative.** Track desired/supervising state separately from confirmed IMAP
readiness. Promote repeated or clearly terminal login/config errors to a degraded/failed runtime
state with the last actionable error, while still allowing bounded reconnect for transient faults.

## E01-F21 — P1 conditional — a cancelled Email runtime does not own its in-flight IMAP worker

**Evidence.** Each poll runs synchronous IMAP work through `asyncio.to_thread()`.
`EmailChannel.stop()` only sets `_running=False`; the manager then cancels the channel's start
task. Cancelling the coroutine waiting on `to_thread()` does not stop the already-running worker
function. The IMAP constructor/login/select/search/fetch calls have no adapter-supplied socket
timeout, and `_fetch_messages_once()` does not consult `_running` while iterating messages.
That worker can still mark UIDs seen and save accepted attachments using the old instance's
credentials/config after the owning runtime has been disabled or replaced.

**Consequence.** A slow/stalled poll that resumes after hot disable/reconfiguration can perform
mailbox and filesystem side effects under stale authority even though the manager has completed
runtime replacement. Because the coroutine result is already cancelled, accepted messages can be
marked seen by the stale worker without ever being published by that old instance, causing source
loss as well as cross-generation races.

**Qualification.** The trigger requires disable/replacement/shutdown while an IMAP worker is still
active. Fast provider calls usually finish before this matters. System/TCP-level timeouts may
eventually terminate some stalls, but this adapter establishes no bounded ownership guarantee.

**Smallest later alternative.** Give IMAP operations explicit connection/read deadlines and a
cancellable owner. Avoid detached thread ownership for mutating fetches, or add an epoch/cancel
check before every mailbox/file side effect and synchronously join the worker before reporting
the channel stopped/replaced.

## E01-F22 — P2 conditional — Email body and attachment limits do not bound full-message fetch or decode memory

**Evidence.** After header-level admission, the adapter requests `BODY.PEEK[]` and materializes
the complete RFC message bytes before parsing. `max_body_chars` is applied only after the full
text body is decoded. Attachment `max_attachment_size` is checked only after
`part.get_payload(decode=True)` has materialized the decoded attachment bytes. The per-attachment
limit therefore controls what is saved/forwarded, not the size of IMAP response or MIME payload
that must first exist in memory. Source tests verify oversized attachments are skipped after
construction but do not establish a pre-fetch/pre-decode byte ceiling.

**Consequence.** An authorized sender—or a spoofed sender if E01-F17's condition is met—can deliver
a mailbox-accepted message substantially larger than the configured body/attachment limits and
force the gateway worker to buffer/parse it before those limits take effect. Resource impact is
bounded only by the upstream mailbox/provider limits, not by the adapter configuration.

**Qualification.** Practical maximum size depends on the mail provider's own message-size policy.
The finding is not that oversized attachments are saved; they are correctly skipped after decode.
It is that the configured limits are not resource-admission limits.

**Smallest later alternative.** Establish an overall inbound-message byte budget before full
materialization, use size-aware/partial IMAP fetch where possible, and stream/decode attachments
with a hard byte ceiling rather than decoding the whole payload first.

## E01-F23 — P2 conditional — Email can be enabled with no sender allow-list but cannot bootstrap pairing from inbound mail

**Evidence.** The Email manifest does not require `allowFrom`; its default runtime config is an
empty list. The validation source test submits no `allowFrom` and asserts
`can_enable is True`. During polling, however, Email calls `is_allowed(sender)` before the
shared `_handle_message()`. An unapproved sender is remembered/skipped (and normally marked seen)
without ever reaching the base DM path that generates and sends a pairing code. Email has no
package-owned connect flow that generates that code.

**Consequence.** A normal fresh WebUI setup can validate and enable successfully while every
incoming sender is silently rejected. With no pre-existing pairing-store approval, the mailbox
cannot bootstrap itself into the generic pairing flow; users must discover and configure
`allowFrom` out of band.

**Qualification.** Explicit `allowFrom`, `"*"`, or an already-approved pairing identity makes
the channel usable. This is a setup/admission contract mismatch, not an authorization bypass.

**Smallest later alternative.** Either require a non-empty Email `allowFrom` during validation,
as Telegram does for its stricter policy, or intentionally route unauthorized Email identities
through a safe pairing workflow before marking/skipping the source message.

## E01-F24 — P2 conditional — same-name Email attachments overwrite one another within a message

**Evidence.** Attachment persistence derives each destination as
`<media_dir>/<uid>_<safe_filename(original_name)>`. The UID is common to every MIME part in one
email and no part index/hash/collision check is added. Two attachment parts with the same filename,
or two distinct names that sanitize to the same safe filename, therefore resolve to the same
destination. Later `write_bytes()` overwrites the earlier file while both saved entries can
reference that same Path.

**Consequence.** A valid email containing multiple colliding attachment names can silently lose
earlier attachment content and present the final bytes multiple times to the canonical media
pipeline, so the agent sees a different attachment set from what the sender supplied.

**Qualification.** This requires at least two accepted attachment parts in one message whose safe
names collide. Filename sanitization still prevents path escape, and distinct safe names are
unaffected.

**Smallest later alternative.** Include a MIME-part index, stable content hash or collision-safe
generated identifier in every persisted attachment filename while preserving the original name as
display metadata.

## Existing-finding consolidation from E01-F

### E01-F02 — stronger Feishu QR evidence; do not create a duplicate finding

E01-F02 already owns the root defect where channel operations can ignore an explicit gateway
config path. E01-F adds a concrete Feishu control-plane consequence:

- `SystemSettingsHandler` owns path-scoped configuration through
  `WebUISettingsConfig(config_path)`, but caches a package connector with no config-path
  argument.
- `FeishuConnectStore` therefore cannot bind credential persistence to that gateway path. On
  provider success it delegates persistence to Feishu's registration-save helper.
- Earlier bounded Feishu support reads in E01-A established that this registration-save helper
  loads/saves through the process-global config path rather than an injected explicit path; the
  Feishu login source tests likewise set `loader._current_config_path` and assert the helper
  writes there.
- After the connector reports success, the settings handler separately enables/hot-applies the
  returned instance through its own path-scoped settings service.

Therefore, when an explicit gateway path A differs from process-global path B, one ordinary Feishu
QR flow can persist the new app secret/identity into B while the settings request subsequently
enables A. This remains the same explicit-config-root ownership defect as E01-F02, with a sharper
cross-account credential mutation consequence; it is **not** counted again.

### E01-F03 — Feishu instance normalization independently reproduces truthy enablement

Feishu's management adapter derives instance activation with
`bool(config.get("enabled", ...))`. A persisted truthy non-boolean such as `"false"` therefore
also activates a Feishu instance before runtime construction. This is additional Feishu evidence
for E01-F03's existing non-boolean activation root and is not counted as a new finding.

## E01-F25 — P2 conditional — Feishu validation reports “Connection verified” without verifying Feishu credentials

**Evidence.** The package validator runs only local required-field checks and an App-ID prefix
shape check. It never sends the app ID/secret to Feishu/Lark or performs any credential
authentication. Nevertheless, whenever the required `appId` and `appSecret` fields are merely
present, it returns status `connected` even if the App ID shape check is only a warning. The
shared validation payload renders `connected` as “Connection verified.” and allows enablement.

**Consequence.** Manually entered stale, mistyped or otherwise invalid Feishu/Lark credentials can
be presented by the validation API as a verified connection before any provider authentication has
occurred. The actual runtime can fail later, so the setup result can contradict runtime reality
and mislead an operator troubleshooting an assistant.

**Qualification.** The default QR registration path has provider-side authorization evidence and
is stronger than this manual validator. This finding concerns the package validation contract for
saved/manual credentials, not a claim that runtime startup trusts the validator for security.
E01-A's broader observation that setup validation is non-authoritative remains true; the defect is
the stronger `connected`/“Connection verified” status chosen despite no connection check.

**Smallest later alternative.** Return `configured` when only field presence/shape is known.
Reserve `connected` for a bounded Feishu/Lark credential probe, or explicitly label the result as
unverified setup.

## E01-F26 — P2 conditional — Feishu QR session storage is mutated concurrently without one session-map lock

**Evidence.** `SystemSettingsHandler` caches one `FeishuConnectStore` for the channel. Every
`start`, `poll` and `cancel` action delegates synchronous store work through
`asyncio.to_thread()`, so multiple requests can execute against the same store on different
worker threads. The store's `_sessions` dictionary is inserted/read/removed outside a common
lock. `_completion_lock` protects only the narrow successful-save-vs-cancel critical section.
In particular, `_cleanup()` iterates `self._sessions.items()` without that lock while another
start/cancel/completion thread may insert or pop an entry. Python dictionary mutation during such
iteration can raise `RuntimeError`; the package tests cover cancellation versus in-flight
provider confirmation/save, but not concurrent cleanup/start/cancel mutation.

**Consequence.** Two local settings clients—or overlapping QR actions from one client—can turn an
otherwise valid connection attempt into a 500-class connect failure or leave stale session state
solely because session bookkeeping raced. This is most plausible around a start/poll cleanup
overlapping a cancel or another completed/start session.

**Qualification.** The connector routes are authenticated and local-browser restricted, so this is
not an unauthenticated remote denial-of-service finding. Individual dictionary get/pop/set
operations are not claimed to corrupt CPython memory; the defect is the unsynchronized compound
iteration/state transitions across real worker threads.

**Smallest later alternative.** Own all `_sessions` reads/writes/cleanup under one lock (using a
per-session lock only for slow completion work where appropriate), or keep session state on the
event loop and offload only provider calls rather than the state machine itself.

## Retained E01-F observations / E01-G or later questions

1. `FeishuConnectFlow` always sends `domain: "feishu"`, including replacement/create flows,
   while the backend connector and config model explicitly support `domain="lark"`. The UI copy
   says either Feishu or Lark can scan the QR code. Confirm in E01-G whether the deferred
   registration transport makes a Feishu-started QR genuinely cross-domain; if not, promote the
   unreachable Lark QR path there.
2. Duplicate enabled app identities are intentionally persisted but only one is effectively
   enabled. A failed attempt to enable the suppressed duplicate can therefore leave latent
   `enabled=true` desired state that becomes eligible if the current owner is later disabled or
   changes identity. Tests deliberately preserve duplicate app records and effective suppression,
   so keep this as a desired-state/product-semantics question unless E01-G shows an unsafe
   transition.
3. `mode="create"` generates assistant IDs from only three random bytes
   (`assistant-<6 hex>`) and does not check the generated ID against existing config before the
   external registration begins. Collision is unlikely at ordinary assistant counts but becomes a
   destructive replacement risk at high cardinality; retain for P01 unless scale expectations make
   it material sooner.
4. The connect-session dictionary has no maximum session count. Sessions expire logically but are
   physically cleaned only by a later start/poll action. Together with repeated abandoned connect
   flows this is a connector-specific cardinality/lifetime question for P01; E01-F26 owns only the
   concrete cross-thread race.
5. The server returns a provider-requested poll interval, and the generic UI respects a minimum
   interval, but the server does not enforce per-session poll throttling. Because the route is
   local/authenticated, retain provider-hammering policy for P01 rather than promoting here.
6. A transient provider poll exception is stored as `last_error` but not surfaced in the pending
   payload, so the UI can continue displaying “Waiting for authorization” until expiry. Retain as
   UX/observability polish unless transport review shows common non-healing errors.
7. Invalid/non-dict/duplicate-ID raw Feishu instance records are skipped by runtime-spec expansion
   so healthy instances can continue. Canonical writes reject duplicate/invalid IDs. This is
   fail-closed for runtime authority but can hide manually corrupted records from the instance UI;
   retain as config-recovery policy rather than promote a defect.
8. The per-instance `name` fallback is seeded by defaults before `setdefault`, so a manually
   materialized non-default instance without an explicit name may display simply as “nanobot”.
   QR-created instances pass an explicit generated name, so this is limited presentation polish.
9. Remote assistant avatar URLs are rendered directly by the browser when available. Any browser
   privacy/local-network implications depend on the provider's avatar URL guarantees and broader
   WebUI policy; do not double-count E02 without integrated evidence.
10. Manual per-instance settings saves do not run the Feishu validator first. The shared hot-runtime
    path and deferred Feishu identity-boundary synchronization need to be reviewed in E01-G before
    classifying app-ID/domain changes, access reset and failed-start behavior.
