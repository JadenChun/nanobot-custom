## 2026-11-07 R01-A checkpoint

R01-A established the remote owner/device authority split across fourteen fresh primary-body reads. Durable device/scopes/revocation and refresh hashes live in the independent owner store; short-lived access credentials are memory-only; owner pairing requires local approval; and gateway owner-permission mutations use a typed authorize→single-use-consume admission before the existing workspace permission owner acts.

One provisional P2 finding is retained: desktop approval persists the device and stores only the refresh hash before the phone has confirmed custody of the plaintext access/refresh pair. `PairingService.poll()` also marks that in-memory result delivered before IPC/HTTP response delivery. Owner restart or response loss in that window can therefore strand a durable paired device with no recoverable client credential, requiring local revoke/re-pair. R01 transport/native conclusions remain pending.

## 2026-11-07 R01-C checkpoint

## 2026-11-07 R01-E checkpoint

R01-E adds a complete full-body review of the 1,359-line Android `NativeNetworkPlugin.kt`, the central bridge that owns pairing, refresh, native transport lifecycle, HTTP/WS correlation, media/attachment helpers and custody integration. Cumulative R01 source review is **F31/P0/R39**, still unpublished and coordinator-unaccepted.

Two new provisional P2 findings are retained. **R01-F09** records a submit-before-correlation race: both Android `jsonRequest()` and the shared mobile JS runtime install their request-ID waiter only after native HTTP has already launched its worker, so a fast completion can be consumed as an unmatched generic event and the owning request later times out. Refresh can turn that race into the same credential-stranding consequence described in R01-F03. **R01-F10** records a transport-size mismatch: the native broker admits roughly 36 MiB WebSocket frames but JNI retries event polling with at most 12 MiB. Because accepted WS frames are base64-wrapped in JSON, a raw frame around 9 MiB can exceed the JNI buffer; the Go queue deliberately retains that head event, while Kotlin treats JNI null as no event, wedging the entire event pump until transport restart.

Counterevidence narrowed the remaining leads: native route policy still blocks raw arbitrary dialing, Tailscale login URLs are independently whitelisted in Go and Kotlin, single-flight refresh plus custody fencing prevents post-logout credential resurrection, and no deterministic current OOM threshold was established for the chunked outbound-frame Java buffer. R01-F is limited to seven Android attachment/link/media helper primaries.


## 2026-11-07 R01-F checkpoint

R01-F adds seven full Android primary-body reads covering attachment policy, pairing challenge/deep-link parsing and the media helper/interceptor layer. Cumulative R01 source review is **F38/P0/R32**, still unpublished and coordinator-unaccepted.

One new provisional P2 finding is retained. **R01-F11** records that the production `NativeMediaInterceptor` logs the complete signed `/api/media/<sig>/<payload>` request URL at INFO whenever media opens. That URL is itself a replayable HMAC capability: the direct desktop media route verifies the signature/path but does not require a separate API token, and the signature carries no embedded expiry. The consequence is bounded by access to Android logs and network reachability, so this is retained as P2 rather than a broader owner-authority defect.

Counterevidence narrowed the rest of the helper slice: pairing/challenge parsers are strict, the native streaming API does preserve canonical `Content-Type`, and the current product bridge no longer exposes the legacy `NativeMediaFetcher`/handle-based picker path. The handle store double-counts its byte budget and the legacy media fetcher consumes unrelated events, but both are retained as unwired/dead-path cleanup observations rather than promoted live findings. R01-G is limited to the five-file JNI/C ABI and Go-export boundary.


## 2026-11-07 R01-G checkpoint

R01-G adds five full JNI/C/Go-export primary-body reads covering the Android JNI bridge, native probe, Android tsnet interface shim, exported Go C ABI and public header. Cumulative R01 source review is **F43/P0/R27**, still unpublished and coordinator-unaccepted.

One new provisional P2 finding is retained. **R01-F12** records that the exported native `last_error` diagnostic is a single process-global C string whose writer, `setError()`, frees/replaces it without the mutex used by `nanobot_network_last_error()`. Android invokes the ABI concurrently from the event poller, cached operation executor and WebView media path. Concurrent failures can therefore misattribute error text, double-free the same C pointer, or free it after `last_error()` returns but before JNI's `NewStringUTF()` copies the bytes, creating an Android process-crash window.

Full ABI review reaffirms R01-F10 rather than duplicating it: JNI still retries retained oversized events with a fixed 12 MiB buffer and converts a second negative result into null/no-event. The media read ABI correctly distinguishes EOF from negative error, while the Java stream collapses both to EOF; that observation is carried into R01-H because the exact truncation/cache consequence depends on the unread Go media body. The remaining typed ABI is narrow and its current C/Android tests are sequential rather than concurrent. R01-H is limited to the eight Go native-broker core primaries.


## 2026-11-07 R01-H checkpoint

R01-H adds eight full Go native-broker primary-body reads covering config normalization, tsnet lifecycle/peer resolution, bounded event delivery, HTTP policy/redirects, media streaming/cache, encrypted state and WebSocket concurrency. Cumulative R01 source review is **F51/P0/R19**, still unpublished and coordinator-unaccepted.

Two new provisional P2 findings are retained. **R01-F13** records a broker backpressure gap: HTTP admission checks event-queue occupancy only before launching asynchronous work, but terminal HTTP response/error events later use non-blocking emits whose queue-full failures are discarded. WebSocket close/error notifications can be dropped the same way. Server/native state can therefore advance while Android/JS later times out or retains stale socket state; refresh/pairing/revoke paths make that ambiguity materially observable. **R01-F14** records that the advertised 512 MiB media-cache budget is only applied after a complete full-response temp file is written, fsynced and renamed. Because the cache lives under persistent `filesDir/network-state` and signed media has no corresponding size ceiling, one sufficiently large stream can exceed the budget or hit ENOSPC before trimming.

Counterevidence narrowed the rest: revocation detection explicitly purges both media caches; state writes are authenticated, atomic and directory-fsynced; redirects remain GET-only/same-origin/re-allowlisted; the media read-error→EOF wrapper does not commit corrupt cache entries because cache completion is set only on true EOF. R01-I is limited to the five packaged-WebUI bootstrap/runtime-composition primaries.


## 2026-11-07 R01-I checkpoint

R01-I adds five full packaged-WebUI/bootstrap primary-body reads covering Capacitor/Vite composition, the fixture shell/broker and the 937-line production mobile bootstrap. Cumulative R01 source review is **F56/P0/R14**, still unpublished and coordinator-unaccepted.

One new provisional P2 finding is retained. **R01-F15** records that the phone pairing UI's **Cancel** action only fences/clears volatile JavaScript state. QR/link collection persists the pairing id/origin/challenge in encrypted native custody for process-death recovery; the Cancel handler never clears that durable record. On the next app launch, startup calls `pendingPairing()`, restores the canceled challenge and resumes polling automatically. If the desktop owner approved it meanwhile, the phone can persist pairing credentials without a fresh phone-side pairing action. The same gap applies when Cancel races an in-flight native `pairStart()`: browser generation checks ignore the late result, but native collection can still persist pending state after Cancel.

Counterevidence narrows the rest: release/debug packaging explicitly uses `www-shared`, mixed content is disabled, the shared service worker is removed/suppressed, bearer/refresh material remains native, and the production WebSocket bridge chunks Capacitor calls at 256 KiB. Existing tests cover late in-memory pairing completions after Cancel but do not model the later-added encrypted pending-pairing state. Console-to-logcat mirroring and full-frame Java accumulation remain observations, not new promoted findings. R01-J is limited to the eight mobile build/package wrapper primaries.
