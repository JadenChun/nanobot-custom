# P3 version-2 cron action-store contract

`nanobot.cron.action_store.CronActionStore` is an isolated private POSIX primitive. It is not imported by the cron service and does not execute or deliver cron jobs. Package B adds an explicit, stopped-writer conversion boundary for legacy cron files. Package C will bind the opaque replay candidate to the canonical cron store, Package D will establish occurrence authority, and Package E will add destination receipts and uncertain-send reconciliation. The migration guard remains closed until those packages and their integrated acceptance evidence exist.

## Public bounded API

Construction requires an absolute, non-root, private directory and a UTF-8 store namespace of at most 512 bytes:

```python
store = CronActionStore(root, namespace="cron:workspace-a")
receipt = store.append(action_id="opaque-request-id", request={...})
state = store.replay()
settled = store.checkpoint(expected_generation=state.generation, candidate={...})
```

`append` accepts an opaque JSON object only. It returns an `ActionReceipt` containing namespace, action ID, canonical request digest, sequence, and the journal generation that established it. Reusing an action ID is accepted only when the canonical request digest is identical. `replay` returns detached data: the prior opaque candidate (or `None`), ordered pending opaque actions, all retained receipts, and an `ActionStoreGeneration` CAS token. The module never applies `add`, `update`, or `del` semantics. A later adapter derives its candidate from the returned values.

`checkpoint` accepts only the exact generation returned by `replay`. The token includes the journal generation, snapshot generation, snapshot watermark, and latest visible action sequence, so an append after replay makes a checkpoint stale. It writes a detached opaque candidate after all actions visible to that generation, then compacts the journal. A stale generation fails. Retrying the same token and canonical candidate after a durability error is safe: a published snapshot records its prior generation and is settled or re-proved. Retrying that token with different candidate content fails as a conflict.

The hard limits are 1 MiB per snapshot or journal record, 256 KiB per opaque request/candidate JSON encoding, 8 MiB for the entire current journal, 4,096 retained action receipts, 512 UTF-8 bytes for namespace and action ID, and action IDs matching `[A-Za-z0-9][A-Za-z0-9._:-]{0,511}`. Reaching a receipt or size limit fails closed and requires a later, reviewed export/retention policy; this package must not discard idempotency evidence itself.

## Version-2 durable wire protocol

`journal.jsonl` begins with exactly one strict JSON header:

```json
{"schema_version":2,"kind":"journal_header","store_namespace":"…","journal_generation":1,"base_sequence":0}
```

Each subsequent strict JSON line is an opaque action with that namespace and journal generation, a contiguous sequence of `base_sequence + 1`, an action ID, a SHA-256 canonical-request digest, and the request object. The canonical digest is SHA-256 over `nanobot-cron-action-v2\0` followed by canonical sorted, finite JSON. No field has a default. Every schema version, generation, sequence, base, and watermark field is an exact Python/JSON integer: booleans and `2.0` are corruption even when equality would otherwise succeed. Unknown fields, duplicate object keys, non-finite values, malformed UTF-8, missing final newlines, sequence gaps, and duplicate action IDs are also corruption.

`snapshot.json` is strict version-2 JSON with a namespace, target journal generation, monotonic snapshot generation, base/watermark, prior generation, opaque candidate, and a complete contiguous receipt list through its watermark. A snapshot receipt preserves the original action ID, digest, sequence, and journal generation. Receipt generations must be positive, never later than the prior journal generation, nondecreasing by sequence, older than the current journal for a previously compacted prefix, and exactly the prior journal generation for the new suffix. This makes action retries exact even after compaction.

On checkpoint the store first writes, file-fsyncs, atomically replaces, and directory-fsyncs the snapshot. Its fsynced staging descriptor remains open across the descriptor-relative rename; the destination entry must match that exact inode before and after directory fsync. Only then does it write, file-fsync, replace, and directory-fsync a new header-only journal whose generation and base equal the snapshot's target generation and watermark, using the same staged-descriptor proof. A restart which sees the new snapshot but old journal accepts it only when the journal is the exact receipt prefix covered by that snapshot and contains no later action. It re-fsyncs the snapshot and directory before finishing journal cleanup. Any other mixed state is ambiguous and fails closed.

The action header and every append are independently file- and directory-fsynced before acknowledgement. An append retry with the same action ID and digest re-fsyncs its source before returning its old receipt. These retry rules make failures after writes, renames, or directory fsyncs safe without silently treating visible data as durable.

## Package B legacy conversion

`CronActionStore.convert_legacy(root, namespace="…")` is an explicit, one-way, local migration operation. It must run with all legacy cron writers stopped. Service startup never invokes it, and success does not enable job execution. The result reports a deterministic conversion identity, converted action count, source-backup digests, and whether a jobs snapshot candidate is available.

The converter accepts only a private, newline-terminated `action.jsonl` containing strict JSON records with exactly `action` and `params`. `action` is one of `add`, `update`, or `del`; `add` and `update` must contain a valid cron-job object, and `del` must contain exactly one non-empty `job_id`. Unknown actions, duplicate JSON keys, empty lines, malformed JSON, truncated records, or malformed action-job payloads fail closed before changing the action source bytes. A malformed `jobs.json` instead records `unavailable` while preserving that snapshot and the independently converted action journal.

Each legacy action receives a deterministic action ID from the conversion identity, complete source digest, and one-based line ordinal. The conversion identity is SHA-256 over the conversion schema tag, store namespace, and verified original action/jobs source digests. `conversion.json` records those original digest references only as evidence: each resume recomputes the identity from the private source or content-addressed backup and rejects a mismatch. Thus duplicate source lines remain separate actions. Legacy `add` and `update` records become opaque `upsert` requests with `runtime_state_policy: "snapshot_wins"`; a later adapter must preserve the newer snapshot runtime state instead of applying stale action history. `del` becomes an opaque `delete` request. The request carries its source digest and ordinal for audit. On every resumed conversion, the converter reads the verified backup bytes again, recreates every operation and ID, and requires an exact canonical match with `conversion.json`; a manifest never supplies action semantics by itself.

The converter accepts established camelCase and snake_case aliases only for persisted timing, delivery, origin, history, and identity fields; a record may not carry both aliases for the same field. It does not coerce booleans, numeric strings, empty strings, or other falsey values into valid job data. Job ID and name are non-empty strings; booleans are exact booleans; timestamps and durations are exact non-negative integers; schedules are `at`, `every`, or `cron` with their required scalar fields; execution status is `ok`, `error`, or `skipped`; historical run outcomes are `completed`, `succeeded`, `failed`, `pending`, `running`, `cancelled`, `skipped`, or `error`; and histories/destinations are lists of complete objects. Unknown fields, malformed destinations, bad IDs, invalid status values, or a missing/non-list history fail closed rather than being discarded. The validated values then pass through the established cron parsers, preserving schedule timezone, delivery and origin fields, timestamps, enabled state, runtime state, run history, run IDs, run status, and occurrence IDs. Every converted job gets a stable `jobInstanceId` derived from the conversion identity and job ID, plus a `definitionRevision` digest over its definition.

Before an action source is retired or a jobs snapshot is represented in the v2 state, its exact bytes are copied to `legacy-backups/<sha256>.bin`. A backup first uses a unique private staging file, file-fsyncs it, atomically renames it through held descriptor-relative paths, and keeps that descriptor open while proving the final entry before and after the backup-directory fsync. Backup files are private (`0600`), their directory is private (`0700`), and all root, directory, and file bindings are rechecked across the durability boundaries. Interrupted staging files use private `.legacy-backup.*.tmp` names and are ignored as forensic evidence on retry; they can never be mistaken for a final digest backup. `conversion.json` is a private, atomically replaced manifest that records the namespace, conversion identity, original source-digest evidence, generated operations, and separate action/jobs statuses. Before source removal, status transition, or a completed-conversion acknowledgement, the converter also requires a durable v2 receipt for every reconstructed operation: action ID and request digest must match exactly, and the receipts must retain the original contiguous order and journal generation. A missing, conflicting, or sequence-incompatible receipt is corruption; the source remains in place. The action source moves through `pending`, `removing`, and `converted` only as recovery hints, never as authorization, so a failure before or after the unlink is resumable. `jobs.json` is deliberately retained after conversion so a changed digest or a new legacy writer is fenced.

A valid legacy `jobs.json` creates a generic v2 checkpoint candidate containing the canonical jobs and converted operations. This is a representation only: Package C owns applying it to the canonical cron store. If `jobs.json` is corrupt, actions still convert and remain durably replayable, the jobs backup is retained, and the manifest records `unavailable`. Restoring a valid stopped-writer jobs snapshot and explicitly rerunning conversion can then create the candidate. A completed conversion is idempotent; a reappearing `action.jsonl`, changed converted jobs digest, conflicting checkpoint, unsafe backup object, or journal version downgrade is corruption and stops the migration.

The legacy action and jobs inputs use the action-store's 8 MiB bounded private-read limit. Generated v2 requests, checkpoint candidate, journal, and receipt retention remain subject to the normal v2 limits above. A limit or durability failure returns an error and may be retried after the underlying condition is repaired; it never drops source bytes or idempotency evidence.

Rollback is an operator operation with all writers stopped. There is no reverse-conversion API. Restore the desired exact source bytes from the content-addressed private backup, remove the v2 conversion state only through a reviewed recovery procedure, and verify ownership and source digests before restarting a legacy writer. Do not attempt rollback while either the legacy service or a future v2 adapter can write the directory.

## Filesystem and migration boundaries

This package is qualified only on POSIX systems offering `flock`, held descriptor-relative operations, no-follow opens, and directory fsync. It imports on Windows but construction fails closed. It traverses the configured absolute physical path with held no-follow directory descriptors and binds root/lock inodes. Before and after every file or directory fsync that may establish durability or return an acknowledgement, it re-traverses that configured path and requires its root inode to equal the held root. Journal and snapshot descriptors are also checked against their current directory entries before and after fsync, so a same-owner/mode replacement cannot be acknowledged. Root is mode `0700`; lock, journal, snapshot, and temporary files are owned regular single-link files mode `0600`. Existing unsafe paths, symlinks, hard links, mode/owner changes, and root/lock replacement are corruption and are never repaired in place.

The root is dedicated to this primitive. Outside the explicit Package B conversion boundary, a legacy `action.jsonl` filename is detected and raises `ActionStoreConversionRequiredError`; no conversion is attempted. `jobs.json` remains outside normal action-store ownership. Package B reads it only while writers are stopped and never overwrites it. Packages C through E still need to bind converted candidates to canonical job state, establish occurrence and delivery authority, and provide their integrated acceptance evidence before any production use.
