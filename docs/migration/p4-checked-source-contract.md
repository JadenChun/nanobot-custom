# P4 checked-source lock authority contract

`nanobot.session.checked_source.open_checked_session(backend, key)` issues a context-managed capability for one exact `JsonlSessionStore` object and key. The caller must already hold memory authority before entering it. The capability provides `require_current()`, `read_source_bytes()`, `replace_source_bytes(new_bytes)`, and `close()`; it cannot open arbitrary paths or expose descriptors. It is process-local, bound to the exact `Thread` object that issued it, and cannot be copied or serialized.

Entry pins the configured absolute session namespace by opening `/` and walking every path component with descriptor-relative, no-follow directory opens. It retains each ancestor descriptor and the initial directory identity, owner, mode, and parent-edge identity. Before creating or acquiring locks, it requires the session namespace and its migration-lock parent to be effective-user-owned, owner-readable/searchable, and free of group/other write bits and special permission bits. Normal `0755` namespaces and `0700` migration parents are accepted. Higher ancestors must be owned by the effective user or root and must not be group/other writable, except for root-owned sticky system directories such as `/tmp`. The final pinned directory must agree with `backend.sessions_dir`. Each `require_current()` and successful context exit checks every retained descriptor and path edge again. A path, identity, owner, or mode change fails closed with a content-free error code.

The authority acquires locks in this order, using nonblocking exclusive `flock` compatible with the repository's `filelock.FileLock` paths:

1. `<sessions-root>/.workspace-migration.lock`
2. `<sessions-root>/<namespace>/.execution-locks/<storage-key>.lock`
3. `<sessions-root>/<namespace>/.session-files.lock`

The lock files are persistent synchronization objects. Existing files are accepted only when they are empty, regular, owned by the effective user, have one hard link, and have exactly mode `0600`, `0604`, `0640`, or `0644`. Existing files are never chmodded, truncated, written, or unlinked. Missing lock files are created exclusively with no-follow semantics. The returned descriptor is recorded immediately; only that newly created descriptor may be fchmodded, to `0600`. The descriptor and path are compared before and after `flock`, and lock files are never unlinked during cleanup.

The `.execution-locks` directory must be a current-owner directory with exact mode `0700`. If absent, entry attempts `mkdir(0700)` and establishes a fresh no-follow baseline before adoption. A restrictive umask that leaves a different mode produces an `unsafe` failure; that residue is preserved for operator inspection and is never repaired or deleted. A same-UID substitution that occurs before the fresh baseline and presents a safe `0700` directory is indistinguishable from the created directory and may be adopted. Substitution or metadata drift after the baseline is detected and rejected.

Lifecycle is `NEW -> ACTIVE -> CLOSED`, with one entry only. A child process rejects inherited authority before touching its inherited mutex and closes its inherited descriptors without `LOCK_UN`; closing those duplicate descriptors does not release the parent's lock. Calls from a different thread or process fail. Closing detaches descriptor ownership before release and close, so repeated close cannot close an unrelated descriptor that later reuses the same integer.

`read_source_bytes()` and `replace_source_bytes()` are valid only while this exact authority is active and its original three lock descriptors remain held. Calls in `NEW` or `CLOSED` fail with `closed`; calls from a foreign thread or process fail with `invalid`. Neither method reacquires locks or repairs an authority. A successful `read_source_bytes()` retains a private copy of its exact bytes and the complete source stat signature (device, inode, UID, GID, full mode, link count, size, modification time, and change time) as a replacement precondition. A later successful read replaces that private evidence.

Under the three locks, the method revalidates the authority and selects only the exact canonical `<storage-key>.jsonl` entry relative to the pinned session-directory descriptor. It takes a no-follow pre-open stat baseline containing device, inode, UID, GID, full mode, link count, size, modification time, and change time. The source must be a regular file owned by the effective user, owner-readable, have one hard link, and have no group/other write or special permission bits. Ordinary `0600` and `0644` source modes are accepted. An initial size over **67,108,864 bytes (64 MiB)** fails with the fixed `limit` code before opening.

The source is opened read-only, no-follow, nonblocking, and close-on-exec, relative to that pinned directory. The opened descriptor and the current pathname entry must both match the original pre-open baseline before any bytes are read. The method reads in chunks of at most 64 KiB, retries `EINTR`, permits short reads, and consumes no more than the limit plus one byte. It detects early EOF, growth, truncation, path or descriptor replacement, and metadata drift. Between chunks and after EOF it revalidates retained directory ancestry and all three lock identities. It returns detached bytes only after the final descriptor/path comparisons and authority validation succeed; every failure returns no partial data and closes the read descriptor once. Bytes are not decoded, parsed as JSON, sent through the ordinary session loader, or logged, and the source is never written or repaired.

`replace_source_bytes(new_bytes)` accepts only a `bytes` value no larger than **67,108,864 bytes (64 MiB)** and requires retained evidence from a successful source read on this same active authority. A missing read receipt or wrong input type fails with `invalid`; oversized replacement bytes fail with `limit`. The first valid replacement invocation consumes the receipt and marks this authority as used, so it permits at most one replacement attempt even if another read is taken later. Before creating a temporary entry, and again immediately before replacement, it revalidates the authority and reads the entire canonical source through a no-follow descriptor. Both its full stat signature and exact content must still equal the retained evidence; equal-byte inode replacement and same-inode content changes fail with `changed`.

The replacement is written to a random private basename in the pinned namespace using descriptor-relative `O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC|O_NONBLOCK` creation with mode `0600` and bounded collision retries. The newly created descriptor is recorded immediately. Only that descriptor may be fchmodded, and only to establish its required `0600` mode. The method writes all bytes while handling short writes and `EINTR`, checks that the temp descriptor and no-follow pathname still identify the same regular file, verifies exact bytes and size, fsyncs the file, then rechecks the source and authority before calling descriptor-relative `os.replace`. Once `os.replace` is attempted, any error is reported as `uncertain`: the canonical source may already have changed. On success it verifies that the canonical pathname identifies the temp descriptor and contains exactly the requested bytes, fsyncs the pinned namespace directory, and revalidates the authority. It never rolls back the source or unlinks a temporary name after a failure; pre-replacement temporary residue is left for inspection, and ambiguous names are never cleaned up.

The replacement check and `os.replace` are separate pathname operations. A same-UID actor that does not honor the cooperating locks can substitute the temp basename after the final `_check_temp_entry` and before `os.replace`; the replacement may then publish that actor's bytes at the canonical source. The post-rename descriptor/path check detects the substitution and returns `uncertain`, but cannot guarantee that the requested bytes were published or undo the change. This capability is a cooperating-lock checked precondition, not an adversarial same-UID compare-and-swap.

Public failures use only `invalid`, `unavailable`, `unsafe`, `changed`, `busy`, `missing`, `closed`, `io`, `limit`, and `uncertain`. Their messages contain no backend paths, keys, source values, or underlying exception details, and they carry no live exception cause or context. This capability does not change ordinary session APIs or establish source-session format semantics. The lock assumes cooperating code uses the same paths and `flock` protocol; it does not authenticate against a same-UID actor that substitutes a safe directory before the initial baseline.
